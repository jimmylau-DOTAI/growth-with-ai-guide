# 睇完一篇 AI 文章點先算學到？唔係摘要，而係它改變了你哪個工作決定

你可能儲了很多 AI 文章、影片和帖文：看當下覺得很有道理，甚至用 AI 幫忙整理了摘要；但到下一次真要寫 brief、設計 workflow 或 review output，還是很難說出這些內容究竟令你改變了甚麼做法。收藏證明你見過，摘要證明你能重述，兩者都未必等於你有了自己的判斷。

另一個風險是把作者的案例、數字或成功說法直接換成自己的語氣。這不但會誤導讀者，也會令你錯過最重要的一步：外部 source 在你的工作裡是否真的適用？它需要哪些條件？它有哪個地方不應照抄？

Jimmy 的判斷是：一條 source 只有在它令你對一件真工作作出更清楚的取捨，才開始變成你的 insight。你要把「作者說甚麼」和「我現在怎樣做」分開，再說清適用邊界和甚麼新 evidence 會令你改變主意。

| 你留下的東西 | 它能證明甚麼 | 它仍缺甚麼 |
|---|---|---|
| Source link／收藏 | 你見過一段內容 | 與你的工作有何關係 |
| 摘要 | 作者的主張是甚麼 | 你是否同意／如何使用 |
| Source-to-decision note | 你選擇怎樣做 | 能否在新 evidence 下更新 |
| 可重用 rule | 某個 decision 已多次被驗證 | scope、owner 和 expiry |

## AI source、摘要和工作判斷，到底差在哪裡？

Source 是外部作者的材料；它可能啟發你、提供 evidence 或讓你看到另一個做法，但它不會自動變成你的成果。摘要則把 source 的內容縮短，仍然主要回答「作者講了甚麼」。兩者都很有價值，但如果沒有連到一件真工作，它們很容易只留在知識收藏夾。

工作判斷多了一個不能略過的動作：你要說清 source 令你在現在的情境決定保留、改變或停止甚麼，及其原因。這不代表你一定同意作者，也不代表你已驗證其成效；它只是令你不再把閱讀當作完成，而是把它放進一個可 review 的選擇。

**Jimmy 的結論：** 真正屬於你的不是把作者句子改成第一人稱，而是你能說出它讓你在哪一個工作選了甚麼、為何這樣選。

| 層次 | 可問的問題 | 完成時留下甚麼 |
|---|---|---|
| Source | 作者直接說了甚麼？ | link、日期、原始說法 |
| 摘要 | 主要論點／流程是甚麼？ | 壓縮後的重點 |
| Judgment | 我在這件工作同意、不同意或要補甚麼？ | Jimmy／自己的取捨 |
| Decision | 下一次怎樣做？ | 明確行動或停止線 |
| Boundary | 何時不適用、何時改主意？ | evidence boundary |

只要還答不出最後三格，先誠實地把它留作 reference。不是每條 source 都需要硬變成 insight，更不用因為儲得多便假裝學得深。

## AI source 應怎樣選，才值得花時間變成自己的 decision？

先不要由整個收藏夾開始。選一條你近期可能真的會用到的公開 source：它令你重新考慮一個 workflow、review、材料邊界或工具選擇。這樣你有一件真工作作為鏡，較容易看見作者的主張究竟能否改變你的做法，而不是只感到「很有啟發」。

不適合作為第一輪的，是來源不清、無法回看、純勵志、只講成效但沒有機制，或你根本找不到它會影響哪一個工作。這些內容可以暫時留作 reference，但不能給它一個你未能說明的「洞見」身分。

**Jimmy 的結論：** 值得消化的 source 不一定最熱門；而是它能讓你在近期一件工作作出更清楚、可驗證的取捨。

| Source 狀態 | 是否適合作第一輪 | 原因 |
|---|---|---|
| 公開文章，讓你重想 AI 資料不足時應否先問 | 適合 | 可立刻放進 briefing／draft 工作試驗 |
| 只有一句「某 AI 幫人省很多時間」 | 暫不適合 | 缺機制、條件和可驗證 decision |
| 無原作者的轉圖／轉述 | 暫不適合 | 不知內容、時間和主張邊界 |
| 一個與你目前 task 無關的工具 demo | 留 reference | 先不硬建 judgment |

選 source 時也要先看公開安全：不要把私人 Vault、客戶、會議記錄、OCR 或未批准原文搬進公開筆記。外部 source 是啟發，私有工作材料仍應留在原有受控位置。

## Source says 和 My judgment 怎樣分開，才不會把外部主張冒充成自己的成果？

外部 source 的主張有它自己的情境、受眾、資料和限制。你可以引用它提出的問題、機制或例子，但不能把它的 ROI、案例、技術結果或作者觀點寫成「我已做到」或「這對所有人都成立」。這是公開寫作的誠信問題，也讓你在內部決策時不會把別人的證據誤當成本地證明。

My judgment 則是你的延伸：在現有工作下，你同意哪一部分、要補甚麼條件、暫時拒絕哪個太大的跳躍。這格可以比 source 更貼近你的處境，但必須承認它是你自己的判斷，而不是作者已經為你驗證的結論。

**Jimmy 的結論：** Source 只負責說它說過甚麼；你的 judgment 才負責說在這個工作你會怎樣取捨，兩者不能混成同一條主張。

| 欄位 | 應寫甚麼 | 不應寫甚麼 |
|---|---|---|
| Source says | 作者可回看的直接主張／機制 | 把作者案例的成效套到自己身上 |
| My work context | 你正在處理的 generic 工作問題 | 客戶、合約、CRM、未公開資料 |
| My judgment | 同意／不同意／需要的條件 | 假裝作者已驗證你的處境 |
| Decision for now | 下一次的最小做法 | 一次跳到全自動／對外行動 |

```text
Source says：＿＿＿＿＿＿＿＿＿＿
My work context：＿＿＿＿＿＿＿＿＿＿
My judgment：我同意／不同意／要補的條件是＿＿＿＿＿＿＿＿＿＿
Decision for now：下一次我會＿＿＿＿＿＿＿＿＿＿
```

分欄寫，會令你在關掉 source 後仍然知道自己的決定是甚麼，也令任何人都可追問哪一句來自外部、哪一句是 Jimmy／你的延伸。

## My work context 怎樣寫，才不會把 private Vault 搬進公開 insight？

有些人一聽到「放進真工作」，便把會議紀錄、客戶名單、合約細節或 CRM 狀態全放進 note。這既不是必要 context，也不適合公開。你只需要用 generic／synthetic 描述說明工作摩擦：例如「把公開資料轉成 internal briefing，常缺日期或方法」；這已足夠讓判斷有真實使用情境。

若這條 source 只在一個私人、敏感或未公開案例才適用，它可能很有價值，但應留在 Vault 的受控 insight 層，而不是為了 GitHub 攻略而強行 sanitise。公開版要保持可以獨立學到判斷，同時不讓讀者反推任何客戶、項目或 production data。

**Jimmy 的結論：** 真工作 context 要足夠說明判斷，卻不需要暴露真實的人、資料或未公開結果；無法安全抽象的內容就留在私有層。

| Context 寫法 | 是否適合公開 | 原因 |
|---|---|---|
| 「公開活動資料缺日期，AI 是否可先起 internal brief？」 | 適合 | 有工作摩擦，沒有私人資訊 |
| 「某客戶的合約與 CRM 欄位如何處理」 | 不適合 | 涉及客戶、商業與受控資料 |
| 「新手教學稿常先講工具、忘了讀者的工作」 | 適合 | 可重用、非敏感的判斷 |
| 「某內部 campaign 未發布的成效」 | 不適合 | 未公開結果不能作公開 evidence |

把 context 安全地抽象後，你的 source-to-decision note 仍可教人怎樣想；它不需要披露任何私有細節才看起來「真實」。

## Decision for now 怎樣寫，才不會由「我同意」停在抽象道理？

「我認同 AI 應先問問題」是一個態度，不是一個工作決定。它沒有說明在哪類任務要問、要問多少、問不到時怎樣做；下一次你仍會隨意選擇是否跟從，AI 也沒有辦法在 prompt 中執行。Decision for now 應該把主張縮小到一個近期可以試、能被 reviewer 看見的動作。

最好的決定通常不是大轉型，而是保留、改變或停止一件小做法。它有明確工作、最小 action、可見 artifact 和人手邊界；做完後你能說這個 source 是否真的令你的判斷變好，而不是只證明你看過它。

**Jimmy 的結論：** Insight 的完成線不是「我同意」；而是下一次在一個明確情境，你知道先做甚麼、不要做甚麼、怎樣知道它有沒有幫到。

| 抽象認同 | 可試的 decision for now |
|---|---|
| AI 資料不足要問問題 | 每次公開資料 briefing 前，先列最多兩條會改變結論的 unknown |
| AI 要有 review | 每份 internal draft 交前用三條 rubric 決定 pass／revise／stop |
| 要做 workflow | 先畫 input → draft → review → handoff，不接任何真系統 |
| 不要盲目追工具 | 用同一份公開材料比較兩個工具的 reviewability |

```text
下一次在哪個工作：＿＿＿＿＿＿＿＿＿＿
我會保留／改變／停止甚麼：＿＿＿＿＿＿＿＿＿＿
交回甚麼 artifact：＿＿＿＿＿＿＿＿＿＿
誰會 review：＿＿＿＿＿＿＿＿＿＿
本輪不可做：＿＿＿＿＿＿＿＿＿＿
```

當 decision 已小到可以明天試一次，你才有可能用結果回頭修正這條 insight，而不是把它供在筆記庫裡。

## Boundary 怎樣寫，才知道甚麼時候不應照抄 source？

每個 source 都有 evidence boundary：它可能來自某個市場、工具、作者個人 workflow，或只在特定風險與成本條件下成立。若你不寫 boundary，很容易把一個啟發當成普遍定律，最後不是過度自動化，就是把不適合的做法硬套到不同讀者、不同工作和不同權限環境。

Boundary 也不是一句免責聲明。它應說清何時不用、要看到甚麼新 evidence 才會改變主意、以及哪個決定仍要由人保留。這讓 source-to-decision note 能隨工作更新，並避免你因曾經寫下一條 rule 就把它當成不可挑戰的真理。

**Jimmy 的結論：** 一條成熟 insight 不只說「現在怎樣做」；它也說「這裡不適用」和「甚麼情況令我重新判斷」。

| Boundary 問題 | 例子 |
|---|---|
| 何時不適用？ | 純格式轉換、已具完整規格的工作不需先反問 |
| 哪個條件改變便要重看？ | 讀者、材料權限、對外後果或 reviewer 改變 |
| 哪些資料不能因它而使用？ | 客戶、合約、CRM、credentials、production data |
| 人仍要決定甚麼？ | 外發、權限、承諾、最終採用與高後果 action |

```text
Boundary：＿＿＿＿＿＿＿＿＿＿
不適用於：＿＿＿＿＿＿＿＿＿＿
若看到以下新 evidence，我會重看：＿＿＿＿＿＿＿＿＿＿
仍必須由人決定：＿＿＿＿＿＿＿＿＿＿
```

加上 boundary 不是削弱你的見解；它令讀者知道怎樣安全地使用它，也令 AI retrieval 不會把一條局部判斷錯套成所有問題的答案。

## 用「資料不足先問」的公開 source 示範，怎樣變成自己的工作 decision？

假設你讀到一篇公開文章，主張 AI 在資料不足時應先問問題。若只做摘要，你可能寫「作者認為 AI 不應亂猜」；若照抄案例，可能把對方的流程和成效當成自己的。這兩種都未足以幫你下次處理一份公開資料 briefing。

把它放進 source-to-decision note 後，工作才清楚：你常把公開材料變成 internal briefing，但日期、方法或批准狀態有時缺失。你的延伸不是要 AI 每次問十題，而是只要缺口會改變結論、對外後果或 reviewer 決定，便要列 unknown；純格式轉換則直接做。

**Jimmy 的結論：** Source 被消化後，不是變成更長的摘要，而是變成一個能在真工作分流「先問、先起 draft、研究或 stop」的判斷。

| 五格 | 這個例子的寫法 |
|---|---|
| Source says | 資料不足時，重要問題要先補關鍵資訊 |
| My work context | 公開資料轉 internal briefing 時，常缺日期或方法 |
| My judgment | 不需每次問很多；只問會改變決定的 unknown |
| Decision for now | briefing 前列最多兩條最影響結論的 unknown |
| Boundary | 純格式轉換不適用；涉及權限／對外承諾則 ask owner 或 stop |

```markdown
# Source-to-decision：資料不足時的 AI 反問

**Decision for now**
下一次公開 briefing 前，先列兩條最影響結論的 unknown；未知不能補成事實。

**Evidence boundary**
此做法不授權讀取私人資料，也不取代 owner 對日期、價格、承諾和權限的決定。
```

關掉原文後你仍能講清這份 decision，才代表 source 真正開始服務你的工作，而不只是留在收藏。

## Source 變成 decision 後，下一步應怎樣保留、合併或升成 rule？

先用 decision for now 在一兩個低風險情境試行，並留下最小 review evidence：它是否減少了同一種猜測？reviewer 是否更容易指出 pass、revise 或 stop？若結果只適合一個情境，保留為 source-to-decision note；不要太早變成長期規則。

若相近工作反覆確認同一個判斷，才把它整理成有 why、scope、owner 和 expiry 的 reference card；若它已經成為穩定 routine，再考慮放進 AI Operator 的 SOP 或 Skill。這讓你的 Vault 和 GitHub 攻略都保留 source、insight、rule、workflow 各自的角色，而不是所有東西混成「筆記」。

**Jimmy 的結論：** Source 消化的完成線不是存好一份 note；是你知道它現在只是 reference、已是局部 decision，還是已有足夠 evidence 升成可重用 rule。

| 現在的證據 | 最合適去處 | 暫時不要做甚麼 |
|---|---|---|
| 只看懂作者說甚麼 | Source／reference | 假裝已有自己的 insight |
| 能改變一件近期工作 | Source-to-decision note | 變成永久 memory |
| 多次 review 仍成立 | Reference card／rule | 忘記寫 scope 和 expiry |
| 有穩定 input、review、exception | SOP／Skill 候選 | 直接接 production action |

想實作這張 note，可先看 [把 feedback 變成 rule](turn-feedback-into-a-rule.md)；想知道資料不足要如何分流，讀 [資料未齊唔等於要停](../chapters/2-12-is-context-ready-to-draft.md)。可返回 [AI Super User stage](../02-ai-super-user.md) 看其他入口。本文只用公開／synthetic 情境，不會將 private Vault、客戶、合約、CRM、credentials 或 production data 變成公開內容。
