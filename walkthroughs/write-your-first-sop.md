# 同一件事隔幾個月又要重新摸索？用第一份 minimum SOP 留住工作標準

同一份月報、briefing 或內容檢查，你明明做過；隔一段時間再做，又要重新找資料、回想上次用哪個格式、猜哪一個決定仍有效。你不是不會做，而是每次都要重新記起自己上次怎樣做。速度可能因 AI 而快了，但重播判斷和重做的成本沒有少。

第一份 SOP 很容易寫錯：有人把一次成功的步驟立即寫死，有人寫了一大段只有自己看得懂的筆記，也有人完成後再沒有更新。這些文件看似有系統，卻無法讓下一位人或 AI 在沒有你在場時安全做對。

Jimmy 的判斷是：SOP 是讓下一次工作有標準可對照的最小合約。它不是保證效率或自動化，而是令下一位知道甚麼時候開始、哪些資料可信、做到哪裡才算可 review、遇到例外應怎樣停。這篇會帶你完成第一張可試跑的 minimum SOP。

| SOP 五格 | 要回答甚麼 | 寫清後留下甚麼 |
|---|---|---|
| Purpose | 這件事真正解決甚麼？ | 範圍與變通原則 |
| Trigger | 甚麼條件齊才開始？ | 不用猜的開始線 |
| Steps／input | 可根據甚麼、怎樣跑？ | 可交接動作 |
| Acceptance | 怎樣才算做完？ | 可 review 完成線 |
| Exception／refresh | 何時停、何時更新？ | 不會過期的邊界 |

## 你有印象，點解仍然不等於有標準？腦內做法無法被下一位對照

熟手做事時常會補上很多隱性判斷：他知道哪份檔案才是最新、哪個小錯可忽略、何時應該先問 owner。這些判斷並不會自動出現在一段「第一步、第二步、第三步」裡。只要換人、隔一段時間或交給 AI，就會顯露出來。

把做法寫下來的目的不是把自己鎖死，而是把可以檢查和討論的部分帶到工作表面。下一位如果卡住，能指出是 input 不清、acceptance 缺失還是 exception 未寫，而不是只說「我唔明」。

Jimmy 的結論是：一次做得好是表現；每次有同一標準可對照，才開始形成可交接工作。

先分辨三種常見假 SOP：

| 假 SOP | 為何不夠 | 第一個修法 |
|---|---|---|
| 流水帳 | 只有動作，沒有完成線 | 每段補「怎樣才算可交」 |
| 只有自己看懂 | 依賴「上次」「那份」等隱性背景 | 指定 source、owner、格式 |
| 寫完沒人碰 | 舊規則繼續被當現行 | 寫 refresh owner 與更新條件 |

如果你的文件有其中一種，不用推倒重來；先將它視為 SOP 草稿，補最早缺的一格即可。

## 第一份 SOP 揀邊件工作先最容易成功？選第三次出現、可回退的小 routine

很多人第一份 SOP 選最重要的工作，因為覺得最值得處理。可是最重要的工作通常例外最多、範圍最大、外部影響也最高；你很難分清是 SOP 未清、工作未成熟，還是個案本身太特別。寫到一半便會變成一本無人敢用的手冊。

第一份應選一件已做過約三次、輸出有相近形狀、出錯仍能人手收回的小 routine。你不需要證明 AI 能做很大件事；只需要看見下一位照著最少標準能否跑一段，並在例外出現時正確停下來。

Jimmy 的結論是：第一份 SOP 最值得買到的不是規模，而是一條能由真 run 驗證、再慢慢修正的工作標準。

選題時逐項確認：

1. 最近是否已出現約三次，可以比較差異？
2. 每次 output 是否有基本完成線？
3. 是否可以只用公開、已批准或 synthetic 材料試跑？
4. 是否有 owner 願意 review，且錯了可退回？

四項都接近成立，這件工作才比「最重要但最亂」的工作更適合當第一份 SOP。

## 五格應該點寫？先寫你下次不想再猜的條件，不要寫所有歷史

minimum SOP 不是把所有舊 chat、每個細節和所有例外搬進一個文件。這樣下一位仍然難找重點，AI 也會把歷史細節誤當成硬規則。它只需要留下下次工作真的要用、而且可被收貨的條件。

每格都應短到可以在下一輪更新。若你寫到某一格要放一大堆背景，改成連到 source of truth，再在 SOP 只寫那份資料的用途與何時有效。這令流程既有 context，又不會變成資料倉。

Jimmy 的結論是：一份夠用 SOP 的尺度，是一位未看過完整歷史的人，仍可依它安全開始、交出 draft、並知道何時停。

直接用這個填寫骨架：

```text
Purpose：今次要交甚麼，幫誰作甚麼決定？
Trigger：甚麼條件齊，才可以開始？
Input／steps：可用哪些材料，依甚麼順序完成？
Acceptance：甚麼欄位、格式、review 才算可交？
Exception／refresh：遇到甚麼停止，誰更新這份 SOP？
```

先把每行填成一句。不要急著追求漂亮格式；能讓人不再猜，是第一輪唯一需要的品質。

## Acceptance 點樣寫先令 AI 同人都知道何時收貨？用可見條件取代「做好」

「整理好交出去」「寫得專業些」「完成後通知我」都不是 acceptance。它們要求執行者猜你的標準：有沒有來源才算好？要幾個重點？哪些未知不能寫？誰最後說可以用？AI 很容易把一段流暢文字當完成，人又只好憑感覺打回。

acceptance 把真正會導致重做的條件寫成可見檢查。它不必量化一切，也不能取代專業 review；但它要讓 reviewer 能明確說「這一格還未過」，讓下一輪知道應修 SOP、補 input 還是處理例外。

Jimmy 的結論是：沒有 acceptance 的 SOP 只是動作紀錄；有 acceptance，才會變成能讓人和 AI 一起收貨的工作標準。

例如一份 internal briefing 可這樣收貨：

1. 只引用指定公開或已批准材料；
2. 有三個重點、來源欄和待確認項；
3. 沒有把未知或推測寫成事實；
4. 格式符合本輪 template；
5. owner review 後才可 closed，不直接外發。

這五條令「不對」可以被定位。下一次 AI 漏了未知，不需重新解釋整篇文案；只要指出 acceptance 第三條未過。

## 有例外時要怎樣做？Stop line 令 SOP 不會把不確定自動化

不少人不想寫 SOP，因為真實工作總有例外。這個擔心沒有錯；錯的是把例外當成完全不能整理工作的理由。事實上，SOP 最需要寫清的正是「哪些地方不能靠流程硬跑」，否則同事或 AI 為了完成任務，會自行補上本來應由人決定的答案。

stop line 將不確定變成一條正常工作路徑：資料不足、資料矛盾、範圍改變、權限不清時，不是繼續生成，而是標 `blocked`、列問題、交給正確 owner。這令例外不再等於失敗，而是 workflow 的安全訊號。

Jimmy 的結論是：SOP 的成熟不在於它沒有例外，而在於遇到例外時，下一位知道自己不應猜甚麼、應找誰。

| 情況 | SOP 應寫的 stop line |
|---|---|
| source 不清 | 「標待確認，交 source owner；不可寫成事實」 |
| 範圍突變 | 「停在 draft，重開 brief 後才繼續」 |
| output 涉及外發 | 「owner approval 前不可發送」 |
| 規則與現況不符 | 「標 SOP needs refresh，由 named owner 更新」 |

有了這一格，AI 可以協助標出問題，但不會被默認可以替你處理高影響決定。

## 寫完怎樣知道它真係成立？做一次「只准睇 SOP」的試跑

一份剛寫好的 SOP 很容易看起來清楚，因為作者仍記得所有背景。真正測試不是你重讀後覺得合理，而是另一位未參與歷史的人或新 AI session，只靠 SOP 能否說出任務、input、output、owner 和 stop line。若他一定要讀很多舊 chat 才能開始，SOP 還只是筆記。

試跑不需要選高風險工作。用同一種公開或 synthetic 材料跑一小段，讓執行者起 draft；reviewer 按 acceptance 收貨。卡住的位置就是最有價值的 feedback，應補進正確格，而不是把所有背景加進去。

Jimmy 的結論是：一份 SOP 經歷過一次「照住做」才開始成立；未試過的只是一份有用的草稿。

試跑按這五步：

1. 只提供 SOP 和本輪批准 input；
2. 請 worker 覆述自己的 task、owner 和 stop line；
3. 讓他完成一段可回退的 draft；
4. 由 owner 逐項看 acceptance；
5. 將第一個卡點寫回 SOP 或 exception，而不是先加 automation。

成功不代表永遠不用改；它只證明這一版能讓下一位在已知條件下安全開始。

## 用公開 briefing 跑一次：第一份 SOP 怎樣由「我識做」變成「下一位可試跑」

以下是 synthetic 練習。假設你每周把指定公開材料整理成 internal briefing。它有相近 trigger、固定格式和一位 reviewer，適合用作第一份 SOP；不涉及客戶資料、私有對話或直接外發。

先填五格，再讓新 session 只按 SOP 起第一版。這個練習不要求 AI 做完整流程；它只測試 input、acceptance 和 stop line 有沒有足夠清楚讓 AI／同事少猜一次。

| SOP 格 | 本輪例子 |
|---|---|
| Purpose | 一頁 internal briefing，供 owner review |
| Trigger | 本周指定公開材料已選定 |
| Input／steps | 指定 URL → 整理三重點 → 標兩項未知 |
| Acceptance | 來源、格式、未知完整；owner review |
| Exception／refresh | 來源矛盾即 `blocked`；格式改變時 owner 更新 |

Jimmy 的結論是：這次跑完最重要的成果不是一份漂亮 briefing，而是你知道哪一條標準已離開腦袋、哪一條仍需要補清楚。

當同類 run 再出現，再按 evidence 更新 SOP；不要把這個低風險成功包裝成任何自動化或商業成效承諾。

## 今日開始寫第一份 SOP：只完成五行，然後安排一次低風險試跑

不要等有完美時間或完美工具。選一件本周已出現、做過約三次、下一輪可由人手收回的小工作，花十五分鐘填五格。完成後最重要不是再修字，而是安排一位未看過所有背景的人或新 AI session 依它試一次。

若試跑卡住，這正是成果：你找到了原本靠自己記住的條件。只修最早一格，下一次再跑；這種小步反覆比一次寫成十頁文件更會累積真正可交接標準。

Jimmy 的結論是：第一份 SOP 的目標不是完美，而是令未來的你、同事或 AI 第一次不用由零重新猜。

今天請做：

1. 選一件第三次出現的低風險 routine；
2. 填 purpose、trigger、input／steps、acceptance、exception／refresh；
3. 指一位 review owner；
4. 用公開或 synthetic input 只跑一小段；
5. 將最早卡點補進 SOP，保留下一輪 evidence。

要理解 SOP 為何是工作標準而非流程百科，可讀 [SOP 唔止係步驟](../chapters/3-1-sop-trust.md)。若你仍在判斷何時才應把方法固定，可讀 [做過一次就急住寫 SOP？第三次先把做法固定，通常更穩](../chapters/3-7-third-time-minimum-sop.md)。
