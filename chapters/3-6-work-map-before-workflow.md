# 明明每星期都做，點解仍然交唔到畀人或 AI？先畫 work map，後講 workflow

有些工作你自己每星期都做到：整理資料、起 briefing、跟進一份內容、覆核一輪 output。可是只要換一個人、開一個新 chat，或者想交一小段給 AI，整件事就像要由頭講起。大家知道最終大概要交甚麼，卻不知道甚麼時候開始、可用甚麼材料，以及中途有問題應由誰決定。

於是很多人急著寫長 SOP、收集 prompt，甚至直接買 automation。這些做法未必錯，但如果工作本身還未被攤開，步驟只會把原本藏在某個人腦裡的判斷遮得更深；AI 亦只好把沒有說出的條件，補成它最常見的答案。

Jimmy 的判斷是：先把一件重複工作畫成五格 work map，才知道應否寫 workflow、加 prompt，還是根本不應交出去。這不是一幅漂亮流程圖，而是一張讓人看清「此刻卡在哪裡、下一位可以安全做甚麼」的工作地圖。

| 五格 | 它先解開的問題 | 這一格寫清後留下甚麼 |
|---|---|---|
| Trigger | 甚麼事真正令工作開始？ | 一句可辨認的開始條件 |
| Input | 今次可以讀甚麼、不可以猜甚麼？ | 最小材料清單 |
| Owner | 誰準備、誰收貨、誰處理例外？ | 角色與停線 |
| State | 工作做到哪裡，還欠甚麼？ | 可交接的目前狀態 |
| Output | 最後交甚麼才算完成？ | 可 review 的完成定義 |

## 重複工作何時才算真正開始？先寫 Trigger，唔好寫「有人需要時」

最常見的假開始條件是「客人問到就做」、「有空就整理」或「有人叫就處理」。熟手的人聽得明，因為他記得上一次怎樣做；新同事和 AI 卻不知道現在是材料未齊、只是有人提出想法，還是已經可以正式起稿。

Trigger 的作用不是催大家開工，而是把「可以開始」同「仍然要等」分開。若開始條件本身含糊，後面再精密的 prompt 都只會產生很快、但未必應該開始的 output。

Jimmy 的結論是：一條可交接工作，第一句應該是可被任何人確認的事件，而不是某個人的感覺。

你可以先用以下問題把它寫實：

1. 甚麼資料、批准或時間點一出現，這件事才開始？
2. 若只得一半材料，工作是 `blocked`、等待，還是只可做準備？
3. 誰有權說「今次不用做」或「先不要開始」？

例如，不寫「每周整理資料」，而寫「本周已選定的公開材料已齊，並已指定 briefing 的對象和截止時間」。這句 trigger 留下來後，下一位不用翻舊訊息猜今天是否真的要做。

## AI 可以讀乜、又唔應該自己補乜？Input 要少而準，不是愈多愈好

很多工作一交給 AI 就變差，不一定是模型能力不足，而是 input 混了三種東西：真正需要的材料、背景噪音，以及根本未確認的假設。為求「畀多啲 context」，人很容易整個資料夾丟進去；結果不是更準，而是 AI 把過期版本、私人資料或互相矛盾的說法混在一起。

Input 不是一份檔案目錄，而是今次工作被批准可以看的最小材料集。它也要標明甚麼缺了就不能猜、甚麼只可當背景、甚麼不可以給 AI 處理。這一步同時保護工作質量和資料邊界。

Jimmy 的結論是：好 context 不是「全部畀晒」，而是「足夠完成今次 output，並且人人知道不足的地方要停」。

一張小 input 清單可先分成三欄：

| 類別 | 例子 | AI 可以怎樣用 |
|---|---|---|
| 必要材料 | 指定公開 URL、已批准 brief、固定格式 | 用來整理、比較、起 draft |
| 參考材料 | 一份已核對的好範例 | 只作格式和力度參考 |
| 缺口／禁區 | 未確認數字、私人名單、尚未批准內容 | 標記待確認；不可自行補寫或上傳 |

當這格寫得清楚，AI 交出錯誤內容時就不再只是「它亂答」：你可以回頭看，是材料未齊、材料衝突，還是它越過了禁區。這才是一個可修正的工作問題。

## 邊個可以決定、邊個只可以準備？Owner 同 exception 要一齊寫

「AI 幫手做」很容易把責任變得模糊。有人以為自己只是按掣，另一位以為 output 已經有人看過；一旦資料矛盾、要求忽然改變，大家都不知道應繼續生成、回去問人，還是停止。這不是工具失控，而是 owner 從未被寫進工作裡。

即使是同一個人同時 prepare 和 review，也要把兩個帽子分開寫。因為當你日後交接、找同事覆核或加入 AI，真正需要保留的不是某人的名字，而是每個決定由哪個角色負責。

Jimmy 的結論是：AI 可以協助準備，不能取代一條工作裡誰有權驗收、誰有權停線的安排。

先為每次運行寫四句已經足夠：

- **Prepare：** 誰把 input 變成第一稿或資料包？
- **Review：** 誰判斷 output 是否可進下一步？
- **Decide：** 誰能接受例外、改範圍或要求重做？
- **Stop：** 碰到來源不清、材料矛盾、範圍改變時，先交回哪個 owner？

這四句不是公司層級表。它留下的是一條安全停線：一旦遇到例外，AI 和人都不需要硬撐著把不確定的事做完。

## 唔好靠翻舊 chat 猜進度：State 要令下一位看得見目前位置

一段 chat 可能有很多好答案，但它不是可靠的工作狀態。隔兩日回來，你很難看出哪份資料已確認、哪一版 draft 等 review、哪個問題仍未解；交接給同事時，更容易因為不同人只看了不同訊息而重做。

State 不是叫你立即建複雜 dashboard 或接 CRM。開始時，一組人人看得懂的文字狀態已經足夠。重點是每個狀態有清楚的進入條件和下一個 owner，而不是為了看起來專業而開更多欄位。

Jimmy 的結論是：如果下一位要讀完整個聊天紀錄才知道能否接手，這件工作還未真正可運行。

一個低風險的最小狀態可以是：

```text
new → context-ready → draft-ready → owner-review → closed
                    ↘ blocked（材料不足／範圍改變／需要決定）
```

每次只問兩件事：現在在哪一格？要去下一格，還缺甚麼？留下這兩個答案，比保存一百句「我跟緊」更能讓工作累積。

## 做到邊度先算完成？Output 要寫成可以收貨的東西

「幫我做好」、「出一份稿」和「整理一下」都不是完成定義。它們只講了動作，沒有講會交甚麼、誰會看、哪些條件不符合就要退回。AI 很容易因此交出一段看似完整的文字，但人仍要重新猜它是否可用。

Output 需要把成品、位置、驗收者和下一步連在一起。這不表示每件事都要有正式簽核；只要令一個人可以合理地說「這版可以 review」「這版要退回」或「這件已 closed」，已經比模糊的「做好」強很多。

Jimmy 的結論是：真正的 output 不是 AI 產生了甚麼，而是人能否用一個明確標準收貨或退貨。

例如，將「整理 briefing」改寫成：

> 交一份放在指定位置、只含已批准公開資料的 internal briefing draft；由內容 owner review。若缺來源、結論無法追溯或格式不符，就退回 `draft-ready`，不可直接對外發送。

收貨時，至少逐項看三件事：

- **成品是否對？** 它是不是原來約定的一頁 draft／表格／briefing，而不是另一種看似更完整的內容？
- **驗收是否有人？** 指定的 review owner 有沒有看過，並知道自己要判斷甚麼？
- **退回是否有路？** 缺來源、未確認資料或格式不符時，是否能回到正確 state，而不是叫 AI 繼續猜？

這段完成定義留下的不是一份漂亮文案，而是一個可驗收的交接點。之後你才有條件比較 cycle time、重做次數，或者判斷哪一格值得優化。

## 用一個安全例子跑一次：公開材料 briefing 的五格 work map

以下不是客戶流程，也不是自動化模板；它是一個用公開材料練習的 synthetic 小工作。目的不是追求一次做得很大，而是讓你看見五格如何把「想請 AI 幫手」變成可 review 的運行。

假設小組每周要把指定公開材料整理成 internal briefing。先只做一輪，不對外發送、不接私人資料，也不讓 AI 自己決定結論。

| 格 | 最小寫法 |
|---|---|
| Trigger | 本周公開材料已選定，briefing 對象和截止時間已確認 |
| Input | 指定 URL、已批准格式、一份已核對的好範例；未確認說法一律標記 |
| Owner | 一人 prepare、一人 review；範圍衝突時交回內容 owner |
| State | `new → context-ready → draft-ready → owner-review → closed / blocked` |
| Output | 一份可 review briefing，不直接對外發送 |

Jimmy 的結論是：第一輪的價值不在於產生一份可展示的自動化，而在於找出這件工作真正需要哪一格才能安全運行。

跑完後不要只問「AI 寫得好不好」。回頭看：哪一格最常令工作停住？如果總在 `context-ready` 卡住，先修 input；如果常在 review 打回，先收窄 output 或補驗收標準。這才是用 work map 找真正摩擦。

## 今日先留低一張五格 work map，而不是先寫一大段 prompt

第一張 map 最適合揀你本周至少做過兩次、就算失敗也能人手收回的工作。不要拿最急、最敏感或最複雜的一件來證明 AI；那會令你分不清是工作本身太難，還是五格尚未寫清。

花十分鐘寫下 trigger、input、owner、state、output，再補一句 exception。你不必立即加工具或自動化；先讓另一個人讀完後，能說出現在可不可以開始、缺甚麼、誰收貨。

Jimmy 的結論是：工作未被畫出來之前，AI 只能猜；五格一旦清楚，你才知道應該改善、交接、試行，還是停止。

1. 寫一件重複小工作的一句 trigger。
2. 列出今次真正要用的 input，以及一項不能交給 AI 的資料。
3. 寫明 prepare、review 和 exception owner。
4. 用五個以內的 state 標出目前位置。
5. 把 output 寫成「誰可以 review 的甚麼東西」，而不是「做好」。

留低這張 map，它就是你之後才可以討論 prompt、SOP、Skill 或 automation 的第一個 artifact。若你想把五格變成更完整的重複工作標準，下一步可看 [SOP 唔止係步驟：點樣將一件重複工作寫成可交接的標準](3-1-sop-trust.md)。
