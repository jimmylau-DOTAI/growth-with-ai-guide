# 內容 Agent 點樣先唔會變成自動出廢文：先把證據整理好，再開始寫

很多團隊一聽到內容 Agent，第一個畫面就是「每天自動出幾篇 post」。但真正最花時間的，通常不是把句子寫出來，而是分清楚：近期究竟重複聽到甚麼問題、哪個觀察有根據、哪些說法仍未證實、甚麼角度值得由自己說。

如果這些判斷仍然散在聊天紀錄、收藏、截圖和各人腦內，AI 寫得再快，都只是在把混亂變成較流暢的文字。讀者看似得到一篇內容，團隊卻沒有留下可以重用的問題、主張、證據或改進方向；下一次還是由零開始猜。

Jimmy 的做法不是把內容創作交給一個「自動發文機」，而是先把內容 Agent 放在較可靠的位置：它幫人收集已批准的材料、整理重複問題、標記未知，再把值得寫的東西交回 owner 判斷。當 evidence、角度和 review 有了位置，AI 才真正幫你加快版本化，而不是取代你的聲音。

| 內容 Agent 的一格 | 它要解的工作問題 | 完成後應留下甚麼 |
| --- | --- | --- |
| Evidence bundle | 資料散亂，分不出觀察與猜測 | 可回看的來源、重複問題、已知與未知 |
| Angle decision | 題目很多，不知哪一個值得講 | 有 owner 選過的內容角度與受眾問題 |
| Content brief | AI 每次都重新猜語氣和重點 | 一張可交接的主張、例子、限制和 CTA |
| Review + feedback | 發了就消失，不知下次怎樣更好 | 可追溯的修改原因與下一輪規則 |

## 內容 Agent 自動出 post，為甚麼通常解不到內容方向混亂？

內容 Agent 可以很快把一條 prompt 變成十個標題、五個平台版本，甚至幫你排好發文時間。這些能力適合處理已經想清楚的表達工作；它們不能自行判斷一個題目是否真的來自受眾問題，更不能替你承擔一句未驗證主張帶來的信任成本。

最常見的失敗不是 AI 文筆差，而是輸入只得「幫我寫一篇關於 AI Agent 的貼文」。這種指令沒有指定讀者正在卡在哪裡、文章要處理哪個誤解、哪些例子可以用、哪些說法不能講。AI 於是用最常見的網上語言補空白，產量增加了，辨識度卻慢慢消失。

**Jimmy 的結論：** 內容 Agent 的第一份工作，不是代替你發聲，而是幫你把「值得講甚麼、憑甚麼講、暫時不能講甚麼」整理成一個人可以驗收的決定。

先把工作切開，才知道哪一步可以交給 AI：

| 工作 | 應由誰主導 | 先要有甚麼 |
| --- | --- | --- |
| 找出重複問題與已批准材料 | Agent 協助整理 | 指定資料夾、公開文章、已批准筆記 |
| 決定是否值得講、用甚麼立場講 | 人／內容 owner | 受眾問題、業務方向、風險判斷 |
| 起草標題、段落、渠道版本 | AI 協助 | 已批准的 content brief |
| 對外發佈與改動主張 | 人 review | 最終稿、事實核對、發佈權限 |

當內容方向不再只是 prompt 裏的一句題目，AI 才能做它擅長的整理與變體。否則它只是把一條仍未想清楚的指令，放大成更多不需要的內容。

## Content evidence bundle 應該收甚麼，才不會把收藏夾當成知識庫？

evidence 不是把所有連結、截圖和別人的金句搬進一個文件夾。真正有用的 bundle，要令下一個人看得出每一項材料到底是公開事實、自己觀察、客戶常問問題，還是尚未驗證的假設；否則內容 Agent 仍然會把所有東西當成同等可靠。

對剛開始的人來說，材料愈多不代表愈有方向。十篇都在講「AI 很重要」的文章，未必比一段清楚記下的受眾提問有用。重點是保留足夠 context，讓人知道為何這個問題值得講，而不是為每條來源做一份長摘要。

**Jimmy 的結論：** Evidence bundle 的價值，是把來源變成可判斷的訊號；它不是內容倉庫，也不是把外部作者的說法改寫成自己的文章。

一個公開安全、足夠開始的 bundle 可以只有四格：

| 欄位 | 要記下甚麼 | 例子（synthetic） |
| --- | --- | --- |
| 來源與日期 | 已公開、已批准、可回看的材料 | 公開 webinar Q&A、公司 blog、已發出的社交內容 |
| 重複問題 | 人真正用甚麼語言問 | 「我懂得用 ChatGPT，下一步怎樣把工作交出去？」 |
| 可支持的觀察 | 材料真的能支持甚麼 | 初學者常把聊天結果誤當作可交接 workflow |
| 未知／待確認 | 目前不能斷言甚麼 | 未有數據證明某個 workflow 會節省多少時間 |

這四格令內容 Agent 有一個可追溯的起點。它可以把重複問題分群、抽出可能角度，但不能把未確認的行銷說法升級成事實，更不能把私人會議、CRM 或客戶資料混進公開內容。

## 內容角度怎樣由受眾問題決定，而不是由熱門工具名決定？

熱門工具名很容易帶來短期注意力，但它不一定告訴你讀者想完成甚麼。例如「Codex 教學」可以指第一次開啟工具、把一段程式交出去、驗收 AI 改動，或建立一條有 review 的工作流程。若只跟著工具名寫，內容會混在一起，讀者看完仍不知道自己下一步應做哪一件事。

較穩的角度是從讀者的工作摩擦開始：他在哪個環節重複返工、要交給誰驗收、最擔心 AI 猜錯甚麼。工具可以成為示範，但它不應取代問題本身。工具更新時，你的判斷仍然留得住。

**Jimmy 的結論：** 一個內容角度要先回答「誰在甚麼情境卡住」，才輪到「用哪個 AI 工具示範」。讀者跟的是問題線，不是工具追新線。

可以用這個小型角度選擇表，讓 owner 一次只選一個可講的問題：

1. 寫下受眾用過的原句，而不是抽象標籤。
2. 標記這條問題屬於入門、熟用、交接、建立，還是價值判斷。
3. 寫一句你可以負責的 Jimmy 判斷；沒有把握就留作待確認。
4. 選一個公開或 synthetic 例子，令讀者看見工作怎樣發生。
5. 決定讀者看完應留下的第一個 artifact、規則或下一步，而不是只留下「覺得有道理」。

當角度能夠被這樣說清楚，內容 Agent 才不會把一個寬闊題目拆成十篇彼此重複的貼文。想先把問題與定位記成長期記憶，可接著讀 [內容方向是受眾問題的長期記憶](4-33-content-direction-is-problem-memory.md)。

## AI content brief 要寫到甚麼程度，AI 才不會每次重新猜你的意思？

很多人以為 brief 就是一個題目加字數，例如「寫一篇 800 字關於 AI workflow 的文章」。這會令 AI 每次自己補讀者、主張、例子與限制；即使偶然寫得好，下一篇也很難複製，因為真正有效的判斷仍然沒有被留下。

一張 brief 不需要很長，但要足夠令另一個人或另一個 AI 看懂這次究竟在解哪個工作問題。它是交接用的工作合約，不是文案規格表；有它之後，標題、SEO 段落、社交貼文和課程版本才可以同源而不同形。

**Jimmy 的結論：** Brief 的完成線不是「AI 已開始寫」，而是 owner 即使關掉原來對話，仍能判斷這個內容有沒有答中問題、越過哪些界線、下一步要交給誰。

一份可用的 content brief 可包括：

| Brief 部分 | 要答的問題 |
| --- | --- |
| 讀者情境 | 誰在甚麼工作環節卡住？ |
| 核心問題 | 他真正想解決甚麼，而不是表面搜尋甚麼工具？ |
| Jimmy 判斷 | 你主張的轉念或做法是甚麼？ |
| Evidence／例子 | 有甚麼公開或 synthetic 例子支持解釋？ |
| 邊界 | 哪些成效、事實、客戶細節不能聲稱？ |
| 完成後留下甚麼 | 讀者第一個可以做的安全動作、模板或下一篇？ |

這份 brief 可讓 Agent 幫你出渠道版本，但「Jimmy 判斷」和「邊界」仍要由有責任的人確認。它們正是內容不會變成 generic AI copy 的原因。

## AI 寫內容後，review 怎樣分清楚語氣修改與事實風險？

AI 內容的 review 很容易變成「感覺順不順、像不像我」。語氣當然重要，但若 review 只看字句，真正危險的問題會被漏掉：一個數字有沒有來源、一個案例是否可公開、一個建議是否將適用條件講清楚。

把 review 切成不同層，內容 owner 才不用一次過用直覺處理所有事情。第一層核對內容有沒有答中選定問題；第二層核對主張、例子和外部資訊是否可用；最後才處理語氣、標題和平台長度。這樣 AI 也能收到較可學習的 feedback，而不只是「再像我一點」。

**Jimmy 的結論：** Review 不是內容 Agent 的最後一個阻礙；它是讓內容系統累積判斷、避免把未證實內容推到公開面的品質閘。

用一張簡單的 review receipt，便能把 feedback 留下來：

| Review 層 | 要檢查甚麼 | 遇到問題時怎樣處理 |
| --- | --- | --- |
| 問題對準 | 是否真的回應選定讀者情境？ | 改 brief 或改角度，不是只改標題 |
| 證據與邊界 | 主張、例子、數字是否可公開及可支持？ | 刪除、改為條件句，或留待確認 |
| 聲音與結構 | 是否像 Jimmy 的實戰判斷，而非工具清單？ | 加入具體工作摩擦與清楚結論 |
| 渠道適配 | 長文、社交、課程版本有否保留同一主張？ | 由同一 brief 重新生成版本 |

若一段內容無法通過證據與邊界檢查，最好的選擇可以是不發。這不是 Agent 失敗，而是系統成功把不應公開的說法停在 review 前。

## 發出後的 content feedback 怎樣變成下一輪可用的規則？

內容一發出去，很多團隊只看 likes 或 views，然後下一輪再追另一個熱門題目。這些訊號可以參考，但它們未必告訴你內容有沒有解決工作問題。較有價值的 feedback，通常包括讀者在哪一段停下來追問、銷售或教學時是否有人引用、哪個誤解重複出現。

同樣地，不要因為一篇內容表現好，就把所有細節硬寫成 Agent 規則。先分清楚這是一次偶然的渠道結果，還是跨幾次內容都重複出現的讀者需要；前者只留記錄，後者才值得更新選題、brief 模板或內容角度。

**Jimmy 的結論：** Content feedback 的用途不是追逐每個數字，而是讓下一次更少猜：哪些問題持續存在、哪些解釋真正幫到人、哪些內容風險要在前面擋住。

每次發出後，只需留下四條短記錄：

1. 讀者最常追問的下一個問題是甚麼？
2. 哪一句解釋最常被誤會或需要補充？
3. 哪個案例、主張或字眼被 review 擋下？原因是甚麼？
4. 下次要更新 evidence、brief、語氣規則，還是根本換一個問題？

這些記錄不必包含個人資料或私訊全文；用匿名、概括、公開安全的方式已足夠。累積幾輪後，內容 Agent 才有可以重用的規則，而不是只記得上一條 prompt。

## 想試第一個內容 Agent，最安全的工作單位是甚麼？

第一個內容 Agent 不需要有發布權限，也不需要接所有檔案。最小可驗證版本，是讓它根據一個已批准的公開資料夾或一組公開文章，整理一張 evidence bundle；人再選一個角度、填一張 brief、批准一個初稿。這已經足夠測試它有沒有讀錯、漏掉邊界或產生重複內容。

先用乾淨且可回退的材料，代表你可以看清楚每個環節發生了甚麼。若一開始就把它接上私人 vault、客戶 CRM、草稿庫或自動發佈帳戶，一旦它把 context 混錯、把未批准資料帶進文案，便很難判斷錯誤來自哪一步，也很難安全收回。

**Jimmy 的結論：** 第一個內容 Agent 的成功，不是「它今天自動發了幾篇」，而是「它交出一張可驗收的 evidence bundle，並讓人清楚選到下一個值得寫的問題」。

可以跟著這個 safe first move 試跑：

1. 只選 3–5 篇已公開、已批准的材料，並標明 owner。
2. 要 Agent 輸出來源、重複問題、可支持觀察和待確認空格；不要求它直接發文。
3. 由內容 owner 選一個受眾問題，寫成一張 brief。
4. 用 brief 生成一個長文段落或社交版本，保留人工 review。
5. 留下一張 review receipt，記下哪個規則下次仍然適用。

暫時不要把它接到私有客戶資料、未公開策略、付款／CRM 資料或發文權限；也不要因為一輪試跑順利，就宣稱已建立 autonomous content system。當你先把這個小單位跑穩，才有根據考慮更多渠道、更多版本或更多自動化。
