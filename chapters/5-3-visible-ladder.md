# AI 成長路線要看得見，但唔係升級遊戲

「我算不算識 AI？」「我現在第幾級？」這些問題很自然，卻很容易把人推向買更多工具、追更複雜的 Agent，甚至把一時不懂當成能力不足。其實多數人不是卡在身份，而是卡在一件真工作裡某一個很具體的環節。

有人還未能把任務交清楚；有人每次開新 chat 都要重講背景；有人已有做法卻交不到下一手；有人開始跑流程但不知道 AI 何時會越界；也有人已能做出小成果，卻不知道怎樣帶團隊安全地走過同一段路。這些都是工作狀態，不是人的固定標籤。

Jimmy 的看法是：五個 AI stage 的用途是幫人找最早、最安全的下一步，不是替人考牌。每一段都對應一種常見工作摩擦和一份可留下的 artifact；只要由眼前真工作開始，讀者就不用猜自己「應該是誰」，而能知道下一件事要補甚麼。

| 你在工作上見到的症狀 | 最接近的入口 | 先補甚麼 | 留下甚麼 |
|---|---|---|---|
| AI 只會答問題，交不到成果 | AI User | 小任務、材料、完成線、review | 可 review 的 first draft |

## AI stage 點解不應變成身份：同一個人可以在不同工作處於不同位置

你可能很擅長用 AI 整理公開文章，卻仍然不應把敏感資料交給 AI；你也可能在自己工作裡已經有一條穩定 workflow，但第一次帶團隊試行時仍要重新學 governance 和 change management。這不是矛盾，而是不同工作有不同 input、風險、owner 和驗收要求。

若把 stage 當成身份，人很容易為了「升級」跳過必要步驟，例如未有可交接流程就想做 Agent team，或未跑過安全 pilot 就想宣布公司轉型。相反，將 stage 當成工作地圖，會讓人把注意力放回現在最早斷掉的一格。

**Jimmy 的結論：** stage 描述的是一類工作當下的能力與風險，不是職級、薪酬或永久身份。你不用問「我是哪一級」，先問「這件工作在哪一格最早卡住」。

| 這個想法 | 容易帶來甚麼問題 | 改成甚麼問題 |
|---|---|---|
| 「我一定要升到 Builder」 | 跳過 context、handoff 和 review | 這條工作是否已重複且可驗收？ |
| 「我只係 AI User」 | 低估已有的小成果 | 我能否交出一份可 review draft？ |
| 「他很高級，所以全都可做」 | 忽略資料與權限邊界 | 這個 workflow 允許他做哪一手？ |
| 「公司在 Level 3」 | 將印象當成事實 | 哪條真 workflow 有 evidence？ |

一個好的地圖應讓人對自己少些焦慮、對下一步多些清楚。若它只令你想追一個標籤，就用錯了。

## 五個 AI stage 怎樣對應真工作：由回答問題走到帶人創造價值

AI User 的重點是把一次回答變成一件可 review 的小工作；AI Super User 是令下一次不用從零猜，靠 context、標準與 feedback 改善輸出；AI Operator 再把已驗證的做法留成下一手能接的 current state 和 handoff。這三段先讓個人和小團隊的工作變得可見、可重複。

AI Builder 則在流程穩定後，為一手工作加 input boundary、quality gate、exception 和 stop line，令 AI 不只是聊天而是能在範圍內完成一段可靠工作。AI Value Creator 最後關心的是怎樣帶人選 pilot、設 owner、治理風險、量度 outcome，並決定一條 workflow 是否值得擴大。

**Jimmy 的結論：** 五段不是工具難度表，而是工作可靠度的路線：由交一件工作、留下 context、完成 handoff、建立安全 loop，到帶團隊看見價值。

| Stage | 讀者最常卡住的事 | 一個可驗收方向 |
|---|---|---|
| AI User | AI 回答了，但不能直接用 | 一份有材料和完成線的 draft |
| AI Super User | 每次都要重新講背景 | context pack 加 feedback |
| AI Operator | 做法只在某一個人腦中 | current state 和 handoff |
| AI Builder | 想交工作又怕出錯 | quality gate 與 stop receipt |
| AI Value Creator | 想帶人但不知從哪開始 | 小 pilot 加 owner 和 outcome |

這條地圖不要求每個人走到最後。對很多工作，穩定做到 AI Super User 或 AI Operator 已很有價值；是否往下走，取決於工作是否真的需要和是否有安全條件。

## 最早斷點怎樣決定下一步：先修最便宜、最安全的一格

當一條工作出問題，最常見反應是換工具、加 prompt 或加 Agent；但若 input、完成線和 review 仍然模糊，這些做法只是把混亂放大。下一步應先找最早斷點：AI User 還未交清任務，就不要談 automation；AI Super User 未有可信 context，就不要怪模型每次答不同；AI Operator 未有 handoff，就不要讓 Builder 直接接系統。

找最早斷點的好處是成本低、風險小。你不需要一次修整整個流程，只要補最前面那一格並重跑一次。若 output 因此已更可 review，才走到下一格；若仍然不行，就再看是 input、rule、owner 還是技術可行性出了問題。

**Jimmy 的結論：** 不要跳去最潮的工具，先修最早、最便宜、最安全的斷點。第一個可靠 artifact 比一個很大的 AI 計劃更能告訴你真正下一步。

| 最早看到的斷點 | 先不要做甚麼 | 先補的最小 artifact |
|---|---|---|
| 任務連輸出也未清 | 自動化或 multi-agent | 小 work brief |
| 每次資料／格式不同 | 再換模型 | context／review checklist |
| 下一手接不到 | 建 dashboard | current-state note |
| AI 會越界或亂猜 | 開更多權限 | stop line 和 quality gate |
| 團隊不願持續使用 | 再加長 workshop | workflow diagnosis |

若你補了一格但問題沒有改變，這也是 evidence。它告訴你不是這一層，而要回看更早的 input 或轉查技術是否可行。

## 相鄰一步點樣避免 AI 成長焦慮：由一件小工作逐格向前

下一步不應由 chat 直接跳去「AI team」。例如 AI User 可以先把一篇公開文章變成有來源、未知和 owner review 的 brief；AI Super User 再把格式、例子和 feedback 留成 context；AI Operator 才把重複步驟寫成可交接流程；AI Builder 才為其中一手加 gate；AI Value Creator 才帶其他人用這條已跑過的 workflow 做 pilot。

每一段都留下一個 artifact，讓下一段有東西可以接。這條路雖然看起來慢，實際上更快，因為你不必每次由零重設規則，也不會在未有 evidence 前承擔高風險。它更適合真實工作，而不是只適合一場 demo。

**Jimmy 的結論：** 相鄰一步不是限制野心，而是讓每一次成長都有可回看證據。你不需要先成為 Builder，才可以做出第一份對工作有用的 AI 結果。

| 現在入口 | 相鄰、可 review 的下一步 | 暫時不要跳去 |
|---|---|---|
| AI User | 公開材料的 internal brief | 直接連外部系統 |
| AI Super User | context pack 加 review rule | 把整個 vault 當 memory |
| AI Operator | handoff note 加 current state | 先畫大 Agent org chart |
| AI Builder | 有 stop line 的 bounded loop | 自動對外發送 |
| AI Value Creator | 一條有 owner 的小 pilot | 宣布公司已轉型 |

只要每一步都留下 artifact，你便能誠實地說明自己或團隊不是「升了級」，而是某一條工作變得更可靠了。

## 一個公開安全例子：每週 research draft 如何由 AI Super User 走到 AI Builder

假設有人每星期要整理公開資料，交出 internal research draft，但每次都要重新改格式。不要先說他「未到 Builder」；先看真工作。它已有 output，卻未把格式、來源標記和未知項寫成 context，因此 AI 每次都要重新猜，reviewer 也重複修相同問題。

第一個相鄰步是 AI Super User：做一張 context／review checklist，列出可用公開 source、每個 claim 要有 link、推論標待驗證、資料不足便停。重跑幾次後，若 input、check 和 owner 已穩定，而且每週真的重複，才進 AI Operator 寫 handoff；之後才考慮 AI Builder 把這段變成有 gate 的 Skill 或 loop。

**Jimmy 的結論：** 地圖在這裡不會催人「升級」，而是幫人避免過早 build。先證明一條小工作有穩定 context 和 review，再決定是否值得做成 AI system。

| 觀察到的事 | 真正 stage 需要 | 下一個 artifact |
|---|---|---|
| 格式每次不同 | AI Super User 的 context | checklist 與例子 |
| 只有某人知道怎做 | AI Operator 的 handoff | current-state note |
| AI 會猜或越界 | AI Builder 的 gate | stop／review receipt |
| 想叫其他人都用 | AI Value Creator 的 pilot | owner 與 outcome card |

這個例子只用公開資料和內部草稿。它不要求 AI 讀取私人／客戶資料、對外發送或直接改 production，也不代表所有工作都要走到 Builder。

## 成長地圖常見誤會：工具數量、Agent 數量與 stage 並無直接關係

識得愈多工具，不等於某一條工作有清楚 input、artifact 和 review；開更多 Agent 也不代表 workflow 更可靠。這些都是能力資源，是否有用仍取決於它們是否放進正確問題、正確 context 和正確的責任線。

另一個誤會是每個人只有一個 stage。其實你可能在寫作工作已經是 AI Operator，在資料敏感或高後果工作仍只做 AI User；這反而代表你有正確的判斷。stage 不應被用來評價人，而是幫你選擇每一類工作可安全走到哪裏。

**Jimmy 的結論：** AI 成長不在於收藏工具或追身份，而在於下一件真工作可以少些猜、多些交接、多些驗收。地圖越能指出具體 artifact，越值得用。

| 誤會 | 為何會出事 | 較好的判斷方式 |
|---|---|---|
| 工具越多 stage 越高 | 沒有說明工作有沒有改變 | 看 artifact 和 outcome |
| Agent 越多越成熟 | hand-off 與 owner 未必清楚 | 看 workflow boundary |
| 人人要去 Value Creator | 有些工作不需要帶團隊 | 看職責與風險 |
| 一個人只有一個 stage | 不同工作風險不同 | 按 workflow 判斷 |
| Stage 是考試級別 | 讓人跳過必要步驟 | 只走相鄰一步 |

一張好地圖應讓你更容易開始，而不是令你覺得自己永遠落後。

## 今日怎樣用五段地圖：用上星期一件真工作選下一篇，而不是替自己貼標籤

找你上星期最常返工的一件低風險工作，寫三句：想交甚麼成果、現在最早卡住哪一格、下一個可 review 的小 artifact。不要先替自己選一個永久身份；答案落在哪一列，就由那一段開始讀和試。

若你不肯定斷點在哪，先選最小、最安全的一步：把工作寫成 brief、補 context 或做一張 review checklist。跑過一次後再看 evidence。這比直接買新工具或要求全組升級更能讓你知道，這條工作是否真的準備好進下一個 stage。

**Jimmy 的結論：** AI 成長路線的價值，是令下一步看得見。只要你今天留下一份可 review artifact，你已經不是停在概念，而是在為下一個可靠工作建立證據。

| 三句診斷 | 你要回答甚麼 | 例子 |
|---|---|---|
| 想交甚麼成果 | 最終可 review artifact | 一頁 research brief |
| 最早卡住哪一格 | input、context、handoff、gate 或 adoption | 每次重新講來源與格式 |
| 下一步留甚麼 | 最小可驗收證據 | context checklist |
| 誰 review | 人類 owner 是誰 | content owner |
| 何時停 | 不確定時怎處理 | 缺 evidence 即標 unknown |

先在公開、可回看的 draft 工作跑這一步。未有 artifact、owner 和 review 前，不要把 stage 地圖當成部署計劃，也不要把 AI 接到外部發送、客戶資料或 production。接著可看 [如何診斷一條 AI adoption bottleneck](5-13-diagnose-adoption-bottleneck.md)。

> AI 成長唔係你識幾多工具，而係你下一件真工作可以少啲猜、多啲交接、多啲驗收。
