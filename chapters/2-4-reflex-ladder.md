# 用 Codex／Claude Code 做事，點樣唔好一路燒 Context？先養成五個工作反射

第一次用 Codex、Claude Code 或其他可讀 project 的 AI 工作台，很多人一打開便叫它開始：丟一句需求、等它跑、見到 output 再算。任務一大、材料一多、方向一開始理解錯，後面做得越多，重做就越難受。

問題不是你背得不夠 command，也不是一定要懂 coding。真正欠的是「何時應開始、何時應補 context、何時應停、何時應重開、何時應收貨」的工作反射；工具介面會變，這些判斷不會因為換工具而消失。

Jimmy 的判斷是：AI 工作台入門不是指令清單，而是一條可管理的工作回路。第一輪只用低風險、可回退任務，練好開始、核對、停止與 review，才有條件讓 AI 接更長的工作。

| 任務在甚麼狀態 | 你要有的反射 | 留下甚麼 |
|---|---|---|
| 剛開始 | 先講清目標、範圍、材料和完成線 | 一張 run card 開場 |
| 做到一半 | 核對它理解的方向和目前 artifact | 一次中途 check |
| 方向不對或範圍失控 | 及早停、縮小或改 context | 一條 stop decision |
| 歷史太雜或任務換了 | 用乾淨 brief 重開，而非帶著噪音硬做 | 新一輪任務入口 |
| 準備交件 | 對照驗收條件，人手 review | 可採用／退回的結論 |

## AI 工作台點解會一路做、一邊越錯？問題常在開場未交代清楚

AI 工作台可以讀較多資料、處理多個檔案或跑多個步驟，這正是它有用的地方；但也代表一個早期假設若理解錯，錯誤可以被帶到後面的每一步。當你只說「幫我整好這個 project」，AI 不知道哪些檔案是根據、哪些不可改、誰會用成果、何時需要停。

一開始講清楚並不是為了令 AI 寫得更慢，而是讓你有一個可以中途核對的基準。沒有開場目標和完成線，做到一半發現「唔係我想要」時，你甚至不知道要改任務、改材料還是只改一段 output。

**Jimmy 的結論：** AI 一路做錯，往往不是後面突然變壞；而是前面沒有把工作範圍和成功條件交清楚。

| 只說一句需求 | 開場有 run card |
|---|---|
| 「幫我整理這些檔案」 | 說明只處理哪個資料夾、交回哪張表、哪些原檔不可改 |
| AI 自行猜下一步 | 每一步能回到指定目標與材料 |
| 中途發現錯，難判斷何時偏離 | 可核對目標、範圍、artifact 和停止線 |
| 做完才問是否可用 | 開始前已知道怎樣收貨 |

在 Codex 或任何工作台裡，第一句最值得寫的不是 command，而是任務的 scope。這會保護你免於讓工具在錯方向上做得太有效率。

## AI 工作台開場要交代乜？先寫一張最小 run card

run card 不需要像大型 project plan。它只是把本輪工作固定在一張小卡：要解甚麼摩擦、可看甚麼、可改甚麼、交回甚麼、由誰 review、遇到甚麼要停。你和 AI 都能在工作中途回到這張卡核對。

最重要的是把「可改甚麼」說清楚。若本輪只是起一份文件 draft，就不要讓 AI 同時重構整個資料夾或發佈內容；工作範圍越小，第一次越容易看見真正的問題在哪裏。

**Jimmy 的結論：** 好開場不是把所有背景塞進去，而是讓本輪任務有清楚 scope、artifact、review 和 stop line。

```text
本輪工作要解的摩擦：＿＿＿＿＿＿＿＿＿＿
只可看的材料／工作區：＿＿＿＿＿＿＿＿＿＿
可建立或修改的 artifact：＿＿＿＿＿＿＿＿＿＿
不可做的事：＿＿＿＿＿＿＿＿＿＿
完成後我怎樣 review：＿＿＿＿＿＿＿＿＿＿
遇到甚麼要停下來問人：＿＿＿＿＿＿＿＿＿＿
```

| run card 一格 | 一個安全例子 |
|---|---|
| 摩擦 | 三段公開資料一直要手動整理成會前 brief |
| 範圍 | 只讀指定三個文字檔；不讀其他資料夾 |
| Artifact | 新建 `briefing-draft.md`，用來源／重點／未知欄位 |
| 禁止 | 不覆蓋原檔、不搜尋未批准資料、不對外發送 |
| Review | 人核對來源、日期、未知和格式 |

這張卡讓你有一個穩定開場。若 AI 的理解和卡片不一致，應該先修正再繼續，不要等它做完整條錯路。

## AI 做到一半點樣 check？不要等 output 做完才發現方向歪了

在長一點的任務裡，最昂貴的做法是等所有步驟結束才第一次看結果。這不是因為每個動作都要盯緊，而是因為有些錯誤很早已經出現：它選錯了材料、誤解了輸出格式、把假設當事實，或把本來只需 draft 的工作擴大了。

中途 check 的目的不是打斷 AI，而是確認它仍然沿著 run card 行。選一個自然節點，例如讀完材料後、建立第一份 artifact 後、準備修改前，要求它讀回目前理解、列出已做與未知，再由人決定繼續、修正或停止。

**Jimmy 的結論：** 中途核對不是微管理；它是用最小成本發現方向是否仍對，避免把 review 全押在最後。

| Check 時機 | 應問甚麼 | 有問題時怎樣處理 |
|---|---|---|
| 讀完材料後 | 你理解的目標、可用 evidence、未知是甚麼？ | 修正材料／假設，未開始產出前先停 |
| 第一版 artifact 後 | 欄位是否齊、是否超出範圍？ | 改格式或縮回指定 scope |
| 要改檔前 | 將改哪些檔、預期影響是甚麼？ | 批准最小改動，或改為只提建議 |
| 收尾前 | 還有哪些未驗證、需要誰決定？ | 留待確認和 owner，不假裝完成 |

```text
請暫停在下一個 artifact 前。
讀回：你現時理解的目標、已用材料、已完成項目、未知與準備做的下一步。
不要擴大範圍，等我確認後再繼續。
```

這類 readback 在不同工具名稱下都可做。你要練的是「在可回退的節點檢查」，不是記一條特定指令。

## AI 方向明顯錯咗點算？早停、縮 scope、重寫 brief 三個選擇

看到 AI 方向不對時，很多人會想「等它做埋先，可能後面會好」。這種希望在簡單任務或許有用，但若它已用錯材料、誤解成果或越過權限，繼續做只會產出更多難以 review 的內容。

及早停止不代表剛才白做。它讓你知道 run card 哪一格不夠清楚，並保護原檔、時間和注意力。之後可按錯誤類型選擇縮 scope、補 evidence、改驗收或乾淨重開，而不是在錯方向上修修補補。

**Jimmy 的結論：** 早停不是浪費；在錯的假設還未影響更多 artifact 前叫停，是最便宜的修正。

| 你看到的訊號 | 最合適動作 | 下一步 |
|---|---|---|
| 它讀錯了本輪材料 | 停，補 context／evidence | 再從讀材料後的 check 開始 |
| 它理解錯成果格式 | 停，更新 brief 和範例 | 只重做 artifact，不重跑全部 |
| 任務本身太大 | 縮 scope | 抽一段可 review 的工序 |
| 對話累積太多互相矛盾內容 | 乾淨重開 | 帶著更新後 run card，不帶整段噪音 |
| 已碰到敏感／未批准範圍 | 立即停 | 找 owner，改用安全材料或不做 |

停止後留一句原因，例如「本輪 evidence 未足，不能做最終結論」。這會變成下一次 task brief 的邊界，而不是同一種錯誤再發生一次。

## AI 對話太長或任務已換，何時應該重開而不是硬接住做？

長對話有時很有用，因為它保留了任務的思考過程；但當背景已換、舊指示互相矛盾、或你要做的是另一個新成果，硬把所有歷史帶進下一輪會令工作焦點更模糊。這不是 AI 特有問題，人類接手一個沒有摘要的長 email chain 也會遇到同樣困難。

重開不是否定上一次工作。先把仍有效的目標、已確認 evidence、格式、feedback rules 和未解問題摘要成一張新的 run card，再用乾淨入口開始。這樣你保留價值，丟掉的是不再適用的聊天噪音。

**Jimmy 的結論：** 需要延續的是已確認的工作狀態，不是整段對話紀錄；任務一換，先重寫 brief 通常比硬接住更可靠。

| 繼續同一輪較好 | 重開一輪較好 |
|---|---|
| 目標、材料和 artifact 未變 | 已換讀者、成果或工作問題 |
| 只差一兩個澄清問題 | 舊指示開始互相衝突 |
| 你仍能清楚說出目前狀態 | 你要翻很久才知道上次做到哪裡 |
| 有明確下一個 review 點 | 需要重新界定範圍與完成線 |

```text
新一輪開始前摘要：
- 沿用的目標／artifact：＿＿＿＿
- 已確認的 evidence／規則：＿＿＿＿
- 今輪更新的材料或範圍：＿＿＿＿
- 已知未知／需要 owner 決定：＿＿＿＿
- review 與 stop line：＿＿＿＿
```

這個摘要讓 context 成為可管理的工作狀態，而不是越積越長、沒有人敢清理的對話記錄。

## AI 記憶、設定檔和 project note 有咩分別？不要把它們當成魔法

有些工具可以保存偏好、讀 project instruction，或讓你在工作區放一份規則檔。這些功能可以減少重複交代，但它們不會替你判斷規則是否仍有效、材料是否適合本輪，或是否應進行有風險的動作。

最穩陣的做法是把不變的工作習慣放在 work profile／project note，把本輪材料和任務放在 task brief／run card，把本次未知和收貨結果留在 receipt。三種資料各有工作位置，才不會令一份「記憶」混進過時指示和臨時細節。

**Jimmy 的結論：** AI 記憶不是讓你少思考；它是讓已確認、範圍清楚的規則不用每次重講。

| 放在哪裏 | 適合放甚麼 | 不應放甚麼 |
|---|---|---|
| Work profile／project note | 穩定角色、格式、判斷傾向 | 本輪暫時假設、敏感原始資料 |
| Task brief／run card | 今次目標、材料、artifact、stop line | 所有歷史項目和未整理舊 chat |
| Run receipt／review note | 做過甚麼、未知、review 結果 | 未驗證成果的宣稱 |
| 工具的記憶／設定 | 已確認、可重用、低風險規則 | 權限、credentials、一次性例外 |

當你每次都能說明規則為何在這個位置，你就能在工具換掉時把工作方法帶走，而不會被某個功能鎖住。

## AI 做完之後點樣 review，先算真正完成而不是只見到 output？

AI 工作台常會產出很多「看起來完成」的訊號：生成了文件、改了檔案、跑過一個步驟、寫了一段總結。這些只是活動紀錄；真正完成要看它有沒有交出 run card 原本要求的 artifact，有沒有超出範圍，未知是否仍被看見。

review 不一定要很技術化。對文件和知識工作，讀回成果、核對 evidence、檢查檔案位置、確認沒有不該發生的動作，已經是重要閘口。若工作涉及 code 或檔案改動，還要按該工作類型選擇相應測試或人工檢查。

**Jimmy 的結論：** 有 output 不等於完成；只有 artifact、範圍、未知和人手決定都回到 run card，才叫可靠收貨。

| Review 問題 | 你要找的證據 | 不應只看 |
|---|---|---|
| 交對成果嗎？ | 指定 draft、表格、檔案或清單真的存在 | AI 說「已完成」 |
| 根據對嗎？ | 每個重要主張可回到材料／evidence | 文字是否流暢 |
| 有越界嗎？ | 沒有改原檔、外發或讀未批准資料 | output 看上去是否漂亮 |
| 未知有保留嗎？ | 待確認項目與 owner 可見 | AI 是否看似很有信心 |
| 誰決定下一步？ | reviewer 的採用／退回／擴大決定 | 工具是否建議繼續 |

把 review 結果寫一兩句回 run receipt，下一次你便能知道這段工作是否值得重跑、要補哪條規則，還是本來不適合交給 AI。

## 五個 AI 工作反射怎樣在低風險任務裡練一次？

反射不是靠背出來，而是用一件小而真實的工作跑一次。選擇公開或 synthetic 材料，令 AI 整理一份 internal briefing；在開始、讀材料後、第一版 artifact 後和收尾各做一個簡單決定。錯誤仍留在可回退範圍，卻已能讓你感受到何時該停。

不用刻意讓 AI 做錯來「上課」。只要你在每一個節點問自己：它仍在處理我要的問題嗎？是否用了批准材料？我現在可以收貨嗎？這些問題重複出現，便慢慢變成工作反射。

**Jimmy 的結論：** 反射的目標不是更頻密地打斷 AI，而是在少數關鍵位置保持自己知道工作正在往哪裏走。

| 工作節點 | 你要做的反射 | 可留下的紀錄 |
|---|---|---|
| 開始 | 寫 run card | 目標、範圍、artifact、停位 |
| 讀材料後 | 要求 readback | 已用 evidence、未知、下一步 |
| 初稿後 | 核對格式與範圍 | 需要改的條件 |
| 方向錯時 | 停、縮 scope 或重開 | stop decision 和原因 |
| 收尾 | 人手 review | 採用／退回與下次規則 |

完成一次後，不要急住把五個反射變成自動化。先比較第二次是否少重講、少重改，再決定哪些部分足以寫成可重用 context 或 AI Operator 的 SOP。

## 練好 AI 工作反射後，怎樣由個人使用走向可交接 workflow？

當你能穩定留下 run card、readback、stop decision 和 review 结果，代表工作不再只存在一次對話裡。此時可以把反覆出現的條件整理成 task pack、context rule 或 project note，讓下一次工作更快起步。

若同一段工作持續重複，而且輸入、輸出和例外都越來越清楚，才值得走向 AI Operator 的 SOP 與狀態管理。反過來說，若每次仍在探索內容或決定，留在可 review 的小任務更合適，不要過早把它叫成自動化。

**Jimmy 的結論：** AI 工作台的成熟，不是讓它做得愈久；而是你愈能在對的位置開工、核對、停下和收貨。

| 你下一個卡位 | 接著讀甚麼 | 會留下甚麼 |
|---|---|---|
| 開場仍然沒有材料和完成線 | [五格組一個 AI task pack](../walkthroughs/build-an-ai-task-pack.md) | 一份可 review task pack |
| 每次 feedback 沒有留下 | [把 feedback 變成規則](../walkthroughs/turn-feedback-into-a-rule.md) | 一張 reference card |
| 想把重複任務正式交接 | [AI Operator stage](../03-ai-operator.md) | SOP、可讀狀態和例外處理 |
| 任務牽涉敏感資料或外部動作 | [哪些資料暫時不要上傳 AI](../chapters/1-5-materials-not-to-upload-to-ai.md) | material check 與人手 boundary |

可返回 [AI Super User stage](../02-ai-super-user.md) 看其他入口。例子只用公開／synthetic 情境，不代表任何客戶、公司或 DotAI 已取得的成果。
