# 做過一次就急住寫 SOP？第三次先把做法固定，通常更穩

一件工作第一次做得順，很容易令人立即把步驟寫成 SOP、交給同事或交給 AI。可是那次成功可能只是材料剛好齊、例外剛好沒有出現，或者全部仍靠你在腦裡補位。太早固定做法，往往只是把偶然成功變成下一次的僵化規則。

另一個極端是永遠不寫。結果同類工作做了十次，仍然要靠記憶、舊 chat 和某個熟手的人救場。真正要判斷的不是「有沒有做過」，而是 trigger、input、步驟、驗收和例外是否已經在不同 run 裡重複出現，並且有人能說出為何這樣做。

Jimmy 的第三次法則是一個實戰 heuristic：第一次探索、第二次比較、第三次才寫 minimum SOP。它不是硬性規定每件事都只能第三次才寫，而是提醒你先在低風險、可回退的工作上看清 pattern，才把真正可交接的部分固定下來。

| 第幾次 run | 今次真正要做甚麼 | 留下甚麼 |
|---|---|---|
| 第一次 | 把實際做法和摩擦記下 | 第一張工作觀察 |
| 第二次 | 比較哪些條件反覆出現 | 可疑／可靠 pattern |
| 第三次 | 固定最少規則和例外 | 可交接 minimum SOP |
| 之後 | 按 evidence 更新或退休規則 | 更成熟的 routine |

## 第一次做得順，點解仍然不應立刻把它變成 SOP？一次成功未必是 pattern

第一次順利完成，通常會讓人忘記背後有多少隱性條件：剛好資料完整、剛好由最熟悉的人做、剛好沒有遇到例外。若你只把表面步驟記下來，下一位照做時一遇到材料缺失、範圍改變或同一個人不在，就會發現 SOP 根本沒有告訴他應怎樣判斷。

這不是反對記錄第一次。第一次最值得記的不是「固定流程」，而是實際發生了甚麼：哪一步要人決定、哪一份資料真正有用、哪一個地方你靠經驗補過去。這些摩擦會成為第二次比較時的材料。

Jimmy 的結論是：第一次成功值得留下觀察，但還未足以證明它是一條可以交給下一位照跑的規則。

第一次 run 先記四件事：

1. 甚麼 trigger 令工作真正開始；
2. 實際用了哪些 input，哪些原以為需要但最後沒用；
3. 哪一個決定仍靠人臨時判斷；
4. output 最後由誰怎樣收貨，哪裡幾乎要退回。

這張觀察不是 SOP，而是讓你下一次能找出「上次剛好順」和「真正需要保留」之間差別的證據。

## 第二次應該比較甚麼？找出重複條件，不是硬把兩次做成一樣

第二次 run 常常和第一次不完全一樣：資料不同、時間更趕、問題多了一個、甚至 owner 換了。這正是它有價值的原因。若第二次一有不同就照抄第一次，SOP 只會變成「只適用於第一次那個情境」的故事。

比較的目的不是消除所有變化，而是分清哪些條件必須固定、哪些應保留彈性、哪些一出現就應該停止。你要尋找的是在兩次都成立的工作骨架，而不是把每個偶然細節寫成強制步驟。

Jimmy 的結論是：第二次不是驗收第一次做得對不對，而是用差異找出一條工作真正的邊界。

用這張比較表找 pattern：

| 位置 | 第一次 | 第二次 | 初步判斷 |
|---|---|---|---|
| Trigger | 材料齊才開始 | 材料未齊但有人催 | 需要寫清「未齊即 blocked」 |
| Input | 三份公開資料 | 兩份公開、一份未知 | 未知不可由 AI 補寫 |
| Review | 同一人即時看 | owner 隔日才看 | 要寫出 state 與 review owner |
| Output | 一頁 briefing | 同樣一頁但格式不同 | 格式要列為 acceptance |

當你看到一項差異會改變結果，它就值得在第三次的 minimum SOP 裡出現；若只是個人偏好，先不要假裝成所有人都必須遵守的規則。

## 第三次寫 minimum SOP 時，甚麼必須固定、甚麼仍要留白？只寫能交接的最少規則

有了兩次觀察後，很多人又會走到另一個極端：想把所有細節、每個例子和每個例外都寫進 SOP。結果文件很長，下一位仍然找不到開始條件與完成線；AI 則被大量歷史細節淹沒，反而不知道哪條是硬規則。

minimum SOP 的目的不是記錄一切，而是讓一個未做過的人在已知範圍內能安全開始、交出可 review 的成果，並在遇到不屬於範圍的情況時知道停在哪裡。它必須短到有人願意在第三次真的使用。

Jimmy 的結論是：一份夠用 SOP 不是步驟最多，而是下一位看完後能知道何時開始、怎樣收貨、何時不可繼續。

一份 minimum SOP 最少寫五格：

| 格 | 要固定甚麼 |
|---|---|
| Trigger | 甚麼情況才可開始，甚麼未齊就不能開始 |
| Input | 可用材料、不可猜的空白、資料範圍 |
| Steps | 真正重複、可以交接的動作 |
| Acceptance | output、reviewer 與可收貨條件 |
| Exception／stop | 資料矛盾、範圍改變、權限不足時交回誰 |

所有仍要靠專業判斷的部分可以留在 exception，而不是被假裝成可自動執行的規則。這會令 SOP 更誠實，也更容易日後擴充。

## SOP 寫好後，AI 可以做哪一段？先讓它依規則起草，不讓它自己定例外

一份 minimum SOP 出現後，很自然會想交給 AI。「有了步驟，AI 應該可以做晒」其實是危險跳步。SOP 可能令 AI 更清楚 input、格式和 output，但它不會自動給 AI authority 去處理資料矛盾、對外承諾或未寫清的例外。

比較安全的做法，是先讓 AI 只做其中一段可驗收工作：整理已批准材料、按固定結構起 internal draft、核對欄位是否漏掉。每一輪仍由人 review，並把 AI 找不到答案的情況留回 exception。這樣你才能知道 SOP 哪一部分真的可以被支援。

Jimmy 的結論是：SOP 令 AI 有一致的工作起點，不等於 AI 已經獲得自行完成整條工作的權限。

先用以下分工測試一輪：

| 工作位置 | AI 可以做 | 人必須保留 |
|---|---|---|
| Input 整理 | 列出已給材料與未知 | 決定材料是否可靠／可用 |
| Steps | 按格式起第一稿 | 判斷是否適合此情況 |
| Acceptance check | 對照 checklist 找漏項 | 最終 review 與收貨 |
| Exception | 標 `blocked`、提出問題 | 決定怎樣處理例外 |

這個測試若跑得穩，才有條件把某個局部做成可重用 template 或 Skill；若跑不穩，先回去修 SOP，而不是加一個更長 prompt。

## 用公開材料 briefing 跑三次：何時可以由觀察變成 minimum SOP？

以下是 synthetic 例子。假設你三次整理指定的公開材料，交出一份 internal briefing。第一次，材料剛好完整；第二次，有一條來源未確認；第三次，reviewer 提醒格式不一致。三次都不是大規模 project，但已足夠讓你看見哪些地方不是偶然。

這個例子不包括客戶資料、不會讓 AI 對外發布，也不會聲稱任何效率結果。它只示範一條低風險工作如何由「我自己做得到」走到「下一位可安全接手」。

| Run | 看到甚麼 | SOP 應留下甚麼 |
|---|---|---|
| 第一次 | 材料齊時可按格式完成 | 初步 steps 與 output |
| 第二次 | 一個來源未確認，AI 有補寫風險 | `unknown → blocked` 的停線 |
| 第三次 | reviewer 每次都要補同一格式欄位 | 固定 acceptance checklist |

Jimmy 的結論是：第三次的價值不是終於有一份漂亮 SOP，而是你終於知道哪幾條規則值得交給下一位，而哪些仍然必須留給 owner 判斷。

若第三次仍然每次都遇到完全不同的條件，這不是失敗；它只是證明工作尚在探索階段，應繼續收集 evidence，而不是強迫自己「看起來有系統」。

## 今日怎樣開始？先找一件做過三次、可回退的小工作

不要挑最複雜、最敏感或最急的一件工作來寫第一份 SOP。最適合的是你最近做過約三次、結果可以由人手收回、而且每次都有相近 trigger 的小 routine。它足夠真實，又不會因為一個例外就把你推去高風險決定。

把三次 run 簡單排在一起，再只寫五格 minimum SOP。若你寫不出 trigger、acceptance 或 exception，答案不是「加多些步驟」；而是回去多跑一次、問 owner 或先縮小範圍。

Jimmy 的結論是：第一次不要急住 SOP，第二次看 pattern，第三次才寫最少規則；先把摩擦看見，才不會把錯誤複製。

第一輪可照這五步：

1. 選一件已做過三次的低風險工作；
2. 列出三次各自的 trigger、input、review 和例外；
3. 圈出真正重複、會改變結果的條件；
4. 寫五格 minimum SOP，並明確標出 stop line；
5. 下一次只讓人或 AI 按其中一段跑，再留下是否仍成立的 evidence。

要先看清一件重複工作到底有哪些格，可讀 [明明每星期都做，點解仍然交唔到畀人或 AI？](3-6-work-map-before-workflow.md)。當 SOP 已經令下一位可以接手，下一步可寫一張 [新 AI 一入 project 就要翻晒 chat？你需要的是 current-state note](3-12-current-state-not-chat-history.md)，保留目前仍然有效的決定。
