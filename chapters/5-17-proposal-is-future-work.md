# AI proposal 不只是工具清單：讓對方看見未來的工作怎樣改變

很多 AI proposal 看起來很完整：有平台名稱、功能列表、timeline、價錢和 package。可是客戶或團隊讀完後，真正仍會問同一批問題：明天哪個人要改做法？AI 處理哪一手？資料不完整時怎樣辦？output 錯了誰負責？一份只答到「買甚麼」的 proposal，往往答不到「大家之後怎樣工作」。

這個落差會令 AI 專案一開始就被當成採購或 demo，而不是工作改善。對方看見了一個系統，卻看不見哪條 workflow 真的會變短、哪個 owner 要參與、甚麼結果才叫值得擴大。於是期待被工具名稱拉得很大，實際落地又回到模糊、等待和反覆修改。

Jimmy 的看法是：一份可信的 AI proposal 不先承諾一個很厲害的 Agent 或全面轉型；它先與對方共同定義一條值得驗證的工作改變。對方應能看見現在怎樣做、第一輪怎樣安全改、誰保留判斷、如何檢查結果，以及何時決定要不要繼續。

AI proposal · AI adoption proposal · workflow pilot · AI transformation · scope · governance · outcome · human review

| Proposal 的一格 | 要消除哪個不確定 | 最後留下甚麼 |
|---|---|---|
| 現在 workflow | 現在誰在哪一步重做／等待？ | current-state map |
| 第一個工作單位 | 哪一段可先在有限風險下改？ | bounded pilot scope |
| AI 與人的分工 | AI 做甚麼，人保留甚麼？ | role／approval rule |
| Artifact 與驗收 | 對方怎樣看見交付可用？ | draft、card、receipt、acceptance |
| Evidence | 哪個變化值得觀察？ | baseline／outcome measure |
| 邊界與下一步 | 不做甚麼、何時停、之後誰決定？ | control card 與 decision gate |

## AI proposal 為何不能由工具名稱開始：客戶要買的是工作改變，不是功能列表

當 proposal 一開始寫「部署 Agent」「接入某平台」「建立 knowledge base」，讀者最容易把它理解成採購清單。他仍不知道這些東西要解哪個人正在經歷的摩擦：是資料要搬來搬去、內部 briefing 每次重做、內容起草等太久，還是決策總是缺少可核對資料？沒有這一層，工具愈多，範圍反而愈模糊。

從工作張力開始，並不是要假裝你已知道客戶全部情況。相反，它容許你清楚列出已知與待 discovery 的部分：哪條流程最常被提起、哪個角色最受影響、若不處理是慢、錯、風險還是機會流失。這使 proposal 變成一個可共同校正的工作假設，而不是一份套用在任何公司的銷售模板。

**Jimmy 的結論：** Proposal 的第一頁應讓對方認出自己的工作，不是讓他先背工具名。先講工作摩擦，工具才有正確的位置。

| 工具式開場 | 讀者聽到甚麼 | 工作式開場 |
|---|---|---|
| 「我們會部署 AI Agent」 | 不知 Agent 解甚麼問題 | 「先處理活動後 briefing 的反覆整理」 |
| 「接入 knowledge base」 | 不知資料由誰維護 | 「定 approved source 與 unknown rule」 |
| 「自動化 follow-up」 | 擔心會亂發／越權 | 「先起 internal draft，由 owner review」 |
| 「提高全公司效率」 | 期待很大但不可驗收 | 「比較一條 workflow 的 rework 與 cycle time」 |
| 「建 AI OS」 | 範圍和責任不明 | 「先完成一張 AI work card」 |

若你現在未能用兩三句講出工作張力，proposal 最好的下一步不是加功能，而是先做 discovery，把流程、owner 和現在最常重做的一手找出來。

## AI pilot 怎樣定第一個工作單位：先選可管理的 routine，不承諾全面自動化

「幫你做 AI transformation」聽起來有野心，但它把不同流程、資料、角色、風險和預期全放進同一個承諾裡。第一輪一旦有資料缺失、owner 未定或結果不如預期，大家便很難知道問題來自工具、流程還是 scope 太大。AI adoption 因而常被誤判為失敗，其實只是從一開始就沒有可驗收的單位。

第一個 AI pilot 應縮到一條 routine：已批准材料進來、AI 做一手整理或 draft、指定 owner review，最後留一份可檢查 artifact。這不代表你只做小事，而是先找出這條 workflow 能否可靠地改善。當它跑過幾次，你才有 evidence 去談下一個 integration、更多角色或更大的範圍。

**Jimmy 的結論：** 第一輪賣的不是「全自動化」，而是「把一條真 workflow 跑成可檢查的 pilot」。範圍愈清楚，越容易令客戶安全地開始。

| 太大承諾 | 改成第一個工作單位 | 可驗收交付 |
|---|---|---|
| 全公司 AI transformation | 診斷一條重複 workflow | workflow map 與 priority decision |
| 自動化所有 follow-up | 已批准資料變 internal follow-up draft | draft 加 review checklist |
| AI research team | 公開來源整理成 decision brief | source boundary／brief／receipt |
| 建企業 Agent | 一條低風險 handoff 的 work card | scope、owner、stop line |
| 提升團隊效率 | 比較一次 routine 的 rework | outcome note |

第一個 pilot 不應接到敏感資料、公開設定或 production action。未有 owner、approval 和可回看的 evidence 前，把 AI 保持在整理、草稿和提示層會更安全。

## AI 與人怎樣分工才寫得清楚：不是取代人，而是讓責任可被看見

一份 proposal 若只寫「AI 協助團隊」，實際等於沒有交代任何責任。讀者會自然擔心：它可以讀哪些資料？會不會自行發出？錯了誰跟進？人是否只剩下最後 cleanup？這些問題不應等到 project 開始後才解決，因為它們直接影響對方是否願意讓流程進入真工作。

清楚分工的方式是把 AI 的 input、動作和 output 寫實，也把人保留的優先次序、敏感判斷、approval 和例外處理寫實。你不是承諾 AI 完全不會錯，而是展示錯誤不會無聲流到下一步。這也是讓使用者知道自己不是被替代，而是由重複搬運回到更重要判斷的位置。

**Jimmy 的結論：** AI 分工不是一格「AI 做、 人 review」就完成。要寫清 AI 讀甚麼、交甚麼、不做甚麼，以及哪個人在哪個關口負責收貨。

| 工作格 | AI 可以負責 | 人必須保留 |
|---|---|---|
| Input | 讀 approved、最小必要材料 | 決定資料可否使用 |
| Draft | 整理、分類、起固定格式草稿 | 判斷意思、優先次序與語氣 |
| Unknown | 標記缺漏與矛盾 | 補資料或決定暫停 |
| Approval | 提示待 review 項目 | 決定接受、退回、外發 |
| Exception | 提交 escalation note | 處理客戶、風險、敏感決定 |

如果某一個 AI 動作無法對應一個 owner 或 stop line，先不要把它寫成「自動化」。它可能仍有研究價值，但尚未準備好進入對方的日常工作。

## AI proposal 的交付怎樣令人收貨：用 artifact、review 和 evidence 代替漂亮承諾

客戶不應只收到一份概念圖或功能示意。他需要知道第一輪會看到甚麼：是一張現況 workflow map、一份有來源邊界的 internal draft、一個 review checklist，還是三次 run 的 outcome receipt？當交付被寫成可打開、可核對的 artifact，雙方才有共同語言去判斷今次是否完成。

evidence 也不應只在最後補一個「預計 ROI」。早期最誠實的做法是定一兩個可觀察變化，例如資料齊備後到可 review 的時間、漏欄數、退回原因、使用者是否能接手。這些未必立即證明商業回報，卻能幫你分辨這條 workflow 是真的更可用，還是只是多了一個工具。

**Jimmy 的結論：** 可收貨的 proposal 要承諾 artifact 和看法，而不是虛構結果。先讓對方看見哪份東西會出現、誰會 review、怎樣決定下一步。

| Proposal 寫甚麼 | 可驗收版本 | 不要偷步寫成 |
|---|---|---|
| 現況理解 | current-state workflow map | 「我們已完全了解」 |
| 第一輪交付 | approved-input internal draft | 「已自動完成整條流程」 |
| Quality | review checklist 加退回分類 | 「保證準確」 |
| Outcome | cycle time／rework 的 run receipt | 「必定節省 X 小時」 |
| 下一步 | retain、revise、stop 或 limited scale | 「自然可以擴到全公司」 |

當 proposal 把交付和 evidence 寫得具體，對方就不用靠想像去相信。這亦讓服務方在第一輪保留誠實調整的空間，而不是被一句過大承諾鎖死。

## AI proposal 的風險與停止線點樣寫：邊界不是附錄，是合作的信任基礎

有些 proposal 把 governance、資料範圍和停止線放在最後一頁，彷彿它們只是法律或技術附錄。但對真正使用的人來說，正是這些內容決定他是否敢開始：客戶資料可否進去？不確定內容如何處理？AI 可以否外發？誰有權叫停？這些答案愈早清楚，pilot 才愈不會在第一個例外出現時失控。

停止線也不是表示你預計失敗。它代表你知道甚麼情況下暫停比硬推更負責，例如 input 未經批准、review owner 缺席、品質問題重複出現、風險超出原來 scope。這會讓 client 和 delivery team 知道有一個安全的回轉點，而不是一開始就被迫承擔全面轉型的壓力。

**Jimmy 的結論：** 邊界、approval 和 stop line 是 proposal 的核心 deliverable。它們讓雙方知道 pilot 怎樣保持在可管理範圍，不是令計劃變慢的障礙。

| 風險格 | Proposal 要寫清 | 安全的預設 |
|---|---|---|
| Data | 哪些材料可進、哪些不可進 | 最小必要、已批准 input |
| Action | AI 是否可外發、寫入或改設定 | draft-only，human approval |
| Quality | 遇到 unknown 或不一致怎樣做 | 標記、退回、不可猜 |
| Ownership | 誰 review、誰可叫停 | named owner 與 escalation |
| Scale | 何時才可擴大 | evidence、repeatability、rollback |

若客戶希望第一天就給 AI 更高權限，而你仍未有 input boundary、owner 或 review record，最專業的做法是縮小 pilot，而不是把高風險 access 包裝成進度。

## 一個公開安全例子：活動 follow-up briefing 怎樣寫成第一輪 AI proposal

假設一個小團隊每次活動後，都要整理已批准活動材料、常見問題和報名狀態，供內部準備 follow-up briefing。壞 proposal 會說：「導入 CRM agent，自動化所有 follow-up。」它跳過了資料權限、內容 owner、外發 approval 和未驗證成效，讓大家以為 AI 一開始便可以替代整個流程。

較好的 proposal 會說：第一輪只處理已批准活動資料，輸出 internal briefing draft；內容 owner 對照資料 review 後才決定下一步。客戶聯絡資料、payment、未公開 offer 不進第一輪，AI 不自行發送或寫入 production。三次 run 後看資料齊備到可 review 的時間、漏欄和 rework，再由雙方決定 retain、revise、stop 或小範圍擴大。

**Jimmy 的結論：** 這個 proposal 沒有承諾魔法，但讓所有人知道未來工作會怎樣改。對方買到的是一段可驗收的 pilot，而不是一個不可控制的 Agent 承諾。

| Proposal 格 | 例子中的內容 | 第一輪不做甚麼 |
|---|---|---|
| 工作摩擦 | 活動後資料整理反覆重做 | 不假裝已知所有流程 |
| Scope | approved data → internal draft | 不自動外發／寫 production |
| Owner | content owner review | 不將 approval 交給模型 |
| Artifact | briefing draft 加 checklist | 不只交聊天截圖 |
| Evidence | review time、漏欄、rework | 不預先承諾 ROI |
| Decision | 三次 run 後共同取捨 | 不一開始擴到所有 team |

這是 synthetic 教學情境，不代表任何特定公司、CRM 或客戶已有相同成果。它要展示的是 proposal 如何把工具討論拉回真工作、真邊界和真 decision。

## 下一份 AI proposal 怎樣開始：先寫一個可共同驗證的未來工作句子

下次寫 proposal，先不要由功能或價錢頁開始。用一句未來工作句子把第一個範圍講清：我們先一起找出哪一條重複工作，讓它由現在的哪種摩擦，變成哪份可 review 的 artifact，並在誰的 approval 下觀察哪個變化。這一句未必漂亮，但它逼你回答最重要的問題。

若你暫時答不到 input、owner、review 或 evidence，也不需要假裝準備好。把它寫成 discovery question，或把 proposal 縮回一個 workflow diagnosis。真正的 AI Value Creator，不是把未知藏在很大的 package 裡，而是讓對方知道哪一部分已看清、哪一部分要共同驗證。

**Jimmy 的結論：** 好 proposal 是一份可共同走入的未來工作設計：有目前摩擦、有第一個小改變、有人的責任、有可收貨交付，也有繼續或停止的依據。

| 第一頁先寫的句子 | 你要補的格 | 寫不出時代表甚麼 |
|---|---|---|
| 「先處理＿＿＿工作」 | 真實 workflow pain | 要先做 discovery |
| 「由＿＿＿變成＿＿＿」 | bounded artifact | scope 太大或交付不清 |
| 「AI 只處理＿＿＿」 | AI boundary | 仍在賣工具概念 |
| 「由＿＿＿review」 | owner／approval | 責任未落地 |
| 「觀察＿＿＿再決定」 | evidence／decision gate | 未有 pilot 的完成線 |

完成這個骨架後，可讀 [設計一個真的學到東西的 adoption pilot](5-6-design-adoption-pilot.md)，把 proposal 轉成第一輪驗證；如果你要把已跑過的 workflow 變成可管理服務，下一步讀 [由 AI Builder 走到服務](5-14-builder-to-service.md)。

> AI proposal 的核心不是承諾一個很厲害的系統，而是共同定義一條值得先驗證的工作改變。
