# AI 未開始做已經估錯？Build 前先寫 assumption ledger，唔好等改完才發現前提錯了

你叫 AI「幫我整好個 dashboard」、「照上次格式改」、「做得簡單啲」。它很快交來一個版本，看起來也像樣；但你一打開，才發現它選錯資料、假設了不存在的功能，或者順手改了原本不想碰的地方。最後不是 AI 做得慢，而是大家花更多時間拆掉一個建基於錯前提的完整答案。

這類返工通常不是 prompt 寫得不夠長，而是 brief 裏面有太多無聲假設：「同平時一樣」指哪個版本？哪個數字才是 source of truth？「完成」是有一個畫面，還是資料可保存、有人驗收、不能影響現有流程？如果人自己也未答清楚，AI 很容易把最像合理的做法當成 requirement。

Jimmy 的判斷是：Build 前不是急著問 AI「點做」，而是先把已知事實、暫時假設、仍要問的問題和不可碰範圍攤開。assumption ledger 不是一份很長的 spec；它是一張讓計劃可以被推翻、讓 AI 不會偷偷補完關鍵前提的工作文件。

| Ledger 的一格 | 它要分清甚麼 | AI 可以怎樣處理 |
| --- | --- | --- |
| 已知事實 | 已確認的 source、現況、限制 | 可直接引用，並列進現況摘要 |
| 暫時假設 | 為了提出 plan 而作的可改前提 | 標明影響，不能偽裝成 requirement |
| 仍要問 | Owner 回答前不能自行決定的問題 | 交回問題與選項，停在 plan gate |
| 不可碰 | 本輪不讀、不改、不發送、不部署的範圍 | 不越界；需要碰到便要求重新批准 |
| 驗收影響 | 假設錯了會影響哪個結果 | 讓 owner 優先確認高風險前提 |

## AI Build 為甚麼常常一開始就走錯，不是做到一半才出事？

AI 很擅長根據不完整描述推測一個可行方案。這在 brainstorm 或草稿階段很有幫助，但在改檔案、接資料、設計流程或交付產品時，未被說明的前提會影響後面每一個決定。它不是故意忽略 requirement，而是在用最常見的模式補足你沒有寫出來的部分。

例如「幫我做一個本週工作 dashboard」可能隱含至少五個未決定的問題：資料來自哪裡、只顯示還是可編輯、重開後要不要保留、誰看到、會不會影響真實工作系統。若 AI 直接選了一套資料 schema、加了登入或接外部資料，表面上很主動，實際上已越過了你未批准的決定。

**Jimmy 的結論：** AI build 最常見的錯不是技術做錯，而是把未確認前提做得太完整。先承認不知道甚麼，反而能令第一個版本更快到達正確方向。

開始前可先問這五句：

| 先問甚麼 | 它防止甚麼 |
| --- | --- |
| 現在可確認的 source／state 是甚麼？ | AI 由錯資料或想像中的系統開始 |
| 哪些做法只是暫時假設？ | 假設被寫成永久 requirement |
| 哪些問題 owner 未答？ | AI 代替人做 business decision |
| 本輪哪些東西不可碰？ | 範圍、資料或外部 action 偷偷擴大 |
| 假設猜錯會影響哪個驗收？ | 小問題被誤當成大風險，或反過來 |

當這些問題有位置，AI 可以提出 plan，但不再需要假裝自己已經知道所有答案。

## 已知事實、暫時假設和未確認問題，怎樣先分清楚？

很多 brief 的問題，是一句話同時包含事實、偏好和猜測。例如「用現有資料做一個簡單 dashboard」：也許現有資料真的存在，也許「簡單」只是感覺，也許資料是否可讀、是否完整、是否能保存都還未確認。若不拆開，AI 很容易把所有字看成已批准的規格。

assumption ledger 的作用，就是把每句含糊說法拆成不同責任。已知事實可以用來設計；假設只可以暫時支撐 plan；問題要交回 owner；不可碰範圍則是 AI 的硬邊界。這比單純在 prompt 裏加一句「小心」更可檢查、更容易交接。

**Jimmy 的結論：** 一個好 plan 的可信度，不在於它講得多自信，而在於它有沒有清楚標出哪一格可直接做、哪一格仍可能被推翻。

用一個 public-safe synthetic 例子看：

| 類別 | 「本週工作頁」的示例 | 正確下一步 |
| --- | --- | --- |
| 已知 | 只讀指定 sample JSON；頁面已有三張工作卡 | AI 可先讀檔、列出現況 |
| 假設 | 「下一步」先用純文字顯示，不做提醒 | 放進 plan，請 owner 確認或修正 |
| 仍要問 | 是否需要篩選狀態？重開後是否保存？ | 不猜；列在 plan gate |
| 不可碰 | 不改 schema、不加登入、不接 CRM、不部署 | 若需要碰到，停止並重談 scope |
| 驗收影響 | 保存功能會改變資料與回退要求 | 先確認，再決定是否納入第一版 |

這樣 AI 最終交出的不只是一個畫面，而是現況、ledger、小改動 plan、驗收條件與明確未做項目。

## Assumption ledger 同 scope 有甚麼分別，為甚麼兩樣都需要？

Scope 回答的是「今次做甚麼、不做甚麼」；它幫你把工作砍成一個合理大小。assumption ledger 更早一步，回答的是「我們憑甚麼相信這個 scope 可行？哪些前提仍未確認？」兩者看似接近，但不能互相取代。

假設你已決定本輪 scope 是「在本機 sample 頁加一個 next-step 欄位」。這仍然沒有回答資料來自哪裡、欄位是否需要保存、下一步由誰填、現有 schema 能否承載。若只寫 scope，AI 仍可能在錯前提上執行；若只寫 ledger 而沒有 scope，AI 又可能列出很多問題卻無法開始。

**Jimmy 的結論：** Scope 令工作不會做太大；assumption ledger 令你不會在錯的理解下把小工作做錯。前者定邊界，後者檢查邊界是否站得住。

兩者可以並排使用：

| 文件 | 核心問題 | 例子 |
| --- | --- | --- |
| Scope | 本輪做／不做甚麼？ | 只加文字 next-step；不加提醒、不部署 |
| Assumption ledger | 哪些前提尚待確認？ | 現有 schema 可否保存？誰是欄位 owner？ |
| Plan | 依照已知與假設，準備怎樣做？ | 讀 sample → 加欄位 → 顯示 → 跑檢查 |
| Acceptance | 怎樣才算完成？ | 三張 sample 卡均可顯示 next step，既有資料不變 |

當其中一項需要改變，不要叫 AI 靜靜把其餘三項也改掉；先讓 owner 看見影響，再重新確認。

## AI 寫 plan 前，哪些假設一定要先攤開給 owner 看？

不用為每個小細節開十頁 spec。真正值得先寫進 ledger 的，是一旦猜錯便會改變範圍、資料、責任、驗收或回退難度的前提。這些通常包括資料 source、正本／草稿界線、外部 action、權限、保存需求、品質標準和 release owner。

小而可回退的視覺偏好，例如一個按鈕放左還是右，可以暫時寫成假設，甚至在 prototype 後再改；但「可否把 AI output 自動寫回 CRM」或「哪個數字是真正 source of truth」就不能只靠合理猜測。差別不在於它技術難不難，而在於猜錯後的後果由誰承擔。

**Jimmy 的結論：** 不是所有未知都要先解完；要優先處理那些會令 AI 讀錯資料、改錯地方、做出不可逆 action 或交不到可驗收結果的高影響假設。

可用 impact × reversibility 快速排序：

1. **高影響、難回退**：資料 source、權限、外發、覆寫正本、付款／部署 —— 必須先問。
2. **高影響、可回退**：核心 workflow、保存要求、驗收者 —— 至少要在 plan gate 確認。
3. **低影響、可回退**：文案、排序、視覺細節 —— 可標成假設，先做小 prototype。
4. **不屬於本輪**：未來功能、未定 owner 的想法 —— 放到不可碰或 backlog，不偷塞進 build。

這個排序讓 AI 問的是最值得問的問題，而不是把每次開始都變成無止境的澄清會議。

## AI 怎樣交一份可回覆的 plan，而不是一個看似合理的猜測？

一份好 plan 不應把所有空白都填滿；它要令 owner 能快速確認、修正或拒絕重要前提。這代表 plan 開頭要先說清楚讀到了甚麼現況，哪些地方只能暫定，哪些問題未解，然後才列步驟。沒有這個順序，step-by-step 再詳細也可能在做錯方向。

對 AI Agent 而言，plan 也是一個停止線：只要碰到未確認假設、不可碰範圍，或需要改變 acceptance，便交回 ledger，而不是自行調整成「它認為更好」的版本。這讓 review 變成在實作前處理方向，而不必等修改遍佈 workspace 才開始抓錯。

**Jimmy 的結論：** Plan 的 purpose 不是顯示 AI 有幾聰明，而是讓人看得出「它準備根據甚麼做、還有甚麼不能自行決定、完成後怎樣收貨」。

AI 可以按這個順序交 plan：

| Plan 部分 | 必須看見甚麼 |
| --- | --- |
| 現況摘要 | 已讀 source、現有 state、已確認限制 |
| Assumption ledger | 已知、假設、待問、不可碰與影響 |
| 建議步驟 | 在已確認 scope 內的最小改動順序 |
| 驗收條件 | 人可以怎樣檢查 output 和既有功能 |
| 停止條件 | 哪些發現會令 AI 不再繼續改 |
| 未做項目 | 明確列出本輪沒碰的資料、功能、部署或外部 action |

如果 owner 只需要回覆兩三個高影響問題，就可以讓 AI 繼續；如果問題未答，保留在 plan stage 本身已經是一個安全成果。

## 想用 Codex 或 AI Agent 做第一個 Build，最安全的 assumption ledger 試跑是甚麼？

最適合第一個試跑的，不是客戶系統、production dashboard 或有敏感資料的任務。選一個本機 sample、可回退的 UI 小改動、公開安全的 markdown 或 synthetic 資料，令你可以專注驗證：AI 有沒有分清已知和假設、會不會在範圍外主動擴大、plan 能否被你快速 review。

例如在一個 sample 工作頁顯示三件已知工作和下一步；不接外部資料、不寫回任何正本、不部署。先叫 AI 只交現況摘要和 ledger，再由你批准最小 plan；只在 ledger 內前提成立時才開始改。這讓你學到的，是如何管理 AI build，而不是只是看一次 code demo。

**Jimmy 的結論：** 第一個 ledger 的成功，不是 AI 立即做完功能，而是它在動手前把關鍵猜測攤出來，讓 owner 可以用很少成本避免一次大返工。

可以這樣試：

1. 選一個 local sample 或 synthetic task，避免真客戶與 production 資料。
2. 指定只讀哪些檔案、只改哪個可回退範圍。
3. 要 AI 先交已知、假設、待問、不可碰、驗收影響五格。
4. 先答高影響問題；其餘低風險假設可保留在 plan 內。
5. 批准最小改動後再實作，完成時對照 acceptance 和未做項目。

暫時不要把真客戶 brief、CRM、合約、credentials 或 production deployment 拿來練習；也不要因為 AI 列了 ledger 就讓它自行決定未確認 business rule。若要進一步把 scope 砍成可 build 的第一版，可讀 [AI coding 愈快，人愈要識砍 scope 同驗收](./4-26-ai-coding-needs-scope.md)；若 plan 已確認、準備在 workspace 做小改動，可讀 [先寫一張 workbench contract](./4-19-workbench-contract.md)；遇到例外時則回到 [Skill 要先寫好 exception ladder](./4-34-skill-exception-ladder.md)。
