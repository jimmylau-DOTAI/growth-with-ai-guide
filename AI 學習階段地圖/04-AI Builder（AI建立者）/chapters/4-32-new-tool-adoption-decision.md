# 新 AI 工具、模型、MCP 值唔值得接？先用一條真工作判斷，不要被 demo 帶著走

每星期都有新模型、新 Agent framework、新 connector 或新 protocol。看見 demo 很吸引，最容易的動作是立刻開帳戶、接 API、把它丟進現有 workflow。幾星期後卻發現：同事不知道何時該用、它讀錯資料、出錯無人知道、或供應商一改版，整條流程又要由頭補。

真正昂貴的通常不是月費，而是你把一條工作重新交代給它、讓人適應新規則、處理例外、維護權限，再承擔 output 對客戶、同事或公開內容造成的後果。新工具能展示一次很漂亮的 output，不等於它已經能在你的工作內穩定運作。

Jimmy 的判斷是：新 AI 工具毋須先證明自己很勁；它要先證明能令一件已存在的工作更可交付，而且增加的維護、風險與依賴在你可承擔範圍。Builder 的重點不是永遠最快試新功能，而是學會設計一個小、可驗收、可回退的試跑。

| 五格判斷 | 它在問甚麼 | 做完後應留下甚麼 |
| --- | --- | --- |
| 真工作 | 它接替哪個現有工作單位？ | 一句可交接的 input、output、owner 描述 |
| 最小 context | 它必須讀甚麼、絕不能讀甚麼？ | approved input 與 access boundary |
| 驗收 artifact | 它交回甚麼，誰能判斷好不好？ | 可打開、可 review 的輸出與 owner |
| 維護與 fallback | 它改價、失效、換人時怎樣繼續？ | 維護責任與舊方法／替代路徑 |
| 停止線 | 它出錯時何時停、誰介入？ | 可回退的 test 範圍與 exception rule |

## 新 AI 工具 demo 很吸引，為甚麼仍未足以證明它值得接進工作？

一條 demo 通常只證明：在某次精心準備的 input 下，工具可以產生一個吸引的 output。它沒有證明它會讀到你真正可用的資料、知道哪些資料不能碰、在資料不足時停下來、讓另一個人接手 review，或在一個月後仍能重跑同一件工作。

這不是對新工具過度保守，而是分清「看見能力」和「得到工作成果」。例如某個 research Agent 能在公開網頁找出十條資料，不代表它能分辨原始來源與二手轉述，更不代表它可以直接把結論寫進客戶簡報或公司內容。後者仍需要證據、owner 和品質閘。

**Jimmy 的結論：** Demo 是一個探索訊號，不是一份採用理由。只有當新工具能被放進一條清楚的工作，並交出可驗收 artifact，才值得投入更多權限與維護成本。

可以先用這張分辨表，不讓「很新」直接變成「值得接」：

| Demo 告訴你甚麼 | Demo 未告訴你甚麼 |
| --- | --- |
| 某種 output 在理想 input 下可能做得到 | 你的資料、例外和真實限制下是否仍然可靠 |
| 介面或功能有新能力 | 它應放在哪個工作環節、誰要負責收貨 |
| 一次完成得很快 | 十次、換人、改版或失敗後能否繼續 |
| 工具供應商怎樣描述自己 | 它有沒有為你的 workflow 創造可量度的改善 |

當你把 demo 放回這個分辨表，就不會因為害怕落後而盲接，也不會因為看過一個失敗示範就錯過真正有用的能力。

## AI 工具要接哪一件真工作，才不會變成「先買後找用途」？

「想試 AI research Agent」或「想接一個 MCP」不是工作定義，只是技術名詞。它沒有說明 input 從哪裡來、AI 要做哪個轉換、最後誰會收到甚麼。沒有工作單位，新工具試用往往只留下帳戶、收藏連結和零散 demo，團隊下次仍不知道它實際幫到哪一段。

一個真工作不必很大。對 Builder 來說，反而應從一段已經重複、低風險、有人願意收貨的流程開始。例如不是「做市場研究」，而是「把三份已批准的公開資料整理成一頁：主張、原始連結、相同與相異處、待確認空格，由內容 owner review」。

**Jimmy 的結論：** 新工具只有在能縮小一個既有工作摩擦時才值得試；先定工作，再揀工具，而不是先把工具帶進來再勉強替它找用途。

寫一張最小 work card，便能把測試講清楚：

1. **觸發**：甚麼時候需要做這件工作？
2. **已批准 input**：它只可讀哪幾份材料、哪個資料範圍？
3. **轉換**：AI 具體負責整理、比較、草擬、分類還是檢查？
4. **輸出**：它要交一份甚麼樣、可打開的 artifact？
5. **完成線**：誰 review、甚麼條件下可以採用？

若這五格填不出來，先不要接工具。想把範圍和可回退工作面寫得更清楚，可讀 [先寫一張 workbench contract](./4-19-workbench-contract.md) 和 [先寫一張可驗收 AI work card](./4-20-ai-work-card.md)。

## 新 AI 工具需要甚麼 context，又有甚麼資料絕對不應交出去？

AI 工具要做好工作，確實需要 context；問題是「給更多資料」不是唯一的做法，也通常不是最安全的做法。若工具不知道任務、欄位和判斷標準，它會猜；若你為了避免它猜而把整個 vault、客戶資料夾或聊天紀錄都接進去，風險便由 output 猜錯變成 access boundary 失控。

最小可用 context 是指它剛好足以完成這次測試的資料。例如一張 approved brief、三篇公開文章和一個輸出欄位 schema，已足夠讓它做比較表。客戶個資、未公開報價、付款資料、私人會議、沒有 owner 的舊檔案，即使「可能有用」，也不應因為方便而自動包括。

**Jimmy 的結論：** Context 不是愈多愈好；它要剛好足以令工具完成指定工作，同時令團隊仍然知道它看過甚麼、沒看過甚麼、錯了可以從哪一格追查。

測試前可以寫一份兩欄 access card：

| 這次允許 | 這次禁止 |
| --- | --- |
| 指定的公開網址或已批准文件 | 客戶、CRM、付款、合約、未公開策略 |
| 明確欄位，例如標題、日期、原始連結 | 全部硬碟、全部 email、未分類 vault |
| 可刪除、可重新產生的試跑輸出 | 直接寫回正本或直接對外發送 |
| 有 owner 的測試資料夾 | 沒有權責、無法追溯的舊檔案 |

如果工具連這個最小範圍也做不好，問題應先被看見，而不是用更多存取權限掩蓋。未清楚資料邊界前，停止擴大連接比繼續調 prompt 更重要。

## AI 工具交回甚麼 artifact，先算不是「Agent 話做完」？

「已完成」是一句狀態訊息，不是一份可驗收交付物。當 Agent 說它已分析、已同步、已研究，reviewer 仍然需要找出它讀過甚麼、改過甚麼、有哪些不確定、可以從哪裡檢查。若找不到這些東西，真正的工作仍在 reviewer 手上。

一個好 artifact 不必漂亮或複雜，但要可打開、可比較、可指出錯誤。研究工具可以交一張附原始連結和待確認欄的比較表；內容工具可以交一份有 evidence boundary 的 brief；自動化工具可以交一張 run receipt，說明它讀了甚麼、停在哪裡、未做甚麼。

**Jimmy 的結論：** 新工具值不值得接，不應由它「講得像完成」決定，而應由人能否用它交出的 artifact 做 review、修正和下一步決定。

在試跑前定下 artifact contract：

| 問題 | 需要有的答案 |
| --- | --- |
| 人可以在哪裡打開 output？ | 指定檔案、表格、draft 或受控資料夾 |
| output 包含甚麼結構？ | 欄位、來源、待確認、版本或狀態 |
| 如何看出 AI 沒有亂猜？ | 引用／連結、空白標記、明確 exception |
| 誰有權批准下一步？ | 指名 reviewer 或 owner，而不是「大家看看」 |
| 若不合格怎樣處理？ | 修正 input、規則或 tool scope；不直接覆寫正本 |

這就是 [答案不等於一份工作](./4-22-answer-is-not-work.md) 的實際分水嶺：你不是收一段文字，而是在收一個可被人採用或拒絕的工作結果。

## 新 AI integration 的維護成本和 fallback，為甚麼要在測試前先寫？

新工具開始時通常只需幾分鐘，但每一個 integration 都有隱藏工作：權限與帳戶管理、API 限額、資料格式改變、模型行為變動、同事要記的新規則，以及出錯時誰會被叫醒。若這些只在 test 成功後才想，團隊很容易把一個小 convenience 變成無人維護的關鍵依賴。

Fallback 不是要你拒絕任何工具，而是避免 workflow 因一個供應商、模型或 connector 出問題便完全停擺。你至少要知道：它明天消失時，舊方法能否暫時完成工作？如果不能，是否已留下足夠的 work card、資料格式和操作說明，讓另一個人可接手？

**Jimmy 的結論：** 可靠的採用不是「永遠不換工具」，而是換工具、失效或換人時，工作和判斷仍然留得住；工具是可替換的一格，不是整條 workflow 的唯一記憶。

試跑前做一個簡短維護檢查：

1. 誰管理帳戶、權限和付款？
2. 誰在工具失敗、超額或改版時 first responder？
3. 哪個 input、schema 或 prompt 需要版本化？
4. 可否用人工方法或另一個工具交回同一種 artifact？
5. 何時會 review 這個 integration 是否仍值得維護？

若其中幾格暫時沒有答案，不代表永遠不能試；只代表 test 不能被偷偷升格為 production dependency。先把它保留在受控、可回退的環境，直至 owner 和 fallback 清楚。

## AI 工具出錯時怎樣停、怎樣回復，才不會把試跑變成 production accident？

第一輪試新工具時，最危險的設計是它一有 output 就可以寫回 CRM、改正本、發 email、發布內容或開啟更多存取權限。這些外部 action 的後果通常比 test 本身大得多，而且一旦出錯，團隊會花很多時間追查它在哪一步把 input、判斷或權限混錯。

一個小而可逆的試跑反而更快學到東西：讓工具只讀 approved copy、產生草稿、排進 review queue，或寫到 sandbox。你看見它哪些地方可靠、哪些 exception 會發生，再決定是否值得加一格權限。這不是拖慢速度，而是避免一次錯誤令所有人失去信任。

**Jimmy 的結論：** 新工具的第一個能力，應該是安全地停下並留下狀態；不是自動完成最多外部 action。能被人停止、檢查和重跑的 test，才有資格慢慢擴大。

一條 safe first test 可這樣設計：

1. 只用 synthetic 或已公開、已批准的材料。
2. 指定它只可產生 draft／比較表／receipt，不可寫回正本或對外發送。
3. 為不確定資料定一個停止規則，例如「找不到原始連結就標記待確認」。
4. 由 named reviewer 看 artifact，記下錯誤類型和修正方法。
5. 只在多次結果都可接受、維護 owner 與 fallback 清楚後，才考慮擴大範圍。

暫時不要把新工具等同於 autonomous system，也不要因一場漂亮 demo 就授予客戶資料、發佈或付款權限。想看多步工作如何保留例外和停止線，可接著讀 [自動化是一條有例外的 pipeline](./4-28-automation-is-a-pipeline.md) 和 [connector 不等於工作系統](./4-27-connector-is-not-an-agent-system.md)。
