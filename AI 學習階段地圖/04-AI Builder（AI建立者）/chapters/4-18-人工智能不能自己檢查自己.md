# AI 自己 check 自己未夠：點樣設計獨立 review

AI 產出後再說「我已經檢查過」，有時確實能捉到格式錯誤；但它仍然可能沿用自己最初的假設、忽略同一個 evidence gap，或者把一段很流暢的解釋誤認為正確。當同一個上下文同時負責做和證明自己做對了，錯誤很容易被原本的理由遮住。

很多人以為只要換一個模型、再開一個 reviewer 就能解決。但另一個 AI 若只看第一個 AI 的結論，或只被問「這份好不好」，它同樣是在猜。真正要獨立的不是所有 context，而是未驗證的推理過程；reviewer 仍然需要回到同一份原始材料、任務範圍和可見的 quality rule。

Jimmy 的看法是：獨立 review 的目的不是再多一個「可以」，而是讓另一個檢查點能說清楚哪一格有 evidence、哪一格只有推論、哪一格應停下。worker 負責交付，reviewer 負責按 rubric 檢查，human owner 才負責承擔是否推進的決定。

| 獨立 review 的一格 | 它解決甚麼問題 | 完成後留下甚麼 |
|---|---|---|
| Approved source | reviewer 不只相信 worker 的結論 | 可回看的原始材料與版本 |
| Task contract | 不讓 reviewer 檢查錯問題 | 目標、範圍與不可做事項 |
| Worker output | 讓檢查對準可見 artifact | draft、表格或 receipt |
| Review rubric | 不只憑感覺說好不好 | pass、revise、unknown、stop 條件 |
| Owner decision | 不把 review flag 當發佈批准 | 最終決定與理由 |

## AI 自己 review 點解未夠：同一個推理鏈會一起漏掉同一件事

一個 worker 最熟悉自己的輸出，因此自查仍然有用；它可以檢查格式、重複、缺欄或是否遵從指定結構。但它也最容易沿用自己開始時的理解：若它一開始把一段推論當成事實，後面的「自我檢查」可能只是在同一個錯誤假設上寫得更完整。

這不是指 AI 一定不可靠，而是所有工作都需要分開「做」和「驗收」。人寫稿也需要 editor，工程師寫 code 也需要 test 或 review；因為不同檢查點能用另一條問題和另一份證據找出盲點。AI workflow 同樣需要讓 reviewer 有機會不被 worker 的理由帶著走。

**Jimmy 的結論：** self-check 可以是第一道 quality gate，但不應是唯一驗收。當輸出涉及外部事實、重要建議或下一手要依賴的工作，至少要有一次能回到 source 的獨立檢查。

| Worker 自查可處理 | 獨立 review 較適合處理 | owner 仍要決定 |
|---|---|---|
| 是否漏填指定欄位 | claim 是否真的被原文支持 | 結果可否用於下一步 |
| 是否符合輸出格式 | 推論有沒有被寫成事實 | 是否接受相關風險 |
| 是否重複或自相矛盾 | input 是否本身不足或過期 | 是否要補資料或停止 |
| 是否按 change request 修改 | rule 是否正確套用到這個情境 | 是否變成對外承諾 |

如果同一個 AI 既產出又宣稱「已驗證」，把它當作一個有用的自查結果，而不是最終證明。下一個問題始終是：另一個人能否依原始材料重看？

## 獨立 review 不是零 context：要分開的是推理過程，不是 evidence

有人一聽到獨立 review，就把 reviewer 放進完全空白的對話。這樣它沒有足夠材料判斷，最終只會用常識猜。真正的獨立，是 reviewer 不需要沿著 worker 的長篇 chat 或自我辯護來理解結果；它應得到完成檢查所需的原始材料、任務契約、最終 output 和 rubric。

這個分法同時保護 evidence boundary。reviewer 不需要讀全部歷史聊天、所有公司背景或無關的私人資料；它只需要看這份工作可以合法、必要地使用的材料。當材料不足時，應輸出 unknown，而不是因為被要求「給答案」而自己補完。

**Jimmy 的結論：** 獨立 review 的核心是同一份可核對 evidence、不同的檢查角度。沒有 source 的 reviewer 是盲猜；只看 worker 推理的 reviewer 則容易被帶偏。

| Reviewer 應收到 | 為何需要 | 不必自動收到 |
|---|---|---|
| 已批准 source 與版本 | 回查 claim、數據或原意 | 全部舊 chat 與內部討論 |
| Task contract | 知道本輪要完成甚麼 | 不相關專案背景 |
| 最終 output | 對準實際要驗收的 artifact | worker 的隱性推理過程 |
| Review rubric | 判斷 pass、flag 或 stop | 「你覺得好不好」式要求 |
| Unknown／escalation rule | 知道資料不足時怎樣停 | 自行擴大權限的指令 |

把這四樣東西打包，reviewer 才能作真正可回看的檢查。任何不屬於檢查所需的私密資料，都不應因為「第二個 AI 要看」而額外分享。

## Review rubric 點樣令獨立檢查有用：先定義甚麼叫 pass、revise、unknown、stop

沒有 rubric 的 review 很容易退化成語氣偏好：一個說「看起來可以」，另一個說「我會寫得不同」。這些意見可以啟發改稿，卻不能證明輸出可否被信任。rubric 要把真正重要的條件寫成可確認的項目，例如每個 external claim 是否有可開啟來源、未知是否標示、是否出現超出工作範圍的承諾。

四種結果尤其重要。pass 代表在已給 evidence 和 rule 下沒有找到阻礙；revise 代表有明確可修正缺口；unknown 代表資料不足，不能判斷；stop 代表碰到不應由本流程繼續的風險。它們讓 reviewer 不必假裝所有事都只有對或錯。

**Jimmy 的結論：** rubric 不是為了讓 AI 打一個漂亮分數，而是令 review 有一致輸出。當 reviewer 能夠清楚說出 pass、revise、unknown 或 stop，owner 才知道應如何處理。

| Review 結果 | 代表甚麼 | 下一步 |
|---|---|---|
| pass | 在目前 evidence 與 rubric 下未見阻礙 | 交 owner 決定是否推進 |
| revise | 有可指出、可修正的缺口 | 回到 worker，附具體 flag |
| unknown | 缺少材料，無法作可靠判斷 | 補 source 或交 owner |
| stop | 碰到權限、私隱、承諾或高風險邊界 | 暫停，不自動繼續 |
| out of scope | 問題不屬於這個 review contract | 重新定義工作或轉交 |

rubric 也必須能被人理解。若一條規則太模糊，reviewer 和 worker 就會各自解讀；先修正規則，比要求它們「再仔細一點」更有用。

## Worker、reviewer 與 owner 點樣交接：把 review 變成一張可追查 receipt

一份好的 review 不應是一段長 comment，而是一張可處理的 receipt。它會指出檢查了哪個 output、根據哪份 source、使用哪條 rubric、發現甚麼、哪些資料仍未知，以及建議下一步。這令 owner 不需要重讀整段對話才能理解責任在何處。

worker 收到 revise 時，也不應只得到「再改好啲」。它應知道哪個 claim、哪段文字或哪條 rule 出現問題；修正後再交回新的版本。若 reviewer 輸出 unknown 或 stop，workflow 需要有明確 escalation，而不是讓 worker 用更長 prompt 蓋過問題。

**Jimmy 的結論：** 真正可交接的是 review receipt，不是「AI 已檢查」這句話。receipt 令錯誤可被定位、修正可被比較、最後決定有 owner。

| Receipt 欄位 | 要回答甚麼 | 一個例子 |
|---|---|---|
| Output version | 檢查的是哪份 artifact？ | research brief v0.2 |
| Rubric item | 用哪條 rule 檢查？ | 每個 external claim 有來源 |
| Finding | 發現甚麼？ | 第二段 claim 沒有 link |
| Evidence | 根據哪份材料？ | 公開原文清單 |
| Status | pass、revise、unknown 還是 stop？ | revise |
| Next owner | 誰處理下一步？ | worker 補 source，owner 再 review |

這份 receipt 不需要很長，但要足夠讓下一手不用猜。它亦會成為改善 prompt、material pack 或 rule 的 evidence，而不是只用來責怪上一輪的 worker。

## 一個公開安全例子：三篇公開文章的 research brief 如何做獨立 review

假設 AI 用三篇公開文章起一份一頁 research brief。worker 交出三個重點、來源連結、未知和兩個待研究問題。它可以先自查格式，但真正的 reviewer 不看 worker 的 chat，只看三篇原文、brief 和已定義 rubric。

reviewer 核對每個 claim 是否真的能回到原文、未知有沒有標示、以及有沒有把 AI 的推論寫成作者結論。若兩個 claim 回不到文章，不是只說「這份不行」；receipt 應標出那兩句、相關 source、缺口類型及結果為 revise。若其中一篇日期或作者資料根本找不到，正確結果可以是 unknown，交 owner 決定是否補資料或不用這篇。

**Jimmy 的結論：** 這個例子裡，獨立 review 不是第二個 AI 幫第一個 AI 加分，而是將 brief 的每個重要主張重新放回公開 evidence 上檢查。human owner 才決定 draft 是否保存、重做或停止。

| 工作位置 | Worker | Reviewer | Human owner |
|---|---|---|---|
| 材料 | 只用已批准公開文章 | 回到相同原文核對 | 確認材料是否足夠 |
| 輸出 | 三點摘要、link、未知 | claim-level receipt | 決定 revise／保存／停止 |
| Rule | 按格式自查 | 按 evidence rubric 檢查 | 決定 rule 是否要改 |
| 資料不足 | 標未知，不補寫 | 回報 unknown | 決定是否補研究 |
| 邊界 | 不對外承諾 | 不宣稱已批准 | 承擔下一步決定 |

這是一個公開、低風險的 internal draft 例子。它不讓 AI 存取私人資料、自己對外發送、作法律／財務判斷或寫入 production 系統。

## 常見錯誤：換模型、加 reviewer，卻沒有真正獨立的檢查面

最常見的錯誤是只換一個模型，卻把上一輪完整答案、理由與結論直接交給第二個模型問「同不同意」。這會令第二個 reviewer 很容易把第一個結論當作默認答案。另一個錯誤是把所有資料塞給所有人；context 多並不必然提高質量，只會令 evidence boundary 模糊和敏感資料擴散。

也有人把 AI reviewer 的 pass 當成發佈批准。pass 只代表它沒有在指定材料和 rubric 下找到阻礙；它不能代表所有事實已獨立驗證，也不能替品牌、客戶、法律或不可逆後果作決定。AI review 是一個 quality signal，不是責任轉移機制。

**Jimmy 的結論：** 獨立 review 的失敗通常不是 AI 不夠多，而是 source、contract、rubric 和 owner 沒有分開。先修檢查面，再談模型或 Agent 數量。

| 容易出錯的做法 | 為何不夠獨立 | 修正方法 |
|---|---|---|
| 叫第二個 AI 同意第一個答案 | 前一個結論成為錨點 | 給 source、output、rubric，不給推理鏈 |
| 所有人看全部資料 | evidence boundary 模糊 | 每位只看完成檢查所需材料 |
| 只輸出一個分數 | 不知道哪裏出事 | 用 pass／revise／unknown／stop receipt |
| AI pass 就直接公開 | 沒有 human approval | owner 依結果作最後決定 |
| 遇到 unknown 仍要答 | 逼模型猜 | 寫清楚 stop／escalation rule |

當一條 review workflow 能夠正確輸出 unknown 或 stop，它不是變慢，而是在避免錯誤由 AI 的流暢語言一路流到不可逆動作。

## 今日怎樣建立第一條獨立 review loop：先檢查一份低風險 draft

選一份可在內部 review 的低風險 output，例如一頁基於公開材料的 research brief。開一個獨立 review context，只提供已批准 source、任務範圍、三條 rubric 和要檢查的 output；不要把 worker 的長篇 chat 或不必要的私人背景放進去。

要求 reviewer 用固定格式輸出每個 flag：哪一格、哪條 rule、根據甚麼 evidence、結果是 pass、revise、unknown 或 stop。之後由 human owner 決定是否退回、保存為 internal draft 或停止。這樣跑過一次，你就會看見自己的 source pack、rubric 還是 owner boundary 哪裏仍不清楚。

**Jimmy 的結論：** 好的 review 不是多一個 AI 說「可以」；而是另一個檢查點能回到同一份 evidence，指出哪裏真的過關、哪裏仍然未知。先把這一條 loop 跑穩，再考慮自動化。

| 第一條 review loop | 你要準備甚麼 | 安全起點 |
|---|---|---|
| Source | 已批准、公開且可回看材料 | 三篇公開文章 |
| Contract | 只檢查這份 draft 的 evidence 與未知 | 一頁 internal brief |
| Rubric | 三條可核對的條件 | claim 有 link、未知有標、不可猜 |
| Output | 一份固定 receipt | pass／revise／unknown／stop |
| Owner | 最後決定下一步的人 | content owner review |

先在可回看的 internal draft 裡保存 source、output 和 receipt。暫時不要把 AI reviewer 的 pass 直接連到公開發佈、外部發送、客戶資料或 production 寫入；這些動作仍需要獨立權限與 human approval。下一步可看 [如何設計多個 specialist review，而不是叫 AI 一齊附和](./4-16-多個人工智能的專家檢查.md)。

> 好的 review 不是多一個 AI 說「可以」；而是有人能回到同一份 evidence，指出這份結果在哪裡真的過關、哪裡仍然未知。
