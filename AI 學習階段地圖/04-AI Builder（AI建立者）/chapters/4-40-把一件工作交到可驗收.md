# 你唔係未識用 AI Agent：你未把一件工作交到可驗收

你已經可以用 ChatGPT 寫初稿、整理資料、拆想法，也開始聽到 Codex、Agent、Skill、automation。這時很容易走兩個極端：一是覺得自己不會寫 code，所以不敢交任何真工作給 AI；二是一聽到 Agent 便想它自己讀晒資料、改晒檔案、接晒工具、甚至自己發出去。

兩個極端其實都把焦點放錯了。AI Agent 的第一個難題不是模型、code 或 connector，而是你能否說清今次到底交甚麼工作、它只可碰甚麼、交回來怎樣驗收、遇到哪裡必須停。沒有這些條件，AI 只會更快把模糊變成 output。

Jimmy 的判斷是：Builder 的起點不是「砌一個 autonomous agent」，而是把一件小而真實的工作交到可驗收。當 AI 能在清楚範圍內交回 artifact、evidence 和未知，你才有基礎談 Skill、loop 或 automation。

| 由聊天走到工作 | 你要先決定甚麼 | 留下甚麼 |
|---|---|---|
| 一句 AI 問題 | 今次想要甚麼答案 | 一段對話 |
| 一個 AI work unit | scope、材料、artifact、check、stop、owner | 可 review work card |
| 一次 bounded run | 只在哪裡可試、怎樣回退 | receipt 與 evidence |
| 一條可重跑 routine | 哪些做法已穩定 | Skill／SOP 候選 |

## AI Chat 和 AI Agent 做事，真正的分水嶺是甚麼？

AI chat 很適合探索：你問一條問題、貼一段材料、拿回一個答案，然後自己決定下一步。它不一定比較低級；很多一次性、需要人思考的工作，用 chat 已經最合適。問題只在於 chat 本身不會自動知道可讀資料、完成線、權限或誰來收貨。

AI Agent work 則把一段工作交代成可見的合約。即使同樣使用對話工具，甚至未寫一行 code，只要你明確指定 task、allowed material、scope、artifact、review 和 stop line，AI 就不再只是回覆，而是在一個受控範圍協助完成工作。Codex 容易示範這件事，因為它可以閱讀指定 workspace、提出計劃、處理被批准的小改動，並交回差異與檢查結果。

**Jimmy 的結論：** Chat 的完成線是得到有用答案；Agent work 的完成線是交回一段有範圍、可檢查、有人負責採用的工作成果。

| 問題 | AI Chat | AI Agent work |
|---|---|---|
| 交出去的是甚麼 | 問題、材料或方向 | 有 scope 的 work unit |
| AI 根據甚麼 | 本輪對話內容 | 指定 materials／workspace |
| 交回甚麼 | 回答、草稿、建議 | artifact、evidence、unknown、receipt |
| 人管理甚麼 | 是否喜歡答案 | authority、quality gate、exception、approval |

不要因為工具名字有 agent 就假定已進入第二欄。真正轉變發生在你能不能說明它做完哪一段、而不是只說它看起來很能做。

## AI Builder 的第一件工作，為甚麼應該細過你想像？

第一次做 Agent 時，很多人想選最大的工作：自動處理客戶查詢、連 CRM、寫完整內容系統、改一個大網站。這些工作同時牽涉資料、權限、例外和多人決定。第一輪一有問題，你根本分不出是 task 未定、context 不足、工具錯、review 不夠，還是本來就不應自動化。

第一個 work unit 應該細到你能看懂每一步，也真到你能判斷它有沒有幫到。例如公開資料轉 internal brief、在公開 demo workspace 檢查一個顯示問題、把一份已批准 outline 起成 internal draft。目標不是展示 AI 多自主，而是讓你練一次清楚交接、人手驗收和安全停止。

**Jimmy 的結論：** 第一個 Agent work 不是要替你做完一個部門；它要交一份你能明確 pass、revise、stop 或回退的小成果。

| 適合 first run | 為甚麼 | 暫時不要做 |
|---|---|---|
| 公開資料 → internal briefing | 來源、欄位、unknown 可核對 | 用真實 CRM／客戶資料 |
| 已批准 outline → draft | 可檢查結構有沒有跟足 | 直接對外發送／發布 |
| Demo workspace 的小 UI 檢查 | diff 與範圍清楚 | 改登入、付款、資料庫 |
| 重複工作 → work plan | 先看懂流程再考慮執行 | 一開始接 connector／automation |

選「錯了也可安全拒絕」的工作。這樣你會學到 Agent 應怎樣停，而不是只看一個碰巧成功的 demo。

## 第一張 AI work card 應寫哪六格，才不會把工作交到一半失控？

很多 prompt 只寫成果，例如「幫我整好首頁」或「幫我研究一下」。這不足以讓 AI 或 reviewer 知道甚麼叫完成：它可否讀任何檔案？可否順便改資料邏輯？遇到材料不足應否找更多資料？改完是否可以自己 deploy？一張 work card 把這些隱藏條件放回同一頁。

六格不是 burocratic 流程，而是一分鐘發現「這件事其實還未可交」的檢查。若 owner、stop line 或 check 根本答不出，先不要用更強工具掩蓋；把工作縮小、問 owner，或只做 plan，會比叫 AI 盲目執行更快。

**Jimmy 的結論：** AI work card 的價值不是命令 AI；而是讓人先看見一件工作是否真的有足夠 scope、邊界和完成線可被交接。

| Work card 格 | 要答的問題 | 沒有它的風險 |
|---|---|---|
| Task／artifact | 今次交甚麼、幫誰作甚麼決定？ | AI 只會給一大段不知怎樣用的 output |
| Allowed material | 只可讀哪份資料／檔案？ | 越權讀取或錯用 context |
| Scope | 只處理哪一小段？ | 小改動變成大 project |
| Check | 怎樣知道已做對？ | 有 output 卻不能收貨 |
| Stop line | 遇到甚麼必須問人？ | AI 把 unknown／權限問題硬做下去 |
| Owner | 誰決定採用、停止或下一步？ | 沒有人對結果負責 |

```text
Task／artifact：＿＿＿＿＿＿＿＿＿＿
Allowed material：＿＿＿＿＿＿＿＿＿＿
Scope：＿＿＿＿＿＿＿＿＿＿
Check：＿＿＿＿＿＿＿＿＿＿
Stop line：＿＿＿＿＿＿＿＿＿＿
Owner：＿＿＿＿＿＿＿＿＿＿
```

當六格能被另一位人讀懂，你已經不再只是在 prompt AI，而是在為一段可回看的工作建立入口。

## 用 Codex 做第一個 AI work unit，怎樣保持 scope、dry run 和 human review？

假設一個公開 demo 網站的首頁在手機版有文字被截斷。這是一個合適的 Codex 練習，因為範圍可限制在顯示層、材料可限於 README 和指定首頁檔案、成果可以用 diff 與明確畫面核對。它不需要接真資料，也不授權改其他功能或部署。

第一輪讓 Codex 先讀、說明理解、提出最小計劃；人確認後才容許它改指定位置。改完再跑現有檢查或做手動 read-back，並要求它列出沒有驗證甚麼、如何回退。這種節奏看似多了一步，但把「它到底做了甚麼」和「是否超出範圍」放在可檢查的位置。

**Jimmy 的結論：** Codex 的價值不是它可以改 code；而是你能在一個清楚工作合約下，看見它讀了甚麼、改了甚麼、檢查了甚麼、哪裡仍要人決定。

```text
先讀 README 和指定首頁檔案，說明你理解的手機版顯示問題。
只檢查並處理首頁顯示層；不要改資料計算、登入、儲存、部署或 production setting。
先交最小修改計劃，等 owner 確認後才改。
改完後跑已有檢查／列出手動檢查；交回 changed files、結果、未驗證項目和回退方法。
若問題超出顯示層，停止並列 owner 要決定的問題。
```

| Loop 一步 | AI 可以做甚麼 | 人仍做甚麼 |
|---|---|---|
| Plan | 讀指定材料、提出最小做法 | 確認 scope 是否正確 |
| Dry run／small action | 只改批准的小範圍 | 保留原狀態和回退決定 |
| Check | 跑已有 check、列出結果 | 判斷 evidence 是否足夠 |
| Receipt | 說明已做、未做、unknown | pass／revise／stop／deploy 決定 |

這個例子也可以換成內容或研究工作。重點始終是：先交一小段人看得懂的工作，再讓 AI 在裡面跑。

## AI 說「做完」後，甚麼 evidence 才算真正可驗收？

AI 交出一段內容、幾個檔案或一句「tests passed」，都只是狀態訊號，不是自動的完成證明。你需要在 work card 的 Check 格預先說明：甚麼 artifact 可見、哪些資料能核對、哪個 reviewer 要看甚麼。沒有這些，你只會靠 output 漂不漂亮或 AI 自己的自述來收貨。

不同工作 evidence 不同：內容 draft 要看 materials、unknown 和 reviewer 改稿；workspace 改動要看 changed files、檢查輸出與回退；研究 brief 要看來源、日期、缺口與下一步。重點不是做很多測試，而是用能回答「它有沒有做到今次承諾」的 evidence。

**Jimmy 的結論：** AI 的 output 是候選成果；只有對應 scope 的 evidence 加上 owner review，才決定這段工作是否完成。

| Artifact | 可用 evidence | 還不能代表甚麼 |
|---|---|---|
| Internal draft | approved materials、unknown、rubric review | 可直接對外發布 |
| Code／workspace diff | changed-file list、check output、read-back | 已安全 deploy 到 production |
| Research brief | source links、時間、待確認事項 | 所有結論已被獨立驗證 |
| Agent receipt | 做過／沒做／停在哪裡 | 下一輪一定可自動化 |

```text
Receipt：
- 本輪 artifact：＿＿＿＿＿＿＿＿＿＿
- 根據／檢查：＿＿＿＿＿＿＿＿＿＿
- 已完成：＿＿＿＿＿＿＿＿＿＿
- 未驗證／unknown：＿＿＿＿＿＿＿＿＿＿
- 下一步由誰決定：＿＿＿＿＿＿＿＿＿＿
```

Evidence 越對應今次 scope，reviewer 越能快判斷採用、修正或停止，而不是被 AI 的自信語氣帶著走。

## AI work unit 何時才值得變成 Skill、loop 或 automation？

一個 first run 成功不代表可直接變成 Skill。第一次可能剛好材料完整、例外未出現、owner 剛好在旁；真正值得重用的工作，應在幾次相近情況仍能說清 input、步驟、output、quality gate、常見失敗和人手決定。此時把 work card 與 receipt 整理成 Skill，才不是把一次 prompt 冷凍起來。

loop 或 automation 的門檻更高：除了 routine 本身穩定，還要有 trigger、可讀 state、error route、approval 與回退。若目前每次 task 都很不同，繼續用 work card 反而更誠實；你正在學工作本身，還未需要為它假裝一個固定系統。

**Jimmy 的結論：** Skill、loop 和 automation 是被 evidence 證明可重跑後的工作形態，不是第一個 demo 的升級獎勵。

| 現在看到的證據 | 最合適形態 | 下一步 |
|---|---|---|
| 工作仍一次性、材料常變 | Chat／work card | 先做清楚一次可驗收 run |
| 相近工作重複、格式漸穩 | Skill 候選 | 寫 input、steps、quality gate、exception |
| 多步反覆、每步有 check | Bounded loop | 加 state、receipt、stop line |
| Trigger／資料／approval 皆穩定 | Automation 候選 | 先 dry run，再決定是否擴大 |

不要把同一條 AI workflow 叫成 agent、Skill、automation 當作進步。真正的進步是下一次能少猜、少越界、少靠運氣收貨。

## AI Builder 第一個 work unit 做完後，怎樣決定下一步？

先回看你的 receipt：最常缺的是 task、materials、scope、check、stop 還是 owner？只修最早失效的一格，然後在同類低風險工作再跑一次。若 AI 總讀錯，就補 context 或 boundary；若 output 不可驗收，就重寫 artifact／check；若總要人臨時決定，就不要急著加 automation。

當你看到同一張 work card 已能讓人和 AI 都少猜一次，就把它保留為下一輪的入口。當它反覆跑穩，再升成 Skill 或 bounded loop；當 workflow outcome 已能被 owner 量度和帶人使用，才走向 AI Value Creator。這樣你的 Builder 路徑是由真工作長出來，而不是由工具清單堆出來。

**Jimmy 的結論：** Builder 的完成線不是「我有個 Agent」；而是有一段 AI 工作能交清、驗到、停得住，並知道是否值得再跑。

| 你現在卡住的位置 | 接著讀甚麼 | 會留下甚麼 |
|---|---|---|
| 想立即填第一張可驗收卡 | [AI work card](./4-20-先寫可驗收的人工智能工作卡.md) | 六格 work card |
| AI 有 output 卻不知怎樣收貨 | [答案不等於一份工作](./4-22-人工智能交出一段答案不等於它交到一份工作.md) | artifact 與 evidence |
| 想將 routine 包成可重跑做法 | [Skill 是工作合約](./4-23-你以為技能是一段指令其實它是一份工作合約.md) | Skill candidate |
| 想安全跑第一條 loop | [先跑一條可停的 Agent loop](./4-25-先跑一條可停止的智能代理循環.md) | bounded loop |
