# Obsidian 筆記愈多愈亂？有用嘅思考摩擦先會變成 AI context

你可能已儲了很多文章、影片、截圖和筆記，卻在幾個月後發現：自己不記得那篇主張是甚麼，AI 也不知道哪些內容可信、相關或已過期。收藏看似很快，實際上只是把未消化資料從瀏覽器搬到另一個地方。

問題不在你用 Notion、Obsidian 還是其他工具，而是每次存入時有沒有做一點加工：重寫標題、說一句自己的判斷、連回一個真問題、放進一個找得到的位置。沒有這些摩擦，知識庫只會愈大，卻愈難讓人或 AI 找到可用 context。

Jimmy 的判斷是：有用的思考摩擦不是拖慢你，而是加工。第一輪可選一篇已公開、低風險來源，用最小 note 寫清主張、自己的判斷、適用範圍和下一步；不需要把整個 vault 或私有資料交給 AI 才開始。

| 只是收藏 | 加工成可用 context | 下次留下甚麼 |
|---|---|---|
| 原文標題和連結 | 自足標題＋來源說甚麼 | 找得到主張 |
| 一堆筆記孤立存在 | 連到問題、概念或工作 | 找得到關係 |
| 摘要像原文縮短版 | 加自己的判斷與邊界 | 找得到用法 |
| 全部資料都可餵 AI | 指明 evidence、reference、unknown | 找得到安全範圍 |

## 筆記存得愈快，點解反而愈難變成可重用 AI context？

儲存是一個很容易完成的動作：按一下 bookmark、貼一條 URL、丟一張截圖，當下會有「我已經處理了」的感覺。但你其實未必回答過這份資料在說甚麼、為何值得保留、跟哪一件工作有關，或它有沒有可信的根據。

AI 讀到未加工收藏時也有同樣問題。它可能可以總結文字，但不知道這是你認同的判斷、外部作者的主張、已過期的參考，還是一條未驗證想法；沒有清楚標記，它只是在大量資料中猜哪些重要。

**Jimmy 的結論：** 收藏只改變資料的位置；加工才令一份資料有主張、關係、用途和可被人／AI 理解的邊界。

| 存下的內容 | 日後的困難 | 加工後的改變 |
|---|---|---|
| 原文標題「10 個效率方法」 | 搜尋時不記得它到底講甚麼 | 改成「效率工具不能代替優先次序判斷」 |
| 一條連結沒有註釋 | 不知它是事實、觀點還是靈感 | 寫明 source 說甚麼、我怎樣看 |
| 截圖放在資料夾 | 不知它應用在哪個工作 | 連到一個任務、概念或 stage |
| 舊筆記混著新資料 | AI／人不知是否仍可採用 | 加日期、適用範圍和待確認項目 |

當一份筆記能回答「它講甚麼、我怎樣用、甚麼時候不適用」，它才由存檔開始變成工作可用的 context。

## 知識庫要經過哪三層，先由收藏倉變成可用 context？

不是所有資料一存下來就值得變成 AI context。大部分來源先只是記憶：你想保留它，未必已同意它，也未必知道它會影響甚麼工作。要讓它可重用，還要建立關係和用法，否則只是一個較整齊的雜物房。

三層不是要你為每一條資料建立複雜關係圖，而是讓你在最小程度上知道：原文在哪裏、它和哪個問題相關、下一次要怎樣拿來用。這同時保護你不會把未消化來源過早升格成自己的結論。

**Jimmy 的結論：** 有用的知識庫不是資料多，而是每份重要資料都能從來源走到關係，再走到一個可驗收的工作用途。

| 層次 | 放甚麼 | 它回答的問題 |
|---|---|---|
| 記憶層 | 來源、日期、摘錄、素材、原始問題 | 原文是甚麼、從哪裏來？ |
| 關係層 | 主題、概念、相連 note、相關 project | 它和我已知的哪件事有關？ |
| 重用層 | 自己的判斷、task brief、規則、下一步 | 它會改變哪一個工作決定？ |
| 邊界層 | evidence、reference、unknown、適用範圍 | 哪些可採用、哪些仍要確認？ |

只做第一層不是失敗；它只是代表這份資料尚未準備好變成 AI context。不要因為有了 vault，便假設裡面任何內容都已可直接交給 AI 或對外引用。

## 一份來源怎樣由「睇過」變成自己的判斷，而不是重複作者說法？

摘要和判斷不是同一件事。摘要回答「作者說了甚麼」；判斷則回答「在我的工作情況下，這有何用、我是否採用、甚麼限制令我不能照抄」。若你只把原文縮短，筆記仍然只是作者的材料，不會自動成為你的 insight。

最小加工可以很短：用自己的語言重寫一個有主張的標題，再寫一兩句「這會改變我哪個工作決定」和「它在哪個情況不成立」。這幾句已足夠讓未來的你和 AI 知道它不是一段漂浮的資訊。

**Jimmy 的結論：** 一份來源變成你的 insight，不是因為你抄得更短，而是因為你能說明它如何改變你的判斷，並承認它的適用邊界。

| Source note 一格 | 你要寫甚麼 | 不要只寫 |
|---|---|---|
| 自足標題 | 用一句話說清主張 | 原文吸睛標題 |
| Source says | 原作者真正提出的重點 | 你希望它在說甚麼 |
| My work context | 它和你哪一類工作有關 | 「很有用」 |
| My judgment | 暫時採用／不採用甚麼 | 原文的複述 |
| Boundary | 甚麼資料／情況仍未支持它 | 「任何人都適用」 |

```text
自足標題：＿＿＿＿＿＿＿＿＿＿
來源說：＿＿＿＿＿＿＿＿＿＿
它和我哪件工作有關：＿＿＿＿＿＿＿＿＿＿
我的暫時判斷：＿＿＿＿＿＿＿＿＿＿
何時不應照抄／仍要確認：＿＿＿＿＿＿＿＿＿＿
下一次會在哪裏試或引用：＿＿＿＿＿＿＿＿＿＿
```

如果你還不能寫出自己的判斷，最誠實做法是保留它在來源層，標成「待消化」，而不是急著變成概念或公開主張。

## 筆記標題點樣改，先讓自己和 AI 日後找得到真正主張？

原文標題通常為了吸引讀者、搜尋或特定平台而寫，未必適合作為你的知識庫索引。三個月後你未必記得「10 個方法」是哪十個方法，也不會想到要用那幾個字搜尋；但你很可能記得當時要解的是「工具很多仍然做不快」這類問題。

自足標題不是要寫得文青，而是讓未看過原文的人也能看出主張與工作問題。這也是 AI retrieval 較容易使用的形式：它能從標題判斷一段內容可能回答甚麼，而不用先讀完整份雜亂來源。

**Jimmy 的結論：** 標題是最便宜、但影響很大的加工；它把一個收藏變成日後可被找回的判斷入口。

| 原文／模糊標題 | 可重用的自足標題 | 它回應的工作問題 |
|---|---|---|
| 「10 個提升效率的方法」 | 「效率工具解決不了未排序的優先次序」 | 為何工具多仍然亂？ |
| 「AI agent 的未來」 | 「AI agent 先要有範圍、驗收和停止線」 | 何時值得把工作交給 agent？ |
| 「How to write better prompts」 | 「Prompt 不足時，要補 context 和完成線」 | 為何 AI 每次仍然猜？ |
| 「Obsidian 入門」 | 「筆記有加工，才會變成可重用 context」 | 怎樣避免 vault 變收藏倉？ |

改標題時發現自己答不出主張，這不是壞事；它代表你應該先回看來源、把它留在 source note，或乾脆不再花時間存它。

## 筆記點樣連結到工作、概念和來源，而不需要一次過重整整個 Vault？

連結的目標不是製造一張漂亮的 graph，而是回答這份資料有哪個去處。它可能支持一個新手教學、補充一個 AI Builder 工作判斷、提醒一條 project 假設，或只是一個日後可參考的反例；有了去處，你下次需要時才找得到。

不要嘗試一次過把整個 vault 補齊關係。先由當前正在做的一件工作開始：每次只連一個最接近的問題／概念和一個來源位置。當關係真正在工作中被使用，才值得逐步補充索引。

**Jimmy 的結論：** 一條有用的連結不是「這篇也許相關」，而是「這份資料會在這個問題或工作決定被重新找到」。

| 這份筆記的角色 | 可以連去哪裏 | 留下的說明 |
|---|---|---|
| 外部做法 | 一個相關 guide／concept | 它補充哪個判斷，不能證明甚麼 |
| 自己的工作學習 | task brief／project note | 它改變了本輪哪個選擇 |
| 反例／失敗教訓 | review rule／exception note | 下次看到甚麼訊號要停 |
| 仍待消化的來源 | source inbox／待判斷清單 | 為何未升成 insight |

```text
這份資料相關的問題：＿＿＿＿＿＿＿＿＿＿
它會影響的工作決定：＿＿＿＿＿＿＿＿＿＿
它支援／挑戰哪條既有判斷：＿＿＿＿＿＿＿＿＿＿
下次何時需要重新找它：＿＿＿＿＿＿＿＿＿＿
```

若連不到任何問題，也不代表必須硬塞。可以先留在 source 層，等待一個真工作令它顯示出用途。

## AI 要讀你的筆記時，哪些內容不可以因為「context」就全交出去？

AI-readable 不等於所有資料都適合給 AI。筆記中可能混有客戶、合約、CRM、credentials、production 設定、會議內容或尚未公開的判斷；即使它們對你有用，也不代表今次 AI 任務、這個工具或這個人有權看到。

先選最小、跟本輪工作有直接關係、可安全解釋的 context。若只是要練「先理解、後生成」，一份公開文章加一段 synthetic 工作情境已經足夠；不要因為想讓 AI 更了解你，就把完整 vault 或所有歷史 chat 一次過餵進去。

**Jimmy 的結論：** AI context 的價值在於合適，不在於全面；每次都要能說明為何這份筆記必要、誰可看、output 怎樣收貨。

| 筆記類型 | 現階段怎樣處理 | 原因 |
|---|---|---|
| 公開來源＋自己的抽象判斷 | 可用於低風險 draft | 有清楚來源和工作用途 |
| 已去識別化／synthetic 範例 | 可用於格式與流程練習 | 能驗證方法，不暴露真資料 |
| 客戶、合約、CRM、會議紀錄 | 不作一般練習 context | 有資料、授權與關係風險 |
| Credentials、API key、production 設定 | 永不放入 context | 可直接影響帳戶或系統 |
| 未確認、過時或用途不明筆記 | 標待消化／不採用 | 不能當成可靠 evidence |

這些界線不令你的知識庫失去價值。它們是讓你日後能選出乾淨 context pack，而不是在需要用 AI 時才發現整個 vault 無法安全使用。

## 筆記加工要做到幾深？何時只存來源，何時才值得升成 insight？

不是每一份資料都值得深度加工。規格、電話、已知資料表或一次性參考，可以只存來源和日期；真正值得多寫幾句的，是它會影響你反覆出現的工作、教學、產品、內容或決策。

不要因為「想建立知識庫」就把每一篇文章升格成自己的 concept。你可以有三個輕重層：source note 保留原貌、insight note 寫你的判斷、concept／guide 只在多個 insights 真正互相支持或被工作驗證後才建立。

**Jimmy 的結論：** 筆記深度應跟它會影響的工作決定走；先保留來源，再消化判斷，最後才把反覆成立的東西升成可教或可重用的概念。

| 層次 | 甚麼時候使用 | 最少需要甚麼 |
|---|---|---|
| Source | 想保留、但未判斷 | 來源、日期、原始主張、用途未定 |
| Insight | 已能說明對自己工作有何判斷 | 自足標題、自己的決定、boundary、連結 |
| Concept／Guide | 多個 insights 反覆支持同一做法 | 核心判斷、可教流程、反例、適用邊界 |
| Skill／SOP | 工作已反覆跑通且可驗收 | 輸入、步驟、輸出、exception、review |

這個次序避免你把未消化收藏包裝成「自己的洞見」。當一條 insight 真的在工作中被重用，它會自然顯示是否值得升級。

## 不用重整整個 Vault，怎樣做第一次 source-to-decision 加工？

隨機選一篇已公開、低風險而且你覺得「可能有用」的舊文章。不要先改 folder、不用搬檔案、不用接 AI 工具；先把它寫成一張 source-to-decision note，目標是證明你下次真的找得到並能說明它的用處。

完成後，把 note 連回你目前一個真問題，例如「如何令 AI output 更可驗收」或「何時先不要做 automation」。若它沒影響任何決定，就把它如實留在 source 層；這比強迫它變成公開 insight 更乾淨。

**Jimmy 的結論：** 知識庫的第一個成果不是更多資料夾，而是一份你重新打開時仍知道主張、邊界和下一步的決策 note。

```text
來源：＿＿＿＿＿＿＿＿＿＿
自足標題：＿＿＿＿＿＿＿＿＿＿
來源真正主張：＿＿＿＿＿＿＿＿＿＿
我的工作情況：＿＿＿＿＿＿＿＿＿＿
我的暫時判斷：＿＿＿＿＿＿＿＿＿＿
Evidence boundary／仍未知：＿＿＿＿＿＿＿＿＿＿
相關問題／下一次使用位置：＿＿＿＿＿＿＿＿＿＿
```

先做三張這種 note，再看有沒有重複判斷值得合併。不要一開始就掃描、重寫或公開整個 vault；真正有用的結構應由使用中的問題長出來。

## 做好一張可重用筆記後，怎樣讓它幫到下一件 AI 工作？

當你下一次寫 task brief、做內容 draft 或準備教學時，先找相關的 insight note，而不是把完整來源丟進 AI。帶入的應該是：已確認的主張、你的工作判斷、可用 evidence、適用範圍和仍需確認的地方，讓 AI 知道它能依據甚麼、不能假設甚麼。

若同一條判斷已被多次使用和 review，才把它整理成 context pack 或 guide；若它只是一次靈感，保留為 source／insight 即可。這種「先用、後升級」的方式，會令你的 vault 和 GitHub 公開攻略都來自真工作，而不是大量未驗證內容。

**Jimmy 的結論：** 筆記真正有用的時刻，是它能讓下一次工作少重講、少猜、少把外部觀點誤當成自己的結論。
