# 改咗十次，AI 下次仍然唔明？你未把 feedback 變成判斷

你常常修改 AI 的初稿：換字、刪段、補資料、改語氣；但一到下一份同類工作，AI 仍然像第一次見你，舊 chat 也愈積愈亂。你明明做了很多 review，卻沒有感覺下一次真的更容易。

問題不是你改得不夠多，而是修改理由只留在當次對話或你腦裡。AI 看不見你為何改、這個標準適用在哪裡，也不知道某句只是今次的臨時要求；把所有歷史都存起來，也只會變成另一堆難以取用的 context。

Jimmy 的判斷是：真正有複利的 feedback，不是記低每個改字，而是分清一次性修改、可重複規則和已改變要求，然後只把值得留下的判斷變成下次可用 reference。

| 你改了甚麼 | 它應留在哪裏 | 下次怎樣處理 |
|---|---|---|
| 今次日期、臨時安排、單次語氣 | 本輪 task／draft | 不升成長期規則 |
| 多次出現、講得出原因的修正 | Reference card／context pack | 下一次先檢查是否適用 |
| 讀者、目標或工作要求已變 | 更新 task brief／work profile | 不把舊規則硬套新任務 |
| 未確定是否重複的意見 | Feedback log | 再觀察一兩輪 |

## AI 改咗好多次仍然重複犯錯，點解不是因為它「唔記得」咁簡單？

AI 在新任務裡不會自然知道你上一次為何修改一段文字。即使你保存了整段對話，裡面也可能混有本輪日期、臨時偏好、不同讀者要求和未確認意見；把全部餵回去，未必會令結果更一致，反而可能令 AI 找不到真正的規則。

人也會有同樣問題。若你只看到最後改好的稿，卻不知道為何當時改了，你很難教同事或下次的自己重做。真正要留下的是「這個修改背後的判斷」，不是每一個字的修訂痕跡。

**Jimmy 的結論：** AI 重複犯錯，不一定是工具沒有記憶；很多時是你未把修改原因變成有範圍、可重用的工作規則。

| 只保留的東西 | 下次的結果 | 較有用的替代 |
|---|---|---|
| 完整 chat 紀錄 | 雜訊很多，難知甚麼仍有效 | 抽出一兩條有原因的 rule |
| 最終版本 | 看到結果，看不到修正理由 | 留初稿、final 和差異說明 |
| 「唔似我」「太硬」 | 太主觀，無法執行 | 說明哪種讀者、哪種結構、為何不適合 |
| 每次要求都存成規則 | context 互相矛盾 | 先分類、再確認是否重複 |

當你能說明「為何改、在哪裡適用、何時不適用」，AI 才有一條下次可以先檢查的路徑。

## AI feedback 要先過哪個小 gate，才不會把每句意見都變成永久規則？

不是所有 feedback 都值得變成 context。一次性 edit 可能是今天日期、某位 reviewer 的臨時偏好或本輪特別安排；changed requirement 則代表讀者、目標或項目方向已經不同，應更新本輪 task，而不是讓舊規則繼續控制未來工作。

只有重複 pattern 才值得升成 reference：你在兩三個相近情境都看到同一問題、能說明為何它重要、也能指明它只適用哪一類工作。這個 gate 令你的 context 長得慢一點，但較不會被一次意見污染。

**Jimmy 的結論：** feedback 的第一步不是存，而是判斷它是一次性 edit、重複 pattern，還是已改變的要求。

| Feedback 類型 | 怎樣判斷 | 正確去處 |
|---|---|---|
| 一次性 edit | 只為今次日期、人物、場合或臨時安排而改 | 留在本輪 draft／task note |
| 重複 pattern | 在相近工作多次出現，原因相同 | 候選 reference rule |
| Changed requirement | 讀者、目標、範圍已轉變 | 更新 task brief／work profile |
| 未確定 pattern | 只出現一次，但感覺可能重要 | 放 feedback log，再觀察 |

```text
這次我改了甚麼：＿＿＿＿＿＿＿＿＿＿
為何要改：＿＿＿＿＿＿＿＿＿＿
它是一次性 edit、重複 pattern，還是 changed requirement？＿＿＿＿
在哪些工作會再出現：＿＿＿＿＿＿＿＿＿＿
下一次應先沿用、再觀察，還是不要帶過去？＿＿＿＿＿＿＿＿＿＿
```

這個小 gate 讓你不必立即建一套龐大標準庫，只要在每次 review 後留下足夠資料，讓下一次有更好的判斷起點。

## AI feedback 怎樣由「這段唔啱」變成可執行的規則？

「太硬」「不夠清楚」「不要亂講」都是有價值的訊號，但還不是 AI 或同事能使用的規則。要讓它可執行，你需要把感覺翻成可觀察條件：哪段結構有問題、哪類主張欠 evidence、哪種讀者會誤解、交付時要看到甚麼。

規則也不應只寫命令。若沒有 why，AI 或下一位同事只會模仿表面句子；若沒有 scope，它可能在不相關工作硬套；若沒有 expiry，過時要求可能一直留在 context 裡。

**Jimmy 的結論：** 好 feedback rule 不是「永遠這樣寫」，而是「在這種情況，因為這個原因，先檢查這個條件」。

| 模糊 feedback | 可執行 rule | 可檢查條件 |
|---|---|---|
| 「不要講得太誇」 | 沒有本輪 evidence 的成效主張，標為判斷／未知，不寫成保證 | 每個強主張可回到 evidence 嗎？ |
| 「開頭不夠吸引」 | 面向新手時，先用日常工作摩擦，再出工具術語 | 第一段有沒有具體摩擦？ |
| 「表格難用」 | Briefing 固定以來源、重點、未知、下一步四欄交回 | Reviewer 能否逐格核對？ |
| 「不似我們風格」 | 先指出讀者的決定，再提出做法；不假設未驗證成果 | 是否先說了讀者要解的問題？ |

把 rule 寫成能檢查的句子，下一次你就可以讓 AI 自查、讓 reviewer 準確退回，也能看出規則到底有沒有真的減少返工。

## 一張 AI reference card 最少應有甚麼，先不會變成另一張 prompt 收藏？

Reference card 不是漂亮的 prompt 模板；它是一條有原因、有範圍的工作判斷。最小一張卡要讓人知道規則是甚麼、為何存在、在哪些工作適用、誰能更新它，以及甚麼時候應重新檢查。

這些欄位令卡片可以被 AI 取用，但不會被當成永恆真理。它也讓你日後看到一條舊 rule 時，能判斷它是仍然有用、只適合某個舊 project，還是應該退休。

**Jimmy 的結論：** Reference card 是下一次工作的判斷提示，不是把所有舊意見永久寫入 AI 記憶。

| 欄位 | 要寫甚麼 | 一個安全例子 |
|---|---|---|
| Rule | 下次先檢查的條件 | 沒有 evidence 時，不寫成已驗證成效 |
| Why | 為何這條規則重要 | 避免流暢 draft 把推論當事實 |
| Scope | 適用哪種工作／讀者 | 需要對外解釋工作成果的草稿 |
| Owner | 誰可確認、修改或退休 | 內容 owner／本輪 reviewer |
| Expiry trigger | 何時應重看 | 讀者、產品、資料來源或政策改變時 |
| Evidence／例子 | 它從哪類 review 觀察長出 | 已去識別化或 synthetic 修改紀錄 |

```text
Rule：＿＿＿＿＿＿＿＿＿＿
Why：＿＿＿＿＿＿＿＿＿＿
Scope：＿＿＿＿＿＿＿＿＿＿
Owner：＿＿＿＿＿＿＿＿＿＿
Expiry trigger：＿＿＿＿＿＿＿＿＿＿
Evidence／例子：＿＿＿＿＿＿＿＿＿＿
```

第一輪只寫一張卡已足夠。若你一開始把所有修改都變成 cards，便會重演 prompt 收藏：數量增加，但下次仍找不到真正重要的判斷。

## 用 internal briefing 示範：哪些修改應留作 rule，哪些只留在這一稿？

假設一份公開資料 internal briefing 被 reviewer 改了三項。第一項是「不要說一定節省時間」；它可能在不同內容裡重複出現，因為成效主張需要 evidence，值得成為候選 rule。第二項是「今次標題改短一點」；它可能只為本輪版面，應留在本次 task context。

第三項是「開頭先說讀者要完成的工作」。若這個修改在多份新手教學都被確認，可以慢慢升成結構判斷；但若下一篇對象已是專家，可能不適用。例子顯示同一個 feedback 的價值取決於原因和 scope，而不是它出現得多大聲。

**Jimmy 的結論：** 不是每個修改都要留；只留下能跨相近工作、又不會錯套到其他情境的判斷。

| Reviewer 修改 | 初步分類 | 下一步 |
|---|---|---|
| 「不要說一定節省時間」 | 重複 pattern 候選 | 寫 evidence／claim boundary card |
| 「今次標題要短一點」 | 一次性 edit | 留在本輪 draft，不升級 |
| 「開頭先說讀者的工作問題」 | 可能的結構 pattern | 觀察下一兩篇新手稿是否仍成立 |
| 「這次寫給技術團隊」 | Changed requirement | 更新本輪讀者與深度，不改全局規則 |

把這個表放在 review 後做，AI 就不只交了一稿；它也讓人留下了下一輪可驗證的工作假設。

## AI feedback 規則怎樣避免污染另一類工作或另一位同事的需要？

一條規則對某類讀者有用，不代表對所有人有用。若你把「新手要先講摩擦」強制套到技術文件，或把某位老闆的一次語氣意見套到所有客戶內容，AI 的 output 反而會愈來愈奇怪，團隊也會不知道誰的偏好才算標準。

Scope、owner 和 expiry 就是防止規則污染的護欄。Scope 說明它在哪裏成立，owner 說明誰可決定是否更新，expiry trigger 讓過時規則不會因為留在 memory 裡就永遠有效。這些不是官僚程序，而是讓共享 context 保持可信的最小安排。

**Jimmy 的結論：** Rule 不應因為被存下來就變成全局真理；它必須有範圍、owner 和退休條件，才可安全重用。

| 容易污染的情況 | 應怎樣寫 scope | 何時重看 |
|---|---|---|
| 新手內容的寫作結構 | 只適用初學者教學文章 | 讀者已熟悉術語時 |
| 某 product 的主張限制 | 只適用這個產品和已批准資料 | 產品、證據或政策更新時 |
| 某 reviewer 的格式偏好 | 只適用這個 deliverable／team | owner 或交付格式變更時 |
| 某次活動安排 | 只適用本輪 task | 活動結束後即退休 |

規則不該變成一把太大的傘。寫清範圍，才能讓 AI 在該用時用、在不該用時不亂套。

## AI feedback rule 何時應該更新、合併或退休？

Context 會隨工作變化。當一條 rule 多次幫你減少相同返工，可以保留；當兩條 rule 其實說同一件事，可以合併成較清楚的核心判斷；當 evidence、讀者、產品或組織要求變了，舊 rule 便需要重新檢查或退休。

不要把「愈多 rule 愈聰明」當目標。大量重複、互相矛盾或沒有 owner 的規則，只會令 AI 和人同樣不知該跟哪一條；好的 library 應該讓每條仍存在的 rule 都有明確工作用途。

**Jimmy 的結論：** Feedback 複利不是無限累積，而是讓有效規則留下、重複規則合併、過時規則能退出。

| 看到的情況 | 做甚麼 | 留下甚麼 |
|---|---|---|
| 同一規則多次被驗證 | 保留並補充好例子 | 穩定 reference card |
| 兩條規則其實同一原因 | 合併，保留較清楚 scope | 一條較強的核心判斷 |
| 規則彼此矛盾 | 拆成不同情境或找 owner 決定 | 範圍說明／停用決定 |
| 讀者、資料或要求已變 | 重新 review 或退休 | 更新日期與新規則 |
| 只出現過一次 | 留在 feedback log | 再觀察，不急住升級 |

每隔幾次同類工作再看一次 cards 已經足夠。重要是有一個能讓舊判斷被挑戰的時機，而不是一寫進去就不再碰。

## 第一次要怎樣由改稿開始，安全地寫一張 AI feedback rule？

找一份低風險、可 review 的 internal draft。不要拿最重要的客戶稿、敏感文件或一段未獲批准的對外內容做練習。先挑一項你已重複改過、也能說明原因的地方，將它填進 reference card，再在下一次相近工作檢查是否真的有用。

練習中不需要把規則寫進任何工具記憶或自動化流程；先放在 task brief 或 project note 旁邊，讓人 review 後決定是否採用。這保留可回退性，也避免一條未成熟規則影響其他工作。

**Jimmy 的結論：** 第一次 feedback rule 的目標不是令 AI 自動學懂你，而是令你下一次能更清楚驗證同一個判斷是否真的成立。

| 第一步 | 你要做甚麼 | 不要做甚麼 |
|---|---|---|
| 選稿 | 選 internal、低風險、已 review 的 draft | 用敏感／未批准文件練習 |
| 選 feedback | 只挑一項真正重複的修改 | 一次過整理十條偏好 |
| 寫卡 | 補 rule、why、scope、owner、expiry | 只寫「唔似我」 |
| 試用 | 在下一個相近任務先檢查 | 直接寫入所有 AI memory |
| Review | 記下 rule 是否仍適用 | 假設一次成功便永遠有效 |

完成這一輪後，若你想逐步把卡片標準化，可讀 [把一條 feedback 變成下次可用的判斷](./練習-turn-feedback-into-a-rule.md)。

## Feedback 變成判斷後，怎樣令下一份 AI 工作真的少重改？

下一份相近任務開始時，不要把整個 feedback 歷史貼進 AI。只帶入這次有關的幾張 reference cards、最新材料和 task brief，並要求 AI 在交付時指出它怎樣遵守這些條件、哪一格仍要人決定。

完成 review 後，再決定這條 rule 是被證明、需要調整、還是不適用。這個短迴路讓 feedback 真正變成 context：每次工作都有機會改進規則，但不會因為舊意見太多而被困住。

**Jimmy 的結論：** 你真正累積的不是修改紀錄，而是一套能在對的任務、對的範圍先幫你少重改的判斷。

| 你下一個卡位 | 接著讀甚麼 | 會留下甚麼 |
|---|---|---|
| 想把規則變成可用卡片 | [把 feedback 變成下一次規則](./練習-turn-feedback-into-a-rule.md) | Reference card |
| 想確認 context 是否可起稿 | [Context 是否 ready to draft](./2-12-is-context-ready-to-draft.md) | Draft-ready decision |
| 想先分清事實和推論 | [生成前先分 evidence 和未知](./2-8-evidence-before-generation.md) | 四欄 brief |
| 同類工作已可交接 | [AI Operator stage](../../03-AI Operator（AI工作操作者）/README.md) | SOP、狀態和例外處理 |

可返回 [AI Super User stage](../README.md) 看其他入口。例子只用公開／synthetic 情境，不代表任何客戶、公司或 DotAI 已取得的成果。
