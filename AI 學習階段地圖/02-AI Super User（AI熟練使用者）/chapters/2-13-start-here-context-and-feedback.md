# 你唔係 Prompt 寫得唔夠長：AI 要見到你做事嘅 Context

你已經用 AI 做過一兩件真工作：叫它寫初稿、整理資料、比較選項，第一眼往往不差；但一到要採用時，又總要自己改一大輪。你換了新 chat，還要重新解釋背景、語氣、哪些資料可信、上次為何不採用某種寫法，彷彿 AI 每次都由零開始認識你。

很多人於是把問題怪到 prompt 太短，開始收集更多「萬能提示詞」。可是字數增加未必讓 AI 更懂你；它真正看不見的，通常是你平日用來判斷好與不好、可說與不可說、已知與未知的材料。沒有那些 context，AI 只能用常見網上模式猜一個像樣答案。

Jimmy 的判斷是：Prompt 只說今次想要甚麼；Context 才讓 AI 看見這件工作可根據甚麼、要避開甚麼、怎樣才算收貨。AI Super User 不是工具收藏家，而是開始把已確認例子、evidence 和修改原因變成下一次可用的工作條件。

| 你每次卡住的位置 | 不是單靠加長 prompt 可解決 | 要留下的 context |
|---|---|---|
| 新 chat 又要重講背景 | 一句更有文采的指令 | task、讀者、可用材料 |
| AI 每次犯同一類錯 | 再補十條即興叮囑 | 修改原因和下次 rule |
| 它把未知寫得很肯定 | 要求它「更準確」 | evidence、unknown、stop line |
| 工具換了又要從頭來 | 追新的 template | 可搬走的 example、review、decision |

## AI Context 是甚麼，為甚麼 Prompt 寫得長仍然會猜錯？

一段 prompt 可以很詳細，仍然可能只是在描述你希望得到的語氣、格式或結果。它未必包含 AI 真正需要的工作依據：哪幾份材料可用、哪幾個舊版本值得模仿、哪些說法仍未確認、這次由誰決定能不能採用。這些東西才會左右 AI 會不會在看似流暢的文字裡偷偷補一個不該補的假設。

Context 也不等於把所有檔案、Drive、Vault 或舊 chat 一次過塞進去。大量不相關材料會令重點更模糊，還可能把不應分享的資料帶入工作。好 context 是貼近今次任務、來源清楚、可被 reviewer 理解的最小材料組，而不是資料量比賽。

**Jimmy 的結論：** Prompt 叫 AI 做一件事；Context 讓 AI 知道它應根據甚麼做、哪些地方不可猜、交回來後誰會收貨。

| 你交給 AI 的東西 | 它能理解甚麼 | 常見限制 |
|---|---|---|
| 「寫得專業但親切」 | 一個抽象語氣 | 它仍要猜你的「專業」是甚麼 |
| 已認可的兩個公開例子 | 結構、語氣和取捨 pattern | 未必知道今次哪些事實可說 |
| 例子＋已批准 evidence＋完成線 | 寫法和本輪可依據內容 | 仍需 human review |
| 例子＋evidence＋unknown＋修改原因 | 方向、邊界和如何改善下一稿 | 不代表 AI 獲得無限記憶或授權 |

當你能分開「今次要它做甚麼」和「它憑甚麼做」，AI 的 output 才開始有穩定可言；否則再漂亮的 prompt 也只是更精緻的猜測。

## AI 每次開新 chat 都要重講背景，最小 task pack 應放哪五格？

最小 task pack 的作用，不是為每一件小工作開一套複雜知識庫，而是把每次都重講的五個條件放在同一個可 review 的位置。它讓你在開新 chat 或換新工具時，仍然可以清楚交代本輪要交甚麼、可看甚麼、什麼才算完成。

若這五格其中一格答不出，先不要用更多材料掩蓋。任務不清楚，便先把「幫我寫好一點」改成可 review 的 artifact；資料未批准，便先問 owner 或只用公開材料；完成線未定，AI 再努力也沒有人知道怎樣算可採用。

**Jimmy 的結論：** 一個好 task pack 不是替 AI 寫長 prompt；它是把一件真工作由模糊願望變成可起稿、可 review 的條件。

| Task pack 格 | 要回答的問題 | 完成後留下甚麼 |
|---|---|---|
| **Task** | 今次交哪一份 draft、analysis 或 plan？ | 清楚 artifact |
| **Allowed material** | 只可根據哪些已批准／公開材料？ | 可追溯 evidence 範圍 |
| **Examples／standards** | 哪兩三個好例子說明「收貨」？ | 可重用 pattern |
| **Review／completion** | 誰看甚麼才決定採用？ | 具體 checklist 與 owner |
| **Unknown／stop** | 資料不足時標記、問人還是停？ | 不由 AI 補成事實的邊界 |

```text
Task：把已批准 workshop outline 變成 internal first draft。
Allowed material：只用公開課程頁、已確認 topic 和兩個公開示例。
Examples／standards：先交代讀者痛點，再給可操作做法；不可聲稱未驗證成效。
Review／completion：內容 owner 檢查事實、語氣和 CTA 後才採用。
Unknown／stop：日期、價格或未批准合作資料一律標待確認，不寫成事實，不外發。
```

你不需要把每一格填到很長。重點是下一位人、下一個 AI chat 和未來的你，都能看得出本輪哪裡已準備好、哪裡仍要人決定。

## AI Context 應放 example 還是 evidence，兩者不分會出甚麼錯？

Example 是讓 AI 看見你喜歡的結構、語氣或表達方式；evidence 則是本輪可以支持某個事實或主張的資料。兩者很容易混在一起：一篇寫得好的舊文未必證明今次的數字或承諾；一份可信來源也未必告訴 AI 要用甚麼語氣、怎樣排段落。

若把 example 當 evidence，AI 可能把舊版本的情況、時間或說法照搬到新工作；若只給 evidence 不給 example，它雖然較不易亂說，卻未必懂你希望的教學節奏和交付形態。把兩者分欄，reviewer 才知道一段內容是「可模仿的寫法」還是「可用作本輪根據的事實」。

**Jimmy 的結論：** Example 教 AI 怎樣表達；evidence 限制 AI 可以說甚麼。兩者都重要，但不能互相冒充。

| 材料類型 | 正確用途 | 不應怎樣用 |
|---|---|---|
| 已認可公開文章 | 參考開場、結構、語氣與深度 | 當成今次所有主張的事實來源 |
| 官方公開頁／一手資料 | 支持本輪已核對的說法 | 直接決定你的獨特觀點或語氣 |
| reviewer 修改紀錄 | 看見何種表達不會收貨 | 當成永遠不變的硬規格 |
| 未確認截圖、轉述或私人資料 | 先標 unknown 或留在受控流程 | 偷塞進公開稿或叫 AI 自行驗證 |

把 materials 分好，AI 不是因此變得「永遠正確」，而是每個結論都更容易被人追問、核對和改正。這才是可持續的 context。

## AI 把不確定資料寫成事實時，unknown 應怎樣留在 Context？

AI 的流暢語言很容易掩蓋未知：某個日期尚未確認，它仍可寫得像已定；某個數字只有舊版本，它仍可寫得很有信心。這類問題不能只靠一句「要準確」處理，因為它真正缺的是本輪哪些東西可說、哪些只能列作待確認的明確邊界。

在 task pack 裡留下 unknown，不會令文章變弱，反而讓 internal draft 有用。AI 可以先整理已知結構、把未確定項放在顯眼欄位、說明少了哪份 evidence；owner 再選擇補資料、改範圍或停止。這比要求它硬寫一份「完整」版本更快找到真正要決定的事。

**Jimmy 的結論：** Context 完整不代表沒有 unknown；它代表 unknown 不會被 AI 靜靜補成一句肯定說法。

| 發現的缺口 | AI 本輪可以做甚麼 | 人要保留甚麼 |
|---|---|---|
| 日期未確認、只需先看結構 | 在對應欄位標待確認，起 internal draft | 確認真正日期 |
| 價格、offer 或對外承諾未批准 | 列出會受影響的位置 | 決定可否提供／使用 |
| 公開背景需要一手資料 | 整理需要查證的問題 | 決定來源是否足夠 |
| 涉及權限、客戶或敏感內容 | 停止並寫 unblock list | 批准、拒絕或提供安全替代 |

只要 unknown 有正確去路，AI 仍然可以幫你前進；沒有去路的 unknown，則不應被一段漂亮文字蓋過。

## AI feedback 怎樣由一次改稿，變成下一次可用的 Context rule？

每次你在 AI 初稿上改字，未必都值得變成規則。有些是今次受眾、情境或材料獨有的選擇；有些卻反覆出現，例如 AI 每次都太早下結論、漏寫 evidence、把待確認寫成已完成。若修改原因只留在你腦裡，下一個 chat 只會再犯一次。

把 feedback 變成 rule 的重點不是記錄「改了哪幾個字」，而是寫清「原本哪個判斷不對、為何不收貨、下次應怎樣檢查」。先把它放在本類工作 task pack 的 review 標準；只有多次證明它真的穩定，才升成較長期的 Skill 或 team rule。

**Jimmy 的結論：** 有價值的 feedback 不只是今次修好 output；它要令下一次 AI 和人都少猜一次「為甚麼這樣不收貨」。

| 改稿觀察 | 不夠好的紀錄 | 可重用的 context rule |
|---|---|---|
| AI 一開場便下結論 | 「開頭不好，改順一點」 | 先列 evidence 或工作情境，再寫判斷；資料不足要標 unknown |
| AI 用了太大的成效說法 | 「不要誇張」 | 沒有可核對 evidence 時，不可把推測寫成成效或承諾 |
| AI 漏掉一個固定欄位 | 「下次記住加」 | 每份 brief 交前檢查：目的、材料、unknown、owner、下一步 |
| 今次只是想換較輕語氣 | 「改口語」 | 留在本輪，不要錯升成所有文章規則 |

三次左右仍然出現的 pattern，才值得變成更穩定的 rule。這樣 context 會愈來愈準，而不會被一次性的喜好塞到越來越肥。

## AI 想愈用愈似你，為甚麼不應該把全個 Vault 交出去？

一聽到「AI 要懂我」，很多人第一反應是把所有舊檔、會議、訊息和筆記放進同一個資料庫。這樣不只增加私隱和權限風險，也會令 AI 難以分辨哪些是目前仍有效的標準、哪些只是過期想法、哪些根本不屬於今次工作。更多 context 不等於更準確 context。

較成熟的做法是分層：source 留作證據與原始記錄；本輪 task pack 只取已批准、貼近工作的部分；feedback rule 記錄可重用的判斷；長期 Skill 只收已經跑穩的流程。每一層都有 owner 和更新節奏，AI 才不會把舊資料當新指令、把私人材料當公開材料。

**Jimmy 的結論：** AI 不需要知道你所有事情；它只需要在當前工作看見足夠、可信、被允許的 context。

| 層次 | 放甚麼 | 不應直接當作 |
|---|---|---|
| Source | 原始公開資料、已批准文件、可追溯 evidence | 永遠正確的工作規則 |
| Task pack | 本輪相關材料、例子、完成線 | 無限期共享的總資料庫 |
| Feedback rule | 多次出現的修改原因與檢查 | 一次性喜好或未驗證意見 |
| Skill／runbook | 已跑穩的步驟、例外、quality gate | 未試過的自動化承諾 |

這種分層讓你可以慢慢累積自己的判斷，同時保留「哪裡不該給 AI 看、何時規則應失效」的控制權。

## AI Super User 應怎樣挑一個 Tier-1 工具，而不是不停換工具？

工具會換、模型會更新，但同一類工作若每次在不同 app、不同設定和不同 chat 歷史裡完成，你很難知道成果改善是因為模型、材料、workflow 還是運氣。先為一種常做工作選一個預設入口，不是要你永遠只用一個工具，而是讓學習有一個可比較的基準。

例如你想練習整理公開資料，可以先固定在一個可保存 task pack、可回看輸出和 review 的工作台；想練習內部 draft，則選一個能清楚分開材料和 output 的入口。當工具真的不適合時，再用同一份 task pack 比較另一個工具，而不是把舊工作記憶丟掉後重新猜。

**Jimmy 的結論：** Tier-1 工具不是「最強 app」；它是你暫時用來把同一類工作做深、做得可比較的預設入口。

| 你要做的事 | Tier-1 工具應至少做到 | 換工具前先問 |
|---|---|---|
| 公開資料整理 | 可帶入來源、保留 output、方便核對 | 是工具問題，還是 task pack 未清？ |
| 文稿起草與 review | 可分開 examples、evidence、修改意見 | 我是否仍能用同一套完成線？ |
| workspace 小改動 | 可讀 scope、顯示差異、跑檢查 | 有沒有可回退與 owner review？ |
| 重複 routine | 可留下 state、exception 和 receipt | 工作真的已穩定到值得 automation？ |

當你先把工作方法固定，工具比較才有意義。否則你只是把同一個 context 缺口帶去下一個新 app。

## AI Context 和 feedback 做得好後，下一個安全動作是甚麼？

先選一件低風險、下星期可能又會再做的工作，完成一次 task pack。不要一開始整理全個 Vault，也不要因為有了 context 就立即接 CRM、外發或自動更新系統；先觀察 AI 是否真的根據材料起稿、未知是否有露出、reviewer 是否能快速說明要改甚麼。

第二次做同類工作時，再回看上一輪哪個 feedback 值得保留。若它只是一次性選擇，留在那一稿；若它反覆影響品質，就寫成 review rule。這一小步已經是 AI Super User 的核心能力：把一次使用變成下一次少猜一次，而不是只累積更多 chat。

**Jimmy 的結論：** Context 和 feedback 的完成線，不是建了一個很大的知識庫；是下一次同類工作可以更快對齊、少犯一個已知錯誤。

| 你現在卡住的位置 | 接著讀甚麼 | 會留下甚麼 |
|---|---|---|
| 想即刻填第一份材料與完成線 | [五格組一個 AI task pack](./練習-build-an-ai-task-pack.md) | 可 review task pack |
| 不知道資料缺口要起稿、問人還是停 | [資料未齊唔等於要停](./2-12-is-context-ready-to-draft.md) | draft-ready decision |
| 想把已認可例子和回饋累積起來 | [由收集 prompt 到 context 複利](./2-2-context-compounding.md) | 可重用 context |
| 同類工作已穩定重複 | [AI Operator stage](<../../03-AI Operator（AI工作操作者）/README.md>) | SOP、state、exception |

可返回 [AI Super User stage](../README.md) 看其他入口。這是 Jimmy 的公開工作方法；它不代表任何模型已記住你的私人資料，也不構成資料存取、外發、系統寫入或 production action 的批准。
