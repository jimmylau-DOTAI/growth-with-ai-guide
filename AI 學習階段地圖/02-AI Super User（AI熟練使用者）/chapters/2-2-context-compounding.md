# AI 學習點先唔係只收藏 Prompt？用 Context 同 Feedback 令每次工作累積

你可能已儲了很多 prompt、看過很多工具教學，但每次開新 chat 仍然要重新講背景、重新改同一種錯。工具越換越多，真正影響結果的例子、標準和修改理由卻仍然困在上一次對話裡。

加長 prompt 有時會改善當次 output，但它不能自動帶走你已接受過的成品、哪些資料可信、哪些修正反覆發生。於是每一件工作都像新的，review 仍然靠你在最後一刻逐句補回自己的判斷。

Jimmy 的判斷是：AI 學習的分水嶺，已由「識點問」走到「能否將資料、範例、標準和 feedback 回收成下次可用的 context」。不是把 AI 訓練成你，而是讓下一次工作不必由零猜你的要求。

| 你現在的習慣 | 容易留下的問題 | AI Super User 要留下甚麼 |
|---|---|---|
| 儲一堆網上 prompt | 句子不一定適合你的工作 | 已確認的工作範例與條件 |
| 改完 AI draft 便關 chat | 相同錯誤下次重現 | 修改原因和有範圍的規則 |
| 把所有舊資料塞進 AI | 重點和事實混在一起 | 最小 context pack 與 evidence |
| 不斷換新工具 | 沒有一種做法被練深 | 一件重複工作跑兩三次的比較 |

## Prompt collection 點解不會自然令 AI 越用越準？

Prompt 很適合把今次要求說出來，但網上收藏的 prompt 往往承載的是別人的場景、語氣和驗收標準。即使它寫得很好，也不會自動知道你的讀者、你接受甚麼例子、你的資料來源是否可靠，或你上次為何把某段改掉。

更重要的是，AI 不會因為你上次改過一份 draft，就自然把那個修改帶到下一次。若沒有把已確認的範例和修正理由留在可重用位置，每次新工作都仍然要由人重新補回背景和判斷。

**Jimmy 的結論：** prompt 是一次工作的入口；真正可累積的是你已確認過的範例、標準和修改原因。

| 你儲的是甚麼 | 下次能否直接幫到 | 原因 |
|---|---|---|
| 一條網上「萬用 prompt」 | 未必 | 沒有你的材料、讀者和完成線 |
| 一份你已 review 過的 briefing | 較可以 | 可看見格式、欄位和接受過的選擇 |
| 一次被拒絕的 draft 加上原因 | 很有用 | 說清哪些邊界不能再踩 |
| 一句「太硬／唔似我」 | 很難 | 沒有把感覺翻成可操作規則 |

不是要丟掉 prompt，而是把 prompt 放回正確位置：它負責開工；你的 context 和 feedback 才令後續工作有可依據的標準。

## AI context 點樣設計？用範例代替模糊形容，但不要把所有資料塞進去

人很多時知道自己「喜歡甚麼」，卻未必能用一句精準指令說出來。例如你可以看出一份 briefing 太長、太像宣傳、太早下結論，但很難一次寫出所有細微規則。這時，少量已確認過的範例比堆疊形容詞更有幫助。

不過範例不是越多越好。三至五個目的一致、來自安全來源的例子，通常比三十個互相矛盾的舊檔更容易讓人和 AI 找到一致模式。任何範例都要有用途、權限和範圍，不應因為「可以幫它理解」就把整個 vault 或所有歷史工作交進去。

**Jimmy 的結論：** 好 context 不是資料多，而是有足夠例子讓 AI 看見模式，同時保留清楚的材料範圍和停止線。

| 模糊要求 | 有用的 context 設計 | 你在教 AI 看甚麼 |
|---|---|---|
| 「寫得專業又親切」 | 三封已批准、適合同類讀者的公開／安全 email 範例 | 語氣、長度、開場與收尾方式 |
| 「做一份好 proposal」 | 已批准的結構、欄位與公開服務描述 | 故事順序、必含內容、不可承諾內容 |
| 「不要寫得太 sales」 | 一段被拒絕的 synthetic 範例＋拒絕原因 | 哪種說法越過了界線 |
| 「整理得清楚」 | 一張已確認的 briefing 表格 | 欄位、未知標記與 review 次序 |

範例只能幫你看見模式，不能替代本輪 task brief。每次仍要說清今次讀者、可用材料、完成線和這次有沒有例外。

## AI context、evidence、reference 有咩分別，點解要分開存？

Context 是 AI 今次理解工作所需的材料和限制；evidence 是你可以用來核對事實的根據；reference 則是有用做法、語氣或結構的參考。它們可能看起來都是「資料」，但混在一起會令 AI 和讀者分不清哪些可以當真、哪些只是一個方向、哪些只是過去的例子。

尤其使用舊 project、舊 chat 或外部文章時，不要把它們全部升格成當前事實。AI Super User 的習慣是把本輪可引用的 evidence、可模仿的 example、仍待確認的 assumption 分開，這樣才能更新其中一格而不破壞整份工作。

**Jimmy 的結論：** 把資料分類不是為了建一個很大的庫，而是讓每一次 AI 工作知道甚麼可作根據、甚麼只可作參考、甚麼仍然未確認。

| 材料位置 | 它回答的問題 | 例子 |
|---|---|---|
| Context | AI 今次可以看甚麼、為誰做？ | 指定三段公開材料、目標讀者、輸出欄位 |
| Evidence | 哪些主張能被核對？ | URL、日期、已批准事實、原始公開文件 |
| Reference | 有甚麼可借鏡的形式或做法？ | 已確認的表格格式、匿名 synthetic 範例 |
| Feedback rule | 下次遇到同類情況要怎樣做？ | 資料不足一律標待確認 |
| Assumption／未知 | 哪些不應被寫成事實？ | 讀者背景尚未確認、資料日期不完整 |

這個分法令 AI 不會把「一個舊例子」當成今日承諾，也讓你在日後要改材料時，知道應改 evidence 還是只改 reference。

## AI feedback 點樣複利？先把初稿與 final 的差異變成可用判斷

每次你把 AI 初稿改成 final，其實都做了一次判斷：哪一段不準、哪一個欄位缺失、哪一句不適合讀者、哪一個未知不能被寫成肯定。若只是改完便交出，下一次你仍要做同一輪判斷。

要讓 feedback 發揮作用，不是把所有修改一律變成永久規則。先把初稿、final 和修改原因放在一起看，找出真正重複、能說明原因、並有清楚適用範圍的部分；一次性的例外則只留在該次任務。

**Jimmy 的結論：** AI 越用越貼近你的工作方式，不是因為它自然記住，而是因為你把重複判斷回收成下一次可讀的規則。

| feedback 流程 | 人要做甚麼 | 留下甚麼 |
|---|---|---|
| 1. AI 起初稿 | 不急住逐句插話 | 一份可比較的初稿 |
| 2. 人完成 review | 改正事實、結構、語氣或欄位 | 一份 final／reviewed draft |
| 3. 比較差異 | 寫出改了甚麼、為甚麼 | 修改紀錄 |
| 4. 判斷是否重複 | 區分一次性例外和穩定偏好 | 候選規則 |
| 5. 寫成 reference card | 補原因、適用範圍、owner／到期檢查 | 下次可用規則 |

```text
初稿的問題：＿＿＿＿＿＿＿＿＿＿
我改成甚麼：＿＿＿＿＿＿＿＿＿＿
為甚麼這樣才較合用：＿＿＿＿＿＿＿＿＿＿
這條規則適用於：＿＿＿＿＿＿＿＿＿＿
不適用／需另判斷的情況：＿＿＿＿＿＿＿＿＿＿
```

這一步讓你由「我覺得唔啱」走到「下次能先檢查這個條件」。可用 [把 feedback 變成規則](./練習-turn-feedback-into-a-rule.md) 將其中一條寫成完整 reference card。

## 「好例子」和「被否決的例子」怎樣一起幫 AI 看清邊界？

只給好例子，AI 可能學到大概風格，但仍不知道甚麼看似相似卻不適合。被否決的版本若配上原因，可以揭示邊界：是事實未確認、語氣過分承諾、格式不利 review，還是它根本不適合今次讀者。

但不要把任何舊 output 一律塞進 context。被否決的例子必須先去除敏感資料，並要寫清楚拒絕的是哪個元素；否則 AI 只會看到兩個互相矛盾的文本，卻不知道甚麼模式應該避免。

**Jimmy 的結論：** 「不要甚麼」只有連同原因才是有用 context；沒有原因的反例只會令標準更混亂。

| 範例類型 | 可以教到甚麼 | 要加上的說明 |
|---|---|---|
| 已接受版本 | 可用結構、格式、節奏 | 為何適合同一類讀者／工作 |
| 被否決版本 | 不可跨過的邊界 | 被拒絕的具體原因與適用範圍 |
| 修改前後版本 | 人手判斷如何改變結果 | 差異和修改理由 |
| synthetic 反例 | 在不暴露真資料下練常見錯誤 | 這是練習，不是真實客戶結果 |

有好例子加上乾淨反例，AI 和人都更容易看見工作標準。重點不是收藏更多文件，而是挑出能回答「為何可用／為何不可用」的 evidence。

## Context 太多會不會反效果？何時不應該急住建立標準庫？

會。當一件工作只做一次、標準仍在探索、或範例彼此矛盾時，硬把它們收進「永久 context」只會令下一次更難判斷。此時最合理的做法，是為今次寫一個小 task brief，並把未知保留為未知。

同樣地，不要因為有了一堆筆記就假設它們適合交給 AI。任何 context 都應有工作用途、權限和更新理由；沒有清楚用途的收藏，應留在參考，而不是變成每次 AI 都要讀的材料。

**Jimmy 的結論：** Context 複利只發生在重複、已 review、範圍清楚的工作上；探索期的材料應該保持輕量和可變。

| 看到的情況 | 現在先做甚麼 | 暫時不做甚麼 |
|---|---|---|
| 只做一次的任務 | 寫清當次 brief | 建永久 template |
| 你自己標準未定 | 多跑幾次、留修改紀錄 | 把一次偏好鎖成全局規則 |
| 範例互相矛盾 | 分析為何不同、標示適用情境 | 一次過塞入 AI 叫它自行猜 |
| 有很多舊檔但用途不明 | 先挑本輪最小材料 | 把整個資料夾當 context |

知道不急住存甚麼，是避免 context 變成雜物房的關鍵。先讓規則被真工作驗證，再決定是否值得保留。

## 不用建 vault 或自動化，點樣由兩行紀錄開始累積 AI 判斷？

你不需要先建一個巨大知識庫，才可以開始 context 複利。選一件你每星期或每月都會做、又能安全起 draft 的工作；每次完成 review 後，只記下 AI 交了甚麼、你改了甚麼、為何改。

三次之後再回看。若同一個改動重複出現，才把它升成有範圍規則；若每次都不同，它可能只是這次情境的例外。這種低成本紀錄讓你的標準從真工作長出來，而不是從一開始便假裝自己已知道所有答案。

**Jimmy 的結論：** 最小的 context system 不是一個新工具，而是一條能把 review 後判斷留到下一次的紀錄習慣。

```text
日期／工作：＿＿＿＿＿＿＿＿＿＿
AI 初稿交了甚麼：＿＿＿＿＿＿＿＿＿＿
我改了甚麼：＿＿＿＿＿＿＿＿＿＿
為甚麼要改：＿＿＿＿＿＿＿＿＿＿
下次是否應沿用：是／否／再觀察
```

把這五行放在你平日找得到的地方即可。當你確定一條模式真的出現，才把它寫進 task brief 或 reference card；先不要為它買系統、連工具或建立大量分類。

## Context 複利完成後，怎樣走向可重用的 AI 工作方式？

當你做過兩三次同類工作，能區分穩定規則、本輪材料和例外，便可以把較穩定部分整理成 context pack。它不需要包辦所有知識，而是讓下一次任務能快速拿到已批准範例、evidence、驗收和停止線。

只有當工作已重複、輸入輸出可預測、例外有處理方式，才值得往 AI Operator 的 SOP 和狀態管理走。若現在仍然每次都在探索，留在 task brief 和 feedback 迴路反而更快，因為你還在學真正的工作條件。

**Jimmy 的結論：** AI Super User 的成果不是一本 prompt 大全，而是一個越做越清楚的 context 和 feedback 回路。

| 你已經做到 | 下一個動作 | 應留下甚麼 |
|---|---|---|
| 有一次安全 draft | [把答案變成 task brief](./2-1-from-answers-to-real-work.md) | 第一份可重跑 brief |
| 有三次修改紀錄 | [把 feedback 變成判斷](./2-9-feedback-into-judgment.md) | 一條有範圍 reference rule |
| 有一致範例和驗收方式 | [確認 context 是否 ready to draft](./2-12-is-context-ready-to-draft.md) | 一個最小 context pack |
| 工作已可重複交接 | [AI Operator stage](../../03-AI Operator（AI工作操作者）/README.md) | SOP、狀態與例外處理 |

可返回 [AI Super User stage](../README.md) 看其他入口。例子只用公開／synthetic 情境，不代表任何客戶、公司或 DotAI 已取得的成果。
