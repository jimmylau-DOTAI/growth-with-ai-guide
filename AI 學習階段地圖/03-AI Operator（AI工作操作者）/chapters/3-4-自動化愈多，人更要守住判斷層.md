# AI 做得愈多，人應該做乜？專業判斷在 workflow 的控制層

當 AI 可以起草、整理、比對、改格式甚至執行一連串操作時，很多人會問：「咁人仲要做乜？」最常見的答案是「做人類才有的創意」或「提升策略」，但這些說法太抽象，不能幫你在下次真工作裡判斷哪一段可交、哪一段要保留。

真正的轉移不是人突然不用做事，而是部分執行工作可以交出去後，問題定義、context、限制、驗收、例外處理與責任變得更重要。這些工作以前可能隱藏在熟手的經驗裡；現在若沒有被寫清，AI 便會很快執行一個其實未被正確定義的方向。

Jimmy 的判斷是：人的專業價值不會自動「升級」，而是要刻意練成 workflow 的控制層。控制層不是坐在旁邊看 AI，而是決定這次要解甚麼、甚麼不能錯、何時可收貨、出錯後要怎樣安全回復。

| 控制層位置 | 人要決定甚麼 | AI 可協助甚麼 |
|---|---|---|
| 問題與目標 | 今次真正要交甚麼 | 追問、整理選項、起草 |
| Context | 哪些資料可信、哪些未知 | 分類、摘要、找缺口 |
| Constraints | 不能做甚麼、權限在哪裡 | 對照規則、標出違反 |
| Verification | 甚麼才算可用 | 跑 checklist、列出不確定 |
| Recovery | 出錯先回哪一格 | 保存狀態、提出下一輪問題 |

## AI 幫你做得快，點解人反而更要先定義問題？沒有目標的執行只會更快偏離

AI 最擅長把已交代清楚的工作推進。但如果你只說「幫我整好」「研究一下」「寫專業啲」，它便要自己補上目標、受眾、完成線與權衡。結果可能看起來很流暢，卻不一定幫到任何人作決定；人只好在最後重新收拾。

問題定義是控制層的第一個工作，因為它決定後面所有 context、工具和驗收該為甚麼服務。這不是要先寫一份大策略，而是把眼前一件工作講成他人或 AI 都能看懂的成果。

Jimmy 的結論是：AI 能加速執行，但不能替你決定甚麼值得完成；目標不清時，最快的 output 也可能是最快的浪費。

先把模糊要求改成四格：

| 模糊說法 | 控制層要補的問題 |
|---|---|
| 「幫我研究一下」 | 為誰回答哪個問題？需要事實、比較還是問題清單？ |
| 「幫我寫篇文」 | 讀者卡在哪、應帶走哪個判斷、可交甚麼 draft？ |
| 「幫我自動化」 | 哪一段重複、input／output 是甚麼、誰收貨？ |

這四格寫清後，才交 AI 做一小段可 review 的執行。人保留的是目的與取捨，不是每個按鍵動作。

## Context 同 constraints 點樣令 AI 不會好心做錯事？讓它知道可以根據甚麼、不能越過甚麼

一個 agent 或 AI 工具拿到任務後，若沒有清楚材料範圍，很容易把過期內容、未確認說法或不應使用資料混進 output。若沒有 constraints，它也不知道哪些動作需要人手 approval，哪句話不能作承諾，甚麼情況應該停而不是繼續補寫。

context 與 constraints 不只是「多給一點 prompt」。前者說明可用的事實、例子和工作狀態；後者說明禁區、權限和停線。兩者都是人把專業判斷翻譯成 AI 可遵守工作條件的方式。

Jimmy 的結論是：專業不是把所有答案背在腦裡，而是知道哪一份 context 會改變決定、哪一條界線不能交給 AI 猜。

| 類型 | 應寫甚麼 | AI 的正確反應 |
|---|---|---|
| Context | 已批准資料、受眾、現行 source of truth | 只按這些資料整理／起稿 |
| Constraint | 不可新增事實、不可外發、不可讀敏感資料 | 標未知、停在 draft、回問 owner |
| Authority | 誰確認材料、誰批准 output | 交回 reviewer，不自行決定 |

當 AI 遇到資料不足而能標 `blocked`，那不是它做得少；那是控制層成功防止一個看似完整但不可信的 output。

## Verification 點樣唔止靠「我覺得唔錯」？先把收貨條件寫成看得見的檢查

人手 review 很容易變成主觀感覺：這版「順啲」、那版「好似唔係我想要」。這些感覺可以是真的，但若沒有拆開原因，AI 下次無法知道應改甚麼，同事也不能一致地收貨。控制層只在最後看一眼，並不能令 workflow 可靠。

verification 的工作，是在執行前先說清楚哪些條件必須成立。它可以包括材料是否可追溯、格式是否完整、未知是否標示、output 是否服務原本目標、是否越過了權限。這讓 review 成為一個可重複的判斷，而非每次重新投票。

Jimmy 的結論是：驗收不是 AI 做完後才加的一關；它是你一開始便要交代給 workflow 的完成定義。

一張最小 acceptance checklist 可有：

1. output 是否解決約定的工作問題；
2. 是否只使用批准材料，未知是否清楚；
3. 格式、欄位與範圍是否合格；
4. 是否已交給正確 reviewer；
5. 有沒有任何一項觸發 stop line。

這些項目不會取代專業 judgment；它讓 judgment 有地方落，並能在下一輪被回收成 rule。

## AI 出錯後怎樣處理才不是一直 retry？Recovery 要先找最早失效的一格

AI 出錯時，最容易的反應是「再試一次」或「換個 prompt」。有時這會剛好成功，但你不知道問題究竟是資料不齊、目標太闊、constraint 未寫、驗收太弱，還是工具本身不適合。retry 愈多，歷史愈長，真正的 failure mode 反而更難找。

recovery 是控制層的另一半：不是誰要為失敗負責，而是回到工作地圖找最早開始不成立的位置。只要修一格並再跑一次，你才能得到可用 evidence；同時換五件事，只會令下次又要靠感覺。

Jimmy 的結論是：有控制層的 workflow 不怕出錯；它怕的是出錯後沒有人知道應從哪一格回去修。

| 症狀 | 先回看哪一格 | 下一步 |
|---|---|---|
| output 離題 | 目標／受眾 | 收窄 task brief |
| 事實混亂 | input／source of truth | 清理材料，標未知 |
| 越界或過度承諾 | constraints／authority | 加 stop line，交回 owner |
| 每次格式不同 | acceptance／SOP | 寫可檢查欄位 |
| 同類錯誤反覆出現 | recovery rule | 一次只修一格再測 |

這個表的目的不是把所有問題歸咎於人或 AI，而是讓故障變成一個可被工作系統吸收的信號。

## 人和 AI 怎樣分工先不會假裝 agent 可以自己負責？執行權跟決策權要分開

一條 workflow 裡，AI 可以做很多執行：整理資料、產生 draft、按 checklist 找漏項、將同一內容轉成不同格式。但「做得到」不等於「應該自己決定」。當一個結果會影響外部承諾、敏感資料、例外處理或重要取捨時，必須有人保留 authority。

這種分工不是把 AI 當低級助手，也不是把人永遠困在微管理。它是讓每一方做自己能被合理驗證的部分：AI 快速執行明確任務；人決定問題、邊界、驗收與不可逆行動。越清楚的分工，越容易知道何時值得增加 AI 的責任。

Jimmy 的結論是：人的控制層不是「做 AI 做不到的所有事」，而是保留需要判斷、驗收與承擔後果的決定。

| 環節 | AI 可做 | 人必須保留 |
|---|---|---|
| 問題定義 | 提出澄清問題 | 決定目標與優先次序 |
| Context 整理 | 摘要、分類、標缺口 | 決定可信來源與可用範圍 |
| 執行 | 起稿、轉格式、跑規則 | 決定是否適合今次情況 |
| Verification | 對照 checklist | 最終 review 與收貨 |
| Recovery／責任 | 列出失敗可能、保留狀態 | 取捨、例外、外部／不可逆決定 |

當你能清楚指出每一格的 owner，AI 才真的有空間幫你做更多；否則所謂 autonomous 只是在隱藏責任未定義。

## 用公開 briefing 跑一次：控制層怎樣令 AI 起稿不等於自動完成

以下是 synthetic 例子。假設你要把指定公開材料變成 internal briefing，目標是讓 owner 有一頁可以 review 的摘要，不是直接對外傳送。人先定好受眾、可用材料、未知標示規則、格式和 reviewer；AI 只負責在這些條件內整理第一稿。

output 出來後，reviewer 對照 acceptance 看來源、未知、格式與是否越界。若一條材料矛盾，AI 不應自己選一個版本，而是標 `blocked`，由 owner 決定。這樣一條小工作已經包含控制層的完整形狀。

| 控制點 | 本輪做法 |
|---|---|
| Goal | 一頁可 review internal briefing |
| Context | 指定公開 URL 與已批准格式 |
| Constraints | 未知要標示；不可新增數字；不可外發 |
| Verification | 三重點、兩未知、來源欄、owner review |
| Recovery | 資料矛盾即 `blocked`，回到 input owner |

Jimmy 的結論是：AI 在這裡做的是受控執行；真正的專業在於人已先把值得交、不可交和怎樣收貨的判斷放進 workflow。

這不代表所有工作都要先建立完整控制系統。對一次性、低影響探索，簡單對話已經足夠；工作愈重複、愈接近外部影響，控制層才愈值得寫清。

## 今日怎樣練控制層？在一件小工作先寫 Goal、Context、Constraints、Verification、Recovery

控制層不會因為你多用 AI 自動出現。最實際的練習，是選一件低風險、可回退工作，把原本藏在腦裡的判斷寫成五格；然後只叫 AI 做其中一段。這會立即暴露你其實還未定義甚麼，或哪個 acceptance 仍然太模糊。

開始時不必把五格都寫得很複雜。只要另一位人或新 session 看完後能說出：今次要交甚麼、能讀甚麼、不能做甚麼、誰收貨、錯了怎樣停，這條工作已經比「幫我做好」更適合交出去。

Jimmy 的結論是：AI 愈能執行，人愈要把專業變成可見的控制點；否則速度只會放大原本的模糊。

第一次請做：

1. 為一件低風險工作寫一句 Goal；
2. 列出兩項可信 Context 與一項 Unknown；
3. 寫兩條 Constraint 和一條 stop line；
4. 定三項 Verification，再交 AI 起一個 draft；
5. 若出錯，只回到最早失效的一格修一次。

要把五個控制點放入更清楚的工作地圖，可讀 [明明每星期都做，點解仍然交唔到畀人或 AI？](./3-6-重複工作交不出去，先畫工作地圖.md)。若你想學怎樣在跑完後逐格修正，可讀 [一條 routine 跑完，下一步改甚麼？](./3-10-一條流程跑完，下一步怎樣改.md)。
