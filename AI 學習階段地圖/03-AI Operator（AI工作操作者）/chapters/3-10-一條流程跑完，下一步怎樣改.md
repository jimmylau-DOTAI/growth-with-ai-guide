# 一條 routine 跑完，下一步改甚麼？不要大改，先找一格真正的摩擦

一條重複工作跑完，最常見的結論是「好像做完了」或「又要重做」。這兩句都不足以讓下次變好：你不知道是 input 未齊、標準不清、owner 太遲接手、例外沒有停線，還是工具真的不適合。於是下一輪很容易同時換 prompt、換工具、換資料和換人，最後更難知道哪件事起作用。

一次 output 看似順利，也不等於流程健康。可能只是某位熟手默默補救、材料剛好完整，或問題還未遇到。若沒有留下 run evidence，下次出事時，團隊只會把一條工作問題簡化成「AI 不準」或「換個工具吧」。

Jimmy 的判斷是：routine review 不檢討誰做錯，而是找一條真 run 裡最早不成立的一格，下一輪只修一個可驗證的原因。改善的單位不是大翻新，而是看得見的摩擦、清楚的 owner，和一個有邊界的改動。

| Review 位置 | 要問甚麼 | 留下甚麼 |
|---|---|---|
| Run evidence | 這次由哪個 state 走到哪裡？ | 可回看的事實 |
| Friction | 哪裡停、返工或要人補救？ | 一句工作摩擦 |
| 分類 | 是 input、standard、owner、exception 還是 context？ | 最早失效位置 |
| Bounded change | 下輪只改甚麼？ | 一個可驗證改動 |
| Owner review | 誰批准、下次看甚麼？ | 下一輪判斷 |

## Output 交咗，點解仍然未必代表 routine 健康？先留 run evidence，不要只留感覺

一份 output 最終被收貨，可能掩蓋很多事情：owner 在最後一刻補資料、同事手動修正格式、AI 第三次才剛好答對。若 review 只看最後版本，就會錯過真正令流程不穩的位置；下一次條件一變，同一問題便會重來。

run evidence 不需要變成員工監控或複雜 dashboard。它只要讓人看見這次工作從哪個 state 開始、在哪裡停、用了甚麼已批准材料、誰作了關鍵決定，以及最後 output 怎樣被收貨。這些事實足夠讓你不必靠印象開會。

Jimmy 的結論是：沒有 run evidence 的改善，只是在為下次猜一個較好的做法；有 evidence 才能知道該修哪一格。

每次 run 最少留下：

1. 起點 state 和真正 trigger；
2. input 是否完整、哪一項曾經缺失；
3. output 第一次可 review 前經過幾次退回；
4. 出現哪種 exception、誰最後處理；
5. 最終是 closed、blocked，還是只靠補救才完成。

這些資料不用精確到分鐘。它的用途是讓下一輪能問出正確問題，而不是證明誰表現好或不好。

## 同一個「做得唔順」點樣分類？不要直接把所有問題叫做 AI 不準

AI output 不合格時，很容易直接歸因於模型：它不懂、它亂答、它不穩。但同樣的表面症狀可以由完全不同原因造成。兩份資料版本不同，問題是 context；output 格式不對，可能是 standard；一直沒人看，可能是 owner；資料不足仍繼續，則是 exception 沒有停線。

把摩擦分類不是為了建立很多標籤，而是避免你用錯藥。只有知道哪一格先壞掉，下一輪的一個改動才有機會被驗證。這也讓 AI 在需要時標示問題，而不是硬把缺口填滿。

Jimmy 的結論是：一個好 review 的第一個成果，不是「找到誰的錯」，而是把模糊失敗翻成一格可以修的工作條件。

| 摩擦類別 | 常見表面現象 | 下一輪先檢查甚麼 |
|---|---|---|
| Input／context | 不同版本講法矛盾 | current reference 是否唯一、最新 |
| Standard | output 每次格式不同 | acceptance 有沒有可檢查欄位 |
| Owner | draft 一直等、最後急改 | 誰能 review／決定有沒有寫清 |
| Exception | 資料不足仍照產出 | 何時 `blocked`、交回誰 |
| Tool／setting | 同一張卡反覆漏同一規則 | 先用同條件再測一次 |

分類後，先挑最早讓工作偏離的一格；不要因為後面看到十個問題，就同時對十格開刀。

## 點解每次都大改反而學唔到？Bounded change 令下一輪有得比較

當一輪出事，很多人會想一次過修好：加更多 context、換工具、改 prompt、增設 checklist、換 reviewer。這些改動各自可能合理，但一起發生時，下一次即使變好，也沒有人知道是甚麼真正改善了；若變差，也不知道應回退哪一項。

bounded change 是刻意把下一輪縮小：只選一個已見到的摩擦，改一條工作條件，其餘盡量保持一樣。這不是拖慢進步，而是讓一次 run 真的能產生下一輪可用的 evidence。

Jimmy 的結論是：流程改善不是一次過大改，而是每次根據看得見的摩擦修正一格。

一個 bounded change 要寫四句：

| 欄位 | 例子 |
|---|---|
| 摩擦 | briefing 有兩份 agenda，AI 用錯版本 |
| 假設 | 若指定唯一 current reference，重做會減少 |
| 本輪只改 | 加一個 version owner check |
| 觀察 | 下一輪是否仍出現版本衝突／需重做 |

若你發現要同時改三件事，先把工作再拆小。能被比較的一次小修，比一個無法解釋的大翻新更接近真正的系統學習。

## 誰應該決定下一輪改甚麼？Review owner 不是最後簽名，而是停線的負責人

有些 routine review 寫得很漂亮，最後卻無人決定是否採用。又或者某位同事自己改了流程，下一位仍然照舊做，因為從來沒有人把新 rule 放進現行工作。這種情況不是少了一張筆記，而是 review owner 沒有被寫進 loop。

owner 不一定要親手做所有事情。他的責任是判斷 evidence 是否足夠、這個 bounded change 是否值得試、以及例外出現時應否停下或改範圍。沒有這一位，AI 產生的任何改動建議都只是另一條意見。

Jimmy 的結論是：routine review 的完成線，不是寫了復盤，而是 owner 已經決定下一輪只試哪一個改動、又用甚麼收貨。

每次 review 結尾都應留下：

1. 本輪最早的摩擦和分類；
2. 下一輪只改的一格；
3. 仍然不改、暫時保留的條件；
4. review owner 和下一輪觀察日；
5. 出現甚麼結果就應回退或停止。

這五項令 review 從一場事後討論，變成一個可接續的工作決定。AI 可以幫你整理 run evidence，但不能替 owner 宣布流程已經可靠。

## 用公開材料 briefing 跑一次：怎樣從重做找出不是工具問題的摩擦

以下是 synthetic 例子。假設一份 internal briefing 要重做兩次，表面看起來像 AI 把內容弄錯。回看 run evidence 後發現，兩份 agenda 版本不同：一份是舊草稿，一份才是本輪已批准材料。AI 只是根據它看到的資料起稿。

因此下一輪不換工具、不加更多 prompt，只加一個 version owner check：input 裡標明唯一 current reference，其他版本只可當歷史參考。output format、reviewer 和材料範圍都維持不變，才看得見這條改動有沒有影響重做。

| Review 格 | 本輪判斷 |
|---|---|
| Evidence | 兩次 draft 分別用了不同 agenda |
| Friction | AI 無法判斷哪一份是現行版本 |
| 分類 | Input／context，而不是文字能力 |
| Bounded change | 加 version owner 與唯一 source label |
| Next observation | 下一輪是否仍因版本衝突退回 |

Jimmy 的結論是：AI 不準有時只是最後看得見的症狀；真正值得修的，可能是所有人都沒有寫清哪一份資料有效。

這個例子不代表所有 AI 問題都不是工具問題。若在同一張安全 task card 下仍反覆出現同一錯誤，才值得進一步做 [換 AI 工具前，先測你帶得走幾多](./3-11-換人工智能工具前，做一次安全替換測試.md) 的 replacement test。

## 今日怎樣做第一次 routine review？只選一條最近返工的低風險工作

不要為整個部門或所有流程開一次大型檢討。先找最近一次需要重做、範圍可以收窄、資料可公開或 synthetic 的 routine。用四句寫下 state、摩擦、分類和本輪只改甚麼；由 owner 確認後，再跑一次。

如果下一輪沒有改善，這不是失敗。你已經得到一條更準確 evidence：原先假設不成立，應回到分類重新看 input、standard、owner、exception 或工具。真正不應做的是一次過再加五個新改動，令學習重新消失。

Jimmy 的結論是：每次只修一格，才能令每一次重做變成下一次少猜的證據。

第一輪請完成：

1. 選一條低風險、最近返工的 routine；
2. 留下最小 run evidence；
3. 將摩擦放進一個分類；
4. 寫一個 bounded change 與回退條件；
5. 請 owner 批准下一輪，並保留結果。

想先把一件工作畫清每一格，可讀 [明明每星期都做，點解仍然交唔到畀人或 AI？](./3-6-重複工作交不出去，先畫工作地圖.md)。如果你懷疑問題真的在工具可攜性，下一篇可讀 [換 AI 工具前，先測你帶得走幾多](./3-11-換人工智能工具前，做一次安全替換測試.md)。
