# OPC 唔係一個人做晒：由個人經驗到可交接嘅 AI 工作系統

好多人聽到 One Person Company，就以為係一個人包辦研究、銷售、交付、客服同管理；AI 愈勁，便只係叫同一個人做得更多。結果你開咗更多工具、起咗更多 draft，但每逢要定方向、補背景、判斷例外、同人溝通，仍然要由你逐格接手。

問題不在於你未有足夠多 AI Agent，而在於最重要的工作判斷仍然只存在你腦裡。AI 可以加快執行，卻不知道哪份資料可信、這次真正要解決甚麼、何時應停下來等人決定。於是速度增加了，老闆的注意力反而被更多 output 拉得更散。

Jimmy 的核心判斷是：**OPC 不是一個人做到盡，而是把一個人的知識、判斷和工作方法，逐步變成 Agent、同事或合作夥伴可以安全接力的能力。AI Agent 是做到這件事的方法，不是終點。**

| 由哪一層開始 | 要回答的問題 | 應留下甚麼 |
| --- | --- | --- |
| Personal OS | 我每次其實在判斷甚麼？ | current state、decision note、可信 context |
| Reusable Skill | 哪些做法已重複而且可講清？ | input、步驟、quality gate、例外 |
| Agentic Work System | AI 可以負責哪一段，在哪裡必須停？ | AI work card、review、run receipt |
| OPC Collaboration | 哪些責任應由 owner、team、partner 或 Agent 接手？ | handoff、owner、interface、下一步 |

## 一人公司點解唔等於一個人做晒？真正要放大的不是待辦清單，而是可交接能力

一個人做所有事，短期看似靈活：不用開會、不用交接、想改便改。但當工作開始重複、客戶變多、內容要持續、決定愈來愈多，最大的成本不是少了人手，而是所有人都要等同一個腦袋重新想一次。每一個人、每一個工具、每一條新 chat 都在等你補回背景和標準。

OPC 的意思不應是「永遠只有我一個」。它比較接近一個 owner 能守住方向、關係、取捨和最後責任，同時把不必每次由自己重新發明的部分，變成別人或 AI 能看懂、執行和回報的工作單位。

Jimmy 的結論是：一個人公司真正的槓桿，不是把自己塞進更多工作，而是減少每次工作都要重新經過自己的地方。

| 仍然只靠自己 | 開始可交接 |
| --- | --- |
| 「你跟住感覺做啦」 | 目標、材料、完成線和例外已寫清 |
| 每次都要口頭講背景 | 有 current state 和可信 context |
| AI 交一堆 output，owner 自己執手尾 | AI 只負責有收貨線的一段，未知即停 |
| 交接等於丟一堆檔案 | 下一位知道讀甚麼、誰決定、卡住找誰 |

這不代表所有工作都要標準化。新方向、重要關係、複雜談判和高風險判斷，很多時正正需要 owner 留在場。OPC 是清楚分開哪些事值得放大，哪些責任不能假裝已交出去。

## AI Agent 點解未必令 OPC 輕鬆？因為沒有 context 的執行，只會製造更多要你處理的問題

AI Agent 最容易展示的是「它做到一次」。它可以研究、起草、整理、轉格式，甚至串接工具跑出一連串動作。但只要它不知道目前哪個版本可信、誰有權批准、輸出給誰、例外出現時如何處理，它就只能用合理文字補空白。看上去很主動，實際上把不確定性推回 owner。

所以 Agent 不是另一位「替身員工」。它是一段被清楚界定的工作能力：拿甚麼 input、負責哪個 output、經過甚麼檢查、遇到甚麼情況必須停下來。你不必一開始建立 autonomous team；先讓一段真實、低風險、可 review 的工作穩定交到手上，已經是重要進展。

Jimmy 的結論是：Agent 的價值不在它看起來多自主，而在它能否讓 owner 少一次重新解釋、同時不失去判斷和控制。

| 沒有工作系統的 Agent | 有界線的 Agent |
| --- | --- |
| 只收到「幫我做好」 | 有清楚 goal、approved context 和 output contract |
| 自己補資料、自己猜優先次序 | 未知、矛盾或超出權限時標記 `blocked` |
| 交一個看似完整的答案 | 交一份可被 reviewer 收貨的 artifact |
| 出錯只會再試一次 | 留下 run receipt，知道應從哪一格修 |

想先建立這種控制層，可讀 [AI 做得愈多，人應該做乜？專業判斷在 workflow 的控制層](./3-4-自動化愈多，人更要守住判斷層.md)。

## Personal OS 點樣先唔只係個人整理？要把隱藏判斷變成下次可以調用的 context

很多人一聽 Personal OS，就想到筆記 app、dashboard 或任務清單。它們可以有用，但不是核心。真正有用的 Personal OS，是令未來的自己、同事或 AI 不用翻晒歷史，已經知道目前正在做甚麼、哪些事已決定、哪些資料可信、哪些問題仍未解。

例如你每次寫內容前都會自然判斷：這個讀者現在卡在哪、這句 claim 有沒有根據、這個角度是否仍然符合你想建立的方向。若這些判斷只在起稿時臨時出現，AI 只會加快文字，不能累積你的工作能力。當它們被壓成一頁 context、幾條 review rule 或一個 current-state note，下一次才有地方開始。

Jimmy 的結論是：Personal OS 不是把人生資料化；它是把會影響下一次工作判斷的脈絡，留在正確位置。

| 不必一開始記錄 | 值得先留下 |
| --- | --- |
| 所有想法和所有舊 chat | 正在進行的目標、已定決策、blocker 和下一步 |
| 工具使用紀錄 | 會改變 output 的材料、標準、反例和 feedback |
| 一堆漂亮模板 | 下一位真正需要的入口、owner 和更新時間 |

你可以由一件剛剛重做過的工作開始。它不必是一個完整系統；只要下次再開始時，你少問一次「上次到底點做」，已經留下了第一格可複利的 context。

## 由 Personal OS 走到 Skill，再走到 Agent：唔好跳級，逐層證明下一位接得住

以下不是一條人人必經的升級路線，而是一個較安全的建造次序。它的目的不是把所有工作都 AI 化，而是避免你在做法仍然模糊時，過早封裝成 Skill 或自動化。每一層都要先在真工作中證明，下一位真的看得懂、用得到、收得到。

| 層次 | 你先驗證甚麼 | 尚未適合做甚麼 |
| --- | --- | --- |
| Personal OS | 工作現況和判斷能否被找回 | 不用急著砌大資料庫 |
| Reusable Skill | input、步驟、output、例外是否開始穩定 | 不要把一次成功當成標準 |
| Agentic Work System | AI 能否在邊界內交出可 review 成果 | 不要直接給高權限或外發權 |
| OPC Collaboration | 角色之間能否以清楚 handoff 接力 | 不要假裝所有責任已消失 |

當一個做法重複出現，而且你能說清 input、output、品質閘和常見例外，它才開始像一個 Reusable Skill。等它可以在受控範圍內多次跑到收貨，再考慮交給 Agent。這樣建出來的 Agent 不只是 prompt 的包裝，而是你對工作質素的可重用承諾。

Jimmy 的結論是：一人能力要被放大，第一步不是找更多 Agent，而是令下一位能少猜一點；Skill 和 Agent 只是把這種清晰度放大。

想判斷一件工作是否已交到可驗收，可讀 [你唔係未識用 AI Agent：你未把一件工作交到可驗收](<../../04-AI Builder（AI建立者）/chapters/4-40-把一件工作交到可驗收.md>)。

## Owner 留低甚麼先唔會變成「AI 做晒」的幻覺？方向、關係、取捨和最終責任仍然要有人持有

當 AI 能起更多草稿、跑更多流程，owner 的價值不應只剩下按 approve。真正要留在 owner 手上的，是決定哪個問題值得做、哪段關係不能被效率取代、資料和承諾可以去到哪裡，以及面對例外時如何取捨。這些不是 AI 暫時「未夠勁」才要人做；它們本身就涉及責任和後果。

這也令 OPC 跟「自動化工場」不同。你不是把每個決定都交出去，而是把可重複的執行從腦裡釋放出來，讓自己花更多時間在真正會改變方向的判斷。若所有事仍要 owner 每輪逐字重寫、逐個核對，系統只是在外面加了一層工具，沒有增加任何委派容量。

Jimmy 的結論是：放大不等於放棄控制；好的 OPC 系統令 owner 更清楚何時必須親自出手，而不是更難追責。

## OPC Network 可以是甚麼？不是把 freelancer 堆在一起，而是讓不同人能以清楚介面協作

當一個人開始有可交接的 context、Skill 和工作邊界，下一步不一定是請一隊傳統 team。某些工作可以由 Agent 完成；某些需要有自己專業和責任的人協作。更有趣的可能性是：不同 owner 都帶著自己的工作系統，以較清楚的 input、output、review 和 handoff 共同完成一個結果。

這是一個值得測試的工作假設，不是已經證明的商業模型。它的前提很高：每一方都要知道自己負責甚麼、交付怎樣驗收、哪些資料不可共享、出現例外誰說了算。沒有這些介面，所謂 Network 只會變成更多 chat、更多追問和更多責任不清。

Jimmy 的結論是：OPC 的終點未必是永遠獨自工作；更可能是你不再只能靠傳統人手堆疊，才有能力與其他有清楚系統的人合作。

## 用一條內容工作試一次：由 founder 腦中的判斷，變成下一輪可接手的能力

以下是 synthetic 例子。一位 founder 想持續分享 OPC × AI Agent 的工作觀察。以前每次想寫文，他都從零開始：翻不同筆記、想受眾、擔心太多 AI buzzword，最後自己逐句改。即使用 AI 起草，也只會更快得到一篇未有立場的文章。

第一輪不用建立內容 Agent。先把一條工作壓成四格：讀者是誰、今次只想改變哪個錯誤理解、可用的 firsthand observation 是甚麼、哪種說法不能作未證實承諾。寫完後，AI 只協助整理成候選結構；owner 仍然決定核心判斷和是否代表自己。

| 這次摩擦 | 留下的資產 | 下次怎樣接力 |
| --- | --- | --- |
| 每次都重新找內容方向 | 一句讀者問題和內容支柱 | 起稿前先讀同一張 context |
| AI 寫得順但沒有 Jimmy 立場 | core judgment + boundary | AI 只把已定判斷延展成 draft |
| 每次都怕講得太大 | evidence / assumption / open question 標籤 | review 時先檢查 claim 邊界 |
| 一次好文沒有留下方法 | candidate insight + feedback | 下一篇回收有用表達或反例 |

這個例子不等於內容一定要自動化。它只是展示：當 founder 的判斷被留下，AI 才有可能幫到下一步；否則 AI 只能不停模仿表面語氣。

## 今日怎樣開始建立 OPC？選一件每周重複、但仍然要你重新解釋的低風險工作

不要由「我要砌一間 AI 公司」開始，也不用立刻畫一張很大的 Agent 組織圖。挑一件你每周或每月都要重做、而且別人一接手便會問很多問題的工作。先看清你真正有沒有一套做法；若還沒有，留下 current state 或 decision note 已經足夠。

當這件工作已跑過幾次、標準開始穩定，再把它寫成最小 Skill；當你可以列出 AI 能做、不能做、怎樣收貨和何時停，才用一個受控 run 測試 Agent。每次只多交接一小格，才會知道能力到底有沒有被放大，而不是只多了一堆工具。

Jimmy 的結論是：OPC 的第一步不是孤身做更多，而是讓一件真工作下次不用再完全靠你記得怎樣做。

第一輪請做：

1. 選一件最近兩三次都由你重新解釋的低風險工作；
2. 寫一句它的 Goal，以及這次不能錯的兩件事；
3. 留下已定決策、可信材料、owner 和下一步；
4. 只交 AI 做一段可 review 的執行，不給外發或不可逆權限；
5. 跑完後寫下一條「下次少猜甚麼」的規則，再決定是否值得變成 Skill。
