# 換 AI 工具就要由零開始？工具可以租，工作 context 要自己掌握

AI 工具愈來愈多，有人花很多時間把某一個 chat、個人設定或 workspace 養到「最懂自己」。它短期很方便；但當你換工具、換帳戶、換同事，或只是開一個新 project，很多關於工作方式、語氣、判斷和驗收的東西又要從頭解釋。工具愈強，這種依賴感反而愈明顯。

問題不是不應使用工具的記憶或設定，而是把所有重要 context 都只留在某一個工具裡。現行規則、可重用格式、自己的判斷、可信材料入口若沒有獨立位置，換工具時就不是「重新連接」，而是要重新累積；團隊也無法看見你一直在使用的工作標準。

Jimmy 的判斷是：工具可以租，context 要自己掌握。這不等於所有東西都要本機化或自己維護基建；意思是將真正屬於工作的方法、判斷、標準和可攜資料放在可讀、可更新、可連回 source of truth 的 context layer，讓不同工具按需要讀取。

| 三層 | 應放甚麼 | 換工具時怎樣處理 |
|---|---|---|
| 工具層 | 模型、介面、雲端功能、外掛 | 可以替換或保留 default |
| 翻譯層 | task card、格式、review rule、SOP | 帶走後按工具重新調校 |
| Context 層 | 身份、工作判斷、已批准材料入口 | 自己掌握、版本化、持續更新 |

## 為甚麼把所有背景留在一個 AI 工具會愈用愈難換？方便不等於可攜

當一個工具已經記得你的語氣、喜好和常用工作，繼續留在裡面當然方便。問題不在這份方便，而在你是否有另一個地方看見它實際記了甚麼、哪條規則已過期、以及哪些內容根本不應被另一個 project 或工具讀到。沒有這些界線，工具記憶會慢慢變成一個不能檢查的黑箱。

更麻煩的是，很多重要 context 原本不是「資料」，而是判斷：你如何收貨、哪些成效不能承諾、哪種語氣適合哪個受眾、遇到未知時應怎樣停。它們若只存在某個專用設定裡，同事和新 AI 都無法對照，也難以分辨今天仍有效的是哪一條。

Jimmy 的結論是：工具可以知道你的工作，但不應成為你工作判斷的唯一住處。

先分辨這三種情況：

| 情況 | 應怎樣處理 |
|---|---|
| 只是工具操作偏好 | 可留在工具設定，換工具時再調校 |
| 會改變 output 的工作標準 | 應寫成可讀 task card、SOP 或 rule |
| 敏感、私人或未確認背景 | 不因可攜而打包；留在有適當權限的原系統 |

這種分法令你不會因為怕 lock-in 而過度搬資料，也不會因為方便而把最重要規則鎖死在某一個 app。

## 三層 context 點樣分工？工具提供能力，翻譯層令能力接到你的工作

很多「工具換了就失效」的經驗，並不是因為檔案真的不能打開，而是中間少了翻譯層。你可能保存了很多文件，但沒有 task 格式、輸出標準或 review rule 告訴新工具怎樣用它們；資料仍然在，工作方法卻沒有跟著走。

三層模型把責任分開：工具負責能力，context 層保留可相信的內容與判斷，翻譯層則把某次工作要做甚麼、怎樣收貨、何時停說清。這讓不同工具能接入同一工作，而不是每個工具各自養一個版本的你。

Jimmy 的結論是：真正可攜的不是一堆檔案，而是 context 加上能讓工具正確使用它的翻譯規則。

| 層 | 例子 | 最常見誤會 |
|---|---|---|
| 工具層 | ChatGPT、Claude、Codex、搜尋工具 | 以為最強工具自然最懂工作 |
| 翻譯層 | prompt template、work card、格式、acceptance | 以為 prompt 只是一次性句子 |
| Context 層 | 已批准材料入口、身份規則、SOP、decision note | 以為 context 等於全部歷史資料 |

當一個 output 不好，先問它是工具能力問題、翻譯未清，還是 context 已過期。這比直接換 app 更容易找到真正要修的格。

## 甚麼應該自己掌握，甚麼可以交給服務？自有內容，不必自建所有基建

聽到「own your context」後，有些人會想把每份資料、每項同步、每個介面都自己建。這會把工具 lock-in 問題換成維護負擔：你花太多時間照顧系統，反而沒有時間做真正工作。可攜不等於要放棄所有現成服務。

較務實的分界是：會改變工作判斷的內容，你要有可讀、可更新的 owner；儲存、同步、搜尋和介面可以使用適合的服務。你掌握的是內容與標準，不是一定要自己經營伺服器或重造工具。

Jimmy 的結論是：自有的是你的判斷、規則與可用內容；可租的是承載它們的工具、介面和服務。

| 應自己掌握的內容 | 可以放心使用服務的部分 |
|---|---|
| 已批准工作標準與 acceptance | 同步、備份、搜尋與版本工具 |
| 可重用 task／SOP／review rule | 模型、介面、文件 app、雲端儲存 |
| 身份與受眾的工作定位 | 協作通知、排程、格式轉換 |
| source of truth 與 refresh owner | 不同工具的便利功能 |

這個分界也提醒你：不是所有資料都適合放進 context pack。敏感資料、合約、客戶紀錄與 production access 即使由你擁有，也不代表應跨工具複製。

## `me.md`、task card 和 SOP 分別留住甚麼？不要用一份大檔案裝所有 context

有些人為了可攜，寫一份很長的「關於我」文件，然後希望任何 AI 每次先讀完。這樣做很快會令身份、project 背景、一次性任務和長期規則混在一起；更新一條資訊時，也沒有人知道它會影響哪些工作。

更有效的是按工作壽命分開：長期身份與合作語氣放在小型 identity note；一次任務用 task card；重複工作用 SOP；當前 project 用 current-state note。不同工具只讀今次需要的那一層，而不是每次吞掉你全部歷史。

Jimmy 的結論是：context 愈重要，愈應按用途拆開；一份全能大檔案通常最難更新，也最難安全帶走。

| 文件 | 適用時間 | 應留下甚麼 |
|---|---|---|
| Identity note（例如 `me.md`） | 長期但會慢慢更新 | 語氣、受眾、合作原則、不可承諾的邊界 |
| Task card | 一次工作 | input、output、acceptance、stop line |
| SOP | 重複 routine | trigger、steps、owner、exception、refresh |
| Current state | 正在運行的 project | 現行決策、blocker、下一步與 owner |

分開後，你不會要求新 AI 一次理解一切；它只要按眼前任務讀到足夠、可信、仍有效的內容即可。

## Context 要點樣更新先不會愈儲愈舊？寫清 source of truth 和 refresh owner

一份 context 即使最初寫得很好，也會過期。受眾改了、材料換了、某條規則被新的 review 推翻，AI 不會自動知道；它只會忠實執行你上次留下的文字。這就是為何同一份 setup 用久了，output 反而開始不似你現在的需要。

避免過期不是每周重寫全部文件，而是令每份重要 context 有 source of truth、用途和更新責任。當某一類變動發生，owner 知道要更新哪一層，而不是讓舊 prompt 靜靜地繼續影響工作。

Jimmy 的結論是：可攜 context 必須可退休；沒有 refresh 的「記憶」只是未來的錯誤來源。

一條最小更新規則可以寫成：

1. 若工作目標或受眾改變，更新 task card／identity note；
2. 若材料或事實改變，更新 source of truth，不讓舊版冒充現況；
3. 若 review 反覆改同一件事，更新 SOP 或 feedback rule；
4. 每份 pack 都寫明 refresh owner 與最近確認日期。

這四句不會令工作變得官僚；它只確保你下次把 context 帶到另一個工具時，帶走的是今天的判斷，不是昨天的習慣。

## 用公開 briefing workflow 跑一次：同一套 context 怎樣在兩個工具都可 review

以下是 synthetic 例子。假設你要將指定公開文章整理成 internal briefing。以前你只在一個 AI 工具保存了語氣和格式；換另一個工具時，output 便突然失去你熟悉的結構。這不是要你把所有個人筆記搬過去，而是要抽出今次真正需要的三層。

你可以把 identity note、task card 和 current source of truth 放在可讀位置，讓兩個工具都只讀這些已批准材料；最後仍由同一位 owner 按同一張 acceptance 收貨。整個練習不涉及私人資料或外發。

| 層 | 本輪放甚麼 |
|---|---|
| Context | 公開文章 URL、已批准格式、香港廣東話工作語氣 |
| 翻譯 | 「三重點、兩未知、來源欄；不新增未查證內容」 |
| 工具 | A、B 各自按同一張 task card 起 draft |
| Review | owner 對照同一 acceptance checklist |

Jimmy 的結論是：可攜性不是兩個工具交出一模一樣的句子，而是兩邊都能在同一套工作邊界內交出可 review 的成果。

若兩邊都需要大量臨時補充，優先修 context 或翻譯層；不要急著宣布某個工具不適合你。這就是 [replacement test](./3-11-tool-replacement-test.md) 真正要驗證的東西。

## 今日怎樣開始？先抽出一件低風險工作的最小 context，不要搬走整個人生

第一步不需要做大型知識庫遷移。選一件你可能會在另一個工具重做、材料可公開或 synthetic、出錯可由人收回的小工作。把它需要的身份語氣、task card、source of truth、acceptance 和 stop line 分開寫成最小包。

然後請一位未讀過完整歷史的人或另一個 AI，只靠這包 context 覆述自己可以做甚麼、不可做甚麼、誰負責收貨。答不清楚時，補一條規則，不要立即加十份資料。

Jimmy 的結論是：工具會換；真正應留下的，是你能否把自己的工作判斷安全、清楚地重新接上。

第一輪請完成：

1. 選一個低風險、可回退工作；
2. 分開 identity、task、SOP／current state，不寫全能大檔案；
3. 只連入本輪可信 source of truth；
4. 寫清 acceptance、owner 與 stop line；
5. 在第二個工具或新 session 做一次小型 review test。

想把可攜 context 變成正式測試，可讀 [換 AI 工具前，先測你帶得走幾多](./3-11-tool-replacement-test.md)。想深入看 context pack 應怎樣設計，可讀 [換 AI 工具就要由零開始？你需要帶得走的不是所有資料，是可信 context](./3-9-portable-context-pack.md)。
