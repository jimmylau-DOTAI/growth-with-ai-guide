# AI 每次都要重講背景？問題多數不是記性，而是 context 放錯層

你可能有過這種感覺：同一句背景明明講過很多次，新 AI session 又要重新交代；另一邊，它又記住了不該帶去新 project 的舊規則。於是你一時覺得 AI 記性很差，一時又覺得它記得太多、答得好像用了錯的前提。

這兩種問題都不單是模型能力。很多 context 混在同一個 chat 或長期設定裡：今次任務、個人語氣、某個 project 的限制、已經跑穩的 workflow 沒有分開。臨時要求污染了長期偏好，過期規則仍影響 output，重複工作則永遠靠你重新說明。

Jimmy 的判斷是：AI 記憶不是「它會不會記得晒」，而是人要先把 context 放進正確層。分流後，出錯時你知道應改 task、長期偏好、project 規則還是 workflow；這比每次重寫整段 prompt 更容易讓工作累積。

| Context 層 | 適合放甚麼 | 放錯最常見後果 |
|---|---|---|
| 今次 task | 一次 output、即時限制、短期完成線 | 臨時要求污染以後工作 |
| 長期偏好 | 穩定語氣、合作原則、常見工作習慣 | 一次性資料變成永久規則 |
| Project 規則 | 某 project 的 source、禁區、完成線 | A project 規則誤用在 B project |
| 可重用 workflow | 重複 SOP、檢查表、成熟 Skill | 同一流程每次從零解釋 |

## AI 看似記性差，點解其實可能是 context 放錯位置？先把症狀翻成分類問題

「每次都要重講我是誰」和「它又拿別個 project 的規矩來用」表面相反，實際都是 context 沒有生命週期。前者把穩定偏好留在一次對話；後者把短期、專案專屬規則錯放到長期層。AI 沒有提醒你它正在使用哪條舊規則，所以 output 仍可能很流暢，卻建立在錯前提上。

先把感覺轉成可以定位的問題，才不用每次只怪模型。你要問的不是「AI 為何又錯」，而是「這條資訊原本應該活多久、服務哪種工作、誰有權更新它」。這三條答案通常已經指出它該放哪裡。

Jimmy 的結論是：AI 記得愈多不一定愈有用；記錯層的 context 會安靜地一直影響判斷。

| 你見到的症狀 | 更可能的原因 | 優先處理 |
|---|---|---|
| 新對話又要重講語氣 | 穩定偏好只留在 chat | 升到長期 identity／voice note |
| 用了其他 project 規則 | project 限制放進長期層 | 搬回 project context |
| 跟著過期安排做 | 會過期資訊未退休 | 更新 source of truth／refresh 日期 |
| 同一流程講了十次 | workflow 未變成可重用標準 | 先寫 work map 或 SOP |

定位後，只修最早放錯的一層；不要把所有 context 再複製一次到新的對話裡。

## 今次 task 要放甚麼？只放會影響眼前 output 的目標、材料和完成線

每個 task 都有一批只對今次有用的資料：deadline、指定格式、目前可用材料、一次性的語氣要求。這些資料不應被永久記住，否則下次不同工作會被舊要求拉走；但若沒有在眼前 task 說清，AI 又會依常見模式自行補足。

task context 的重點不是多，而是讓 AI 或協作者知道今次要交甚麼、可以讀甚麼、哪些不可猜、誰收貨。它能在完成後退休，正好避免一次工作成為日後的隱性干擾。

Jimmy 的結論是：眼前 task 只承擔眼前完成線；不要把所有長期偏好和 project 歷史塞進每一次工作。

一張最小 task card 可有五格：

1. 今次 output 要幫誰作甚麼決定；
2. 可用 input 與 source of truth；
3. 今輪不可做／未知要標示甚麼；
4. 可 review 的格式與 acceptance；
5. reviewer／stop line。

這五格完成後，task 結束即可退休；有真正值得留下的 feedback，再另外判斷應升去哪一層。

## 長期偏好同 project 規則點樣唔好混？問「誰受影響」和「幾時會過期」

長期偏好通常是跨工作都成立的東西，例如你用香港廣東話、先講工作摩擦再講工具、未驗證成果不可包裝成承諾。project 規則則只對一個範圍成立，例如本輪只可用哪幾份材料、某個 repo 的安全邊界、今次 output 交給哪位 owner。兩者若混在一起，長期設定會慢慢裝滿舊 project 的雜訊。

最實用的分法不是看資料看起來多重要，而是看它影響誰、會活多久。影響你多數工作且幾個月仍成立的，可進長期層；只影響一個 project、隨工作結束而過期的，應留在該 project 的 context。任何會改變公開或高影響決定的資訊，都要有明確 owner。

Jimmy 的結論是：長期偏好回答「我通常怎樣工作」；project 規則回答「這次／這個 project 必須怎樣做」。

| 問題 | 放哪一層 | 例子 |
|---|---|---|
| 換大部分工作仍成立嗎？ | 長期偏好 | 語氣、受眾原則、合作方式 |
| project 完結便失效嗎？ | Project 規則 | 指定 source、範圍、禁區、owner |
| 只對本次 output 有用嗎？ | Task card | 今次格式、deadline、一次限制 |
| 多次同類工作都要遵守嗎？ | SOP／Skill 候選 | review checklist、重複流程 |

每次新加長期 context 時，順手寫一個「何時應重看」；答不到時，先不要放長期層。

## 重複 workflow 何時才應升成 Skill？先讓 SOP 跑穩，不要把一次成功寫死

同一流程重講很多次時，直覺是把它直接寫成 Skill 或自動化。但第一次做順可能只是條件剛好齊；例外、owner、驗收還未被看見。過早固定的風險不是只寫錯一份文件，而是日後每次都很有信心地複製錯方法。

較好的做法是先用 work map 看清 trigger、input、owner、state 和 output，再用 minimum SOP 跑幾次。當同樣條件和驗收反覆出現，才把穩定部分升成可重用 workflow。仍會變動的部分要保留在人手 review 或 exception，而不是硬塞進 Skill。

Jimmy 的結論是：Skill 不是收納任何 prompt 的地方；它是已經被多次工作證實、且知道怎樣停線的流程。

| 現況 | 適合放哪裡 | 為何 |
|---|---|---|
| 一次性需求 | Task card | 做完即退休 |
| 未跑穩但有 project 重複 | Project note／SOP 草稿 | 先收集差異與例外 |
| 約三次後骨架已穩 | Minimum SOP | 可交接、可 review |
| input／output／exception 均穩定 | Skill 候選 | 才值得做成可重用能力 |

這個階梯讓你不會把任何一句 prompt 都當作工作資產；真正留下的是能在下一次少猜的部分。

## Context 愈用愈舊點算？每層都要有 refresh 和退休規則

分層不是一次設定後便完結。受眾會改、project 完結、格式會更新、曾經有效的 feedback 會失效。若只加不減，長期偏好和 project 規則很快都變成垃圾場；AI 還是會照讀，只是你很難再看出哪一條讓它答歪。

refresh 不代表每周大掃除。它只是把 context 視為有生命週期的工作資料：有 owner、有最近確認時間、有觸發更新的條件。這令過期規則可以被安全退休，而不是默默留在某個不再打開的設定裡。

Jimmy 的結論是：好的 AI 記憶不是一直增加，而是每層都知道何時要更新、何時應該失效。

| 層 | 何時應重看 | 怎樣處理 |
|---|---|---|
| Task | output 已收貨或範圍改變 | 結束、重開或標 `blocked` |
| 長期偏好 | 你的工作風格、受眾或原則改變 | 更新 identity note |
| Project 規則 | source、owner、目標或安全邊界改變 | 更新 current state／project rule |
| SOP／Skill | 重複 evidence 顯示規則已不適用 | 修正、加 exception 或退休 |

只有在你能指出「這條規則由誰、何時確認」時，它才值得影響一個新 AI session 的工作。

## 用公開教學 outline 跑一次：四層怎樣令新 session 不用翻歷史又不會亂帶規則

以下是 synthetic 例子。假設你要把一篇公開文章整理成 internal teaching outline。這次的 task 是一份可 review outline；長期偏好是香港廣東話、先講工作痛點；project 規則是只用指定公開來源、未知要標示；若這種 outline 已跑穩，才把固定格式升成 SOP。

新 AI session 不需要讀所有舊 chat。它只要讀眼前 task card、適用的 identity／voice note、project 的現行規則，就能知道它可以起草甚麼、不可猜甚麼、要交給誰 review。所有資料都是公開或 dummy，不包含客戶與 production context。

| 層 | 本輪放甚麼 |
|---|---|
| Task | 指定文章、outline 格式、owner review |
| 長期偏好 | 香港廣東話、用工作例子解釋概念 |
| Project 規則 | 只用公開材料；未驗證內容標未知；不可外發 |
| Workflow 候選 | 若每次都用同一 acceptance，才記成 SOP |

Jimmy 的結論是：分層的成效不是 AI 變得神奇記得所有事，而是新 session 也能只讀正確 context，交出不需要靠猜的第一稿。

若它仍然答錯，先回看是哪一層沒有寫清或已過期。這比把整段歷史再貼一次，更容易讓下一輪真正變好。

## 今日怎樣開始分流 context？挑一件你不停重講的工作，只分四桶

你不需要立即建立完整 knowledge system。選一件最近不停重講、但可用公開或 synthetic 材料練習的小工作，把現有內容只分成四桶：今次任務、長期偏好、project 規則、可重用 workflow 候選。先讓分類可見，再決定哪一桶應更新或刪除。

這個練習的目標不是讓每個資料都有完美位置，而是找出最常造成猜測的一條錯放規則。若某項還不確定，暫留 task 或 project 層，等更多 run evidence；不要急著升成永久 memory 或 Skill。

Jimmy 的結論是：你以為 AI 記性差，很多時是未幫它分清今次任務、長期偏好、project 規則和可重用 workflow。

第一輪可以：

1. 列出一段你重講過兩次以上的背景；
2. 問它會活多久、影響誰、誰可更新；
3. 放進四層其中一格，並標一條 refresh／stop rule；
4. 用新 session 只讀這些 context 起一份低風險 draft；
5. 記下它最早仍然猜錯的是哪一層。
