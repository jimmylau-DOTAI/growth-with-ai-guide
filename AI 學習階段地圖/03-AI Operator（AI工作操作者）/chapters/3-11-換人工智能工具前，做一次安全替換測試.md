# 換 AI 工具前，先測你帶得走幾多：一個安全的 replacement test

新 AI 工具一出現，很容易令人想知道它是不是比現有工具更強。可是工具 A 做得較好，未必代表工具 B 不可用；有時真正差別是你給 A 的背景較完整、兩邊讀到的材料不同，或你根本還未寫清楚甚麼才算一份合格工作。

如果直接把一個真 project 拿去比較，結果更難看懂：資料可能敏感、任務中途改了、不同人各自補救過，最後只剩一句「感覺這個較好」。這種比較不能幫你決定該換工具、修 context，還是先把工作方法寫清楚。

Jimmy 的判斷是：replacement test 不是要選出最強工具，而是測試同一份 context 能否在不同工具上交出可 review 的工作。先用公開或 synthetic 材料、同一張 task card、同一位 reviewer 做低風險比較，才知道差異到底出在哪裡。

| 測試條件 | 要固定甚麼 | 它防止甚麼 |
|---|---|---|
| 材料 | 同一份公開／synthetic input | 一邊因資料較好而勝出 |
| 任務 | 同一個 output 與範圍 | 拿不同工作硬比較 |
| Context | 同一張工作交代與邊界 | 把 prompt 差異誤認成工具差異 |
| 驗收 | 同一張 checklist 與 reviewer | 只靠感覺選一邊 |
| 結論 | keep、修 pack、再測或停止 | 比完仍不知道下一步 |

## 覺得新工具好像更勁，點解仍然不應立即換？你未必在比較同一件工作

人很容易記得某一次很驚艷的 output，卻忘記那次用了不同資料、不同問題、不同時間和不同期待。這種體驗可以幫你探索工具，但不能支持工作上的切換決定。當條件不一樣，結果反映的可能是任務難度或 context 完整度，而不是工具能力。

replacement test 的第一個價值，是把「好像更好」翻成可比較條件。它要求你先決定同一件小工作應交甚麼、可以看甚麼、哪些不能做、甚麼算合格。即使最後不換工具，這張卡也會讓你現有的工作更清楚。

Jimmy 的結論是：換工具前最值得測的不是誰最聰明，而是你的工作方法有沒有清楚到能被公平比較。

先問自己四條：

1. 兩邊是否真的在做同一種 output？
2. 兩邊是否看到完全相同、可安全使用的材料？
3. 你有沒有在比較前寫好 acceptance，而不是看完才選喜歡的？
4. 任何一邊出錯時，能否人手收回、不會外發或造成不可逆影響？

四條未能答「是」時，先不要把真 project 丟進去；你仍在做探索，不是在做可用的 replacement test。

## Replacement test 的 task card 應該寫甚麼？同一張 context 先讓比較有意義

沒有 task card 的比較最容易失真。工具 A 收到的是一句短 prompt，工具 B 則因為你邊用邊補了更多資料；其中一邊更熟悉你的偏好；最後你把這些人為差異都歸到模型身上。這樣得出的「勝負」無法重複，也不能被另一位 reviewer 檢查。

task card 要把今輪的目的、可用材料、不可做、output 和完成線放在同一頁。它不是要寫成最長 prompt，而是讓兩邊都面對同一個工作合約。任何一邊需要額外背景，必須明確記錄，而不是暗中加料。

Jimmy 的結論是：公平比較不是把指令寫得很複雜，而是確保每個會改變 output 的條件都被看見。

| Task card 欄位 | 最小寫法 |
|---|---|
| 目標 | 把指定公開文章整理成一頁 internal briefing |
| 可用材料 | 一個 URL、固定格式和已批准 dummy brief |
| 不可做 | 不新增未查證內容、不用私人資料、不外發 |
| Output | 三個重點、兩個未知、來源欄位、可 owner review |
| 完成線 | 未知已標示、格式完整、沒有新編數字 |

同一張 card 一旦寫好，先用你現有工具跑一次。這讓你知道 card 本身是否清楚，而不會把一個未定義工作直接變成工具之爭。

## 五個條件點樣固定先公平？材料、任務、context、驗收和 reviewer 都不能偷偷變

工具測試最常見的問題，是只固定了問題句子，卻沒有固定真正會改變答案的條件。例如一邊得到更新資料、一邊只看舊版本；一邊要求摘要、一邊要求分析；最後由不同人用不同標準看結果。即使其中一邊看起來較好，也無法知道好在哪裡。

把五個條件寫進 test，不是要把探索變得僵硬，而是讓你日後可以重跑。若第二次結果不同，你才有可能找出差異來自工具、設定、材料，還是 reviewer 的判斷變了。

Jimmy 的結論是：可比較的工具測試，靠的是條件一致，不是靠兩張 output 擺在一起看哪張較順眼。

| 條件 | 固定方式 |
|---|---|
| 材料 | 同一公開文章或同一 synthetic brief，不用客戶、CRM、合約、付款或 credentials |
| 任務 | 同一 output、同一範圍，不把 research 與寫作混在一起 |
| Context | 同一份目標、邊界、格式和完成線 |
| 驗收 | 先定三至五項 checklist，再看 output |
| Reviewer | 同一位或同一套明確規則，避免雙重標準 |

若有一項必須改變，就把它記作另一個 test，不要在同一輪裡偷換。這才令結果可以轉化成工作決定。

## Output 應該點樣收貨？先看有沒有遵守工作合約，後看哪一版較順

比較工具時，人很容易先看文筆、速度和「感覺」。但若 output 漏了未知、把推測寫成事實、或根本不符合指定格式，再流暢也不是一份合格工作。先把完成線收好，才值得在合格版本之間比較哪些使用感受更適合你。

acceptance checklist 不必很長，但必須包括真正會影響採用的條件。它要讓 reviewer 可以說「這一格不合格」而不是只說「我比較喜歡另一個」。這也幫你把之後的 feedback 變成 context rule。

Jimmy 的結論是：工具比較的第一層不是美感，而是兩邊有沒有先交到同一種可 review 工作。

可用以下 checklist：

1. 是否只使用批准材料，沒有新增未查證事實？
2. 未知、矛盾或資料不足是否被清楚標示？
3. output 是否符合約定格式與範圍？
4. 是否留下足夠資料讓 owner review？
5. 是否越過了不可外發、不可承諾或需人手決定的邊界？

只有兩邊先通過第一層，才再比較你較喜歡哪一個 default。否則要先修 task card 或 context pack，而不是把不合格 output 也加入「風格偏好」的競賽。

## 四種結果分別代表甚麼？不要因為一輪測試就宣布某工具勝出

一輪 test 的結果通常不能簡化成 A 贏、B 輸。兩邊都不合格時，可能是工作交代未清；兩邊都合格時，代表你的方法有可攜性；只有一邊反覆漏同一條規則時，才值得再做第二個安全任務確認是否有工具或設定差異。

把結論分流能防止你為一個偶發 output 做出昂貴切換。真正的下一步應由 evidence 決定：修 pack、保留 default、再測一次，或暫時停止使用這類任務做比較。

Jimmy 的結論是：最有價值的 replacement test，往往不是找到最強工具，而是把原本困在腦裡的標準寫了出來。

| 你看到的結果 | 更可能的解釋 | 下一步 |
|---|---|---|
| 兩邊都不合格 | context 或完成線未清 | 先修 task card，再測 |
| 兩邊都合格 | 工作方法可攜 | 保留較順手的 default |
| 一邊反覆漏同一規則 | 工具／設定差異可能存在 | 用第二個安全任務重測 |
| 結果不能比較 | 材料、任務或 reviewer 偷偷變了 | 重設更小的 test |

無論哪個結果，都不要把一次低風險試驗寫成工具能力保證。它只支援你對這張 task card 的下一個工作決定。

## 用公開文章 briefing 跑一次：A、B 工具的差異怎樣不會變成感覺之爭

以下是 synthetic 例子。假設你想比較兩個工具能否幫你整理一篇公開行業文章。兩邊收到同一 URL、同一張 task card、同一份格式，並且都只交 internal briefing，不對外發送。reviewer 先看兩邊是否有來源欄、三個重點、兩個未知和沒有新編數字。

結果可能是 A 語言較流暢，但漏掉未知；B 較短，卻完整遵守限制。這時不要立刻說 B 「更聰明」；先看 task card 是否將「未知必須標示」寫成明確、可檢查的 acceptance。若已寫清而 A 再次漏掉，才有理由進行第二輪測試。

| 測試位置 | 本輪固定內容 |
|---|---|
| 材料 | 一篇公開文章 |
| Task card | internal briefing；只引原文；未知必標 |
| Output | 三重點、兩未知、來源欄位 |
| Review | 同一 checklist、同一 owner |
| 結論 | A 要再測未知規則；B 可作暫時 default 候選 |

Jimmy 的結論是：這個結果不是工具排名，而是一條 evidence：哪個 context rule 在哪個工具下仍需要更清楚的設計或驗證。

任何一邊如果開始要求敏感資料、外發或不可逆操作，就應立即停止。replacement test 的價值來自可回退，而不是把真 project 當實驗品。

## 今日怎樣做第一個 test？先只比較一件可安全收回的小工作

不需要一次比較所有工具和所有工作。選一篇公開文章或一份 synthetic brief，寫一張不超過十行的 task card；先讓你現有工具跑一次並確認你能清楚 review，再用另一個工具跑完全相同的一張卡。

完成後只記錄 acceptance 是否通過、哪一條規則被漏掉、下一輪應修 pack 還是再測。不要為了得出勝負而調整中途材料，也不要把探索結果自動升格成 production 決定。

Jimmy 的結論是：換工具測的不是誰最聰明，而是同一份 context 能否產出同樣可 review 的工作。

第一輪照這五步便足夠：

1. 選公開或 synthetic、低風險的小工作；
2. 寫同一張 task card 與 acceptance checklist；
3. 固定材料、任務、context 和 reviewer；
4. 先判斷兩邊是否合格，再談偏好；
5. 按結果選 keep、修 pack、重測或停止。

若你發現真正問題是 context 帶不走，可讀 [換 AI 工具就要由零開始？你需要帶得走的不是所有資料，是可信 context](./3-9-換工具不必從零開始，帶走可信脈絡.md)。要持續改善已跑過的 routine，可回到 [一條 routine 跑完，下一步改甚麼？](./3-10-一條流程跑完，下一步怎樣改.md)。
