# 先用過，再決定建不建：AI 產品、服務與課程最常犯的次序錯誤

看見一個好方向時，很自然想快點把它建成：完整 Agent OS、平台、大課程、很專業的 workflow，或者一組看似已可出售的服務包。可是若你還未親手用過、看過使用者在哪裡卡、知道哪一段真的值得重複，建得愈快，浪費也可能愈大。你會得到更多功能，卻未必得到更多價值。

這不是反對 build，也不是叫人永遠手工。問題是 AI 很容易令人把「模型做得到」當成「應該產品化」。真工作的 input、例外、owner、review、交付和使用意願，往往只有在實際跑過幾次後才看得見。若在這之前已鎖死設計，例外會在最昂貴的階段才出現。

Jimmy 的看法是：先用過，不是拖慢 build；是用最低成本找到真正值得 build 的那一格。先讓一條工作被人完成、重複、review 和交接，再把穩定部分包成 template、Skill、automation 或產品；這樣 build 放大的才是 evidence，而不是想像。

use before build · AI product · AI service · AI course · workflow validation · prototype · pilot · automation

| 先用再 build 的一格 | 先要看清甚麼 | 才值得留下甚麼 |
|---|---|---|
| 真工作 | 原本怎樣完成、哪裡最痛？ | workflow map |
| 受控試行 | AI 只先做哪一手？ | approved input 與 artifact |
| 重複與例外 | 第二、三次仍卡在哪裡？ | run receipts／pattern |
| 包裝 | 哪一段可讓另一人跟？ | checklist／template／Skill |
| 他人使用 | 別人在哪裡卡、怎樣 review？ | adoption feedback |
| Build gate | 手動真的成為瓶頸嗎？ | evidence-based build decision |

## AI idea 點解不要一開始就 build：新能力的興奮不等於真工作需求

一個 Agent 看似能處理某件事，並不代表有人正為那件事付出高成本、願意改做法，或需要你建一個完整產品。最早期若只從 capability 出發，容易花很多時間做介面、integration 或功能組合，最後才發現使用者真正痛的是另一個更簡單的 handoff、資料不清，或根本沒有明確 owner。

「先用過」的第一步是把想法放進一個真但受控的情境。你要知道工作原本怎樣完成、哪一格重複最多、哪一格只是看起來新鮮、AI 需要甚麼 context、output 要怎樣被收貨。這些答案不是 build 前的行政文件，而是產品、服務或課程的原材料。

**Jimmy 的結論：** 最早期不要先問「這個 Agent 可以做甚麼」，先問「它不存在時，這個人怎樣艱難地完成哪一手工作」。真痛點未清，完整 build 通常太早。

| 一開始很想做 | 容易漏掉甚麼 | 先用怎樣驗證 |
|---|---|---|
| 做完整平台 | 使用者是否真有重複痛點 | 跟一位使用者走一次 workflow |
| 砌 agent team | 哪一手最值得交 AI | 先做一個 draft-only action |
| 接很多 integration | 資料是否真有準備好 | 用 approved input 手動跑 |
| 排滿課程章節 | 學員最常卡在哪裡 | 帶小批人完成一個 safe outcome |
| 包成大服務 | 客戶究竟買哪份交付 | 先寫一張 service card |

如果你還未能指出最近三次真使用的 input、例外和收貨方式，暫時不要加功能。先跑一次小範圍，讓真工作決定下一步。

## AI workflow 甚麼才算真的「用過」：不是試工具，而是跑到例外與收貨線

隨便打開一個工具試幾句，不叫真正用過。真正用過代表你把一個想法放到有目的、有材料、有使用者、有完成線的情境，至少能回答：它幫哪個人完成甚麼 artifact？AI 讀了甚麼？哪些 output 可用、哪些要退回？資料不足時怎樣處理？第二、三次又出現甚麼 pattern？

這種試行不必一開始用敏感真資料。公開或 synthetic 材料也可以，只要保留真工作的結構：input boundary、AI action、human review、artifact、exception 和下一輪決定。目標不是製造一場很大的測試，而是讓你遇到設計裡原本看不見的摩擦。

**Jimmy 的結論：** 「用過」的標準不是摸過工具，而是跑過一條可 review 的工作，知道它在甚麼條件下有用、在哪裡要停。

| 只算試過 | 真正用過 | 會留下甚麼 |
|---|---|---|
| 一次生成漂亮 output | 有目的、有 input、有 owner 的 run | work artifact |
| 自己覺得順 | 別人能否理解與收貨 | review result |
| 沒遇到例外 | 記下 unknown／退回／fallback | exception pattern |
| 每次由零開始 | 第二次沿用 rule／template | reusable asset |
| 工具功能很多 | 只處理一個 bounded action | scope decision |

若第一次 run 已經要靠你補十種例外，這不是失敗，而是很重要的發現。先不要 build 把複雜度固定下來；先分類例外、縮小 scope 或調整 input。

## AI product 點樣由手動變 automation：先重複、再包裝、最後才放大

健康的次序不是「想到 → build → 希望有人用」，而是「完成 → 重複 → 包裝 → 讓別人用 → 再 build」。親手完成一次，讓你看到真 workflow；第二、三次讓你看見哪些 input、例外和收貨線是穩定的；包裝成 checklist、template 或 Skill，令另一個人可以試；只有真正重複而且手動成為瓶頸的部分，才值得 automation。

這個次序不是慢，反而令 build 更精準。你不會為一次偶然的要求做長期 integration，也不會因為自己熟悉某套做法便以為別人同樣能跟。當其他人使用後留下的卡點與你原來預期不同，這正是把個人能力變成產品能力的機會。

**Jimmy 的結論：** Build 最值得放大的，是已被多次使用、可被他人理解、知道例外和 completion line 的工作單位。未經這幾步的 automation，通常只是把未知變得更快。

| 次序 | 先做甚麼 | 才知道甚麼 |
|---|---|---|
| 1. 完成 | 用人加 AI 跑一條工作 | 真正 artifact 與 owner |
| 2. 重複 | 跑第二、三次 | stable input 與例外 |
| 3. 包裝 | 寫 template、checklist、Skill | 可被描述的 method |
| 4. 他人使用 | 讓另一人按規則試 | adoption 卡點 |
| 5. Automation | 只自動固定且可 review 一手 | build 是否有淨價值 |
| 6. Scale | 加 governance 與 measurement | 是否值得擴大 |

不要把這些步驟當成硬性儀式。若 evidence 已很充足，可以加快；但若連基本 input、owner 和 artifact 仍未清楚，任何「快 build」都只是在逃避最重要的判斷。

## AI 課程點解都要先用再 build：lesson 應由真學習卡位長出來

設計 AI 課程時，很容易先把工具、術語和章節排得很完整，然後才發現學員真正卡的是「我手上到底有甚麼工作可以交出去」「哪些資料可以放進 AI」「output 出來後怎樣知道可用」。這些卡位若沒有在小批真學員身上出現過，課程很容易變成工具目錄，而非實際能力路徑。

先帶小批人完成第一個安全成果，記下他們在哪一格停下：是 context 不足、材料不敢給、review 不會做，還是根本未看見工作價值？再把反覆出現的卡位變成 lesson、template、walkthrough 或 practice。課程因此不是由工具更新長出來，而是由真學習與 feedback 長出來。

**Jimmy 的結論：** AI 課程最值得 build 的，不是講師覺得最厲害的功能，而是學員在真工作中反覆需要的一個判斷與方法。

| 先排課綱 | 先跑小批學習 | 後者帶來甚麼 |
|---|---|---|
| 按 tool 功能分章 | 按學員真工作卡位分章 | 有 stage-aware 入口 |
| 用泛用 prompt 示範 | 用 approved／synthetic task 練習 | 可安全複製 |
| 只看課堂 feedback | 看有否完成／第二次使用 | 真 adoption evidence |
| 先錄全套內容 | 先驗證一個 lesson outcome | 減少錯誤投資 |
| 一次教所有人 | 按 stage 設下一步 | 新手不被嚇怕 |

當學員最常問的是「我下一件工作怎樣開始」，下一個要 build 的通常是 first-task card 或 safe walkthrough，而不是再加十個工具比較。

## AI service 何時值得產品化：客製交付出現穩定 pattern 才包起來

做服務時，你可能已能親自解很多問題，但每個 client 都有不同資料、不同 owner 和不同例外。若太早把所有東西叫成「產品化服務」，容易承諾過大、scope 失控，或把自己腦內的判斷誤當成已可交接方法。忙碌不等於可 scale。

先留意哪一段交付已經有穩定 pattern：同類人反覆遇到同類摩擦、可用相近 input、交相近 artifact、由相近角色 review，例外也能被分類。把這一段寫成 service card、template 或 workshop module，才是比較誠實的產品化起點。其餘仍需高判斷的部分，保留在 bespoke discovery 或明確 scope 內。

**Jimmy 的結論：** Service 產品化不是把所有客製工作硬塞進一個 package；是把已被反覆跑通、可驗收、責任有邊界的一手工作包起來。

| 客製訊號 | 可以開始包裝 | 暫時不應承諾 |
|---|---|---|
| 同一 workflow pain 重複出現 | workflow diagnosis | 全公司 transformation |
| artifact 格式穩定 | template／checklist | 無限量改稿 |
| review rule 類似 | acceptance rubric | 沒有 owner 的交付 |
| 例外可分類 | escalation note | 高權限 production action |
| 手動成真瓶頸 | 有 guardrail 的 automation | 未驗證固定 ROI |

當你能用一頁說清 input、artifact、review、scope、exception 和 next decision，這一段才較接近值得 build 的 service unit。

## 一個公開安全例子：先手動跑三次 briefing，再決定是否建 Agent

假設一個團隊想建一個 Agent，把幾個公開來源變成每週 internal briefing。第一輪不接 CRM、不外發、不做 production write；只用 approved public sources，由人加 AI 起 draft、標 unknown、由 content owner review。每一次保留 source boundary、draft、退回原因和時間記錄。

跑到第三次後，團隊發現固定欄位、source format 和常見 review rule 已相對穩定，但有些情況仍要人判斷 relevance。這時可把穩定部分寫成 template 或 Skill，讓另一人試用；若第二位使用者也能完成並留下相似 evidence，才考慮把「整理與標記」自動化，而不把 owner judgment 也交出去。

**Jimmy 的結論：** 這個例子沒有一開始 build 大 Agent，卻更快找到值得 build 的核心：重複、低風險、可 review 的整理一手。先用讓 automation 有正確範圍。

| 第幾次 run | 學到甚麼 | 下一步決定 |
|---|---|---|
| 第一次 | input 是否齊、artifact 是否可用 | 補 source boundary |
| 第二次 | 哪些規則可重用、哪裡常退回 | 寫 checklist |
| 第三次 | 手動哪一手真成瓶頸 | 包成 template／Skill |
| 他人試用 | adoption 卡在哪裡 | 改說明或 scope |
| Evidence 足夠 | 是否值得自動化固定一手 | build／continue manual／stop |

這是 synthetic 教學情境，不代表任何特定 Agent、團隊或產品已有相同成果。它要說明的不是 build 慢，而是 evidence 令 build 更值得。

## 今日怎樣判斷下一個 AI 項目要不要 build：先補一個最小 evidence gap

挑一個你最想 build 的項目，然後問五條：最近三次真使用的 input 是甚麼？output 要由誰收貨？哪個例外最常出現？另一個人能否按你的方法完成？手動處理是否已成真正瓶頸？每條答案都不是肯定時，下一步通常是跑小範圍、補 receipt 或寫 template，而不是加功能。

如果你已能答到這些，便不是永遠拖著不 build；你有足夠理由把最穩定的一手自動化或產品化。Build 的範圍仍要保留 input boundary、review、stop line 和 rollback，讓新的效率不會換來新的不可控風險。

**Jimmy 的結論：** 先用再 build 的今日行動，是找出一個最小 evidence gap，先用低成本補它。當 build 真正開始時，它放大的會是已驗證的工作價值。

| 問題 | 答不到時先做甚麼 | 答得到後可考慮甚麼 |
|---|---|---|
| 有真 workflow pain 嗎？ | discovery／manual run | 定 first product scope |
| input／artifact 清楚嗎？ | work card | template／integration |
| 例外有 pattern 嗎？ | run receipts | guardrail／fallback |
| 別人能用嗎？ | guided trial | onboarding／productization |
| 手動是瓶頸嗎？ | 比較 rework 與等待 | automation decision |

想把第三次才出現的規則寫成 SOP，讀 [第三次先寫 minimum SOP](<../../03-AI Operator（AI工作操作者）/chapters/3-7-第三次再寫標準作業程序，做法通常更穩.md>)；想把一次成功的示範變成可重用 Skill，讀 [示範過一次後，怎樣變成 Skill？](<../../04-AI Builder（AI建立者）/chapters/4-11-由示範變成可重跑技能.md>)。
