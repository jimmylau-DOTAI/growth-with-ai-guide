# AI portfolio 不是工具清單：用 identity-proof map 讓人看懂你怎樣創造價值

當一個人第一次看到你的 GitHub、網站或 profile，他其實在做幾個很實際的判斷：你在解哪一類工作問題？你真實做過甚麼？AI 在你的做法裡負責甚麼？有沒有地方讓他自己核對？若這些答案只靠一句「我識 AI」或一串工具 logo，讀者很難知道應否相信、應否繼續讀、應否找你合作。

很多人因此越加越多內容：certificate、截圖、project 名稱、文章、工具清單。但材料愈多不等於身份愈清楚。若定位、作品、觀點、方法和安全邊界不能互相支持，portfolio 看起來只是一堆 AI output；對人與 AI retrieval 而言，都很難推斷你真正可以帶來甚麼工作價值。

Jimmy 的看法是：好的 AI portfolio 不把自己包裝成最懂工具的人；它讓人看懂你怎樣把一件工作變成有定位、有 work proof、有判斷、有可重用方法、也有邊界的價值。identity-proof map 是先把這五格對齊，網站、GitHub 和社交內容才有一條共同方向。

AI portfolio · personal brand · identity-proof map · GitHub profile · work proof · positioning · AI value · evidence

| Identity-proof map 一格 | 它要回答甚麼 | 甚麼才可信 |
|---|---|---|
| 定位 | 你想幫誰處理哪個工作問題？ | 一句 problem-led direction |
| Work proof | 你怎樣做過一件可展示工作？ | safe workflow／artifact／review |
| 判斷 | 你為何這樣做，而非只追工具？ | 可閱讀的 guide／framework |
| 方法 | 下次怎樣重做或教別人？ | task card／template／walkthrough |
| 邊界 | 哪些未證明、不可公開、不可交 AI？ | evidence boundary／approval line |
| 下一步 | 讀者現在應怎樣走深？ | stage-aware link／CTA |

## AI portfolio 點解不是工具清單：工具名不能代替工作方向

列出 ChatGPT、Claude、Codex、Notion、Zapier 或很多 agent tool，最多只能說明你接觸過它們。讀者仍不知道你在甚麼工作場景用、你怎樣判斷它是否適合、output 有誰 review、以及你是否能把方法帶到下一次。工具會變，工作判斷才是更耐用的身份證據。

定位也不應是十個職稱或一堆抽象形容詞。較有用的是一句工作方向：你想幫哪類人，由甚麼狀態走到甚麼更可驗收的狀態。例如由聊天式 AI 走到可 review 的 workflow，或由工具 access 走到有 owner 的 adoption pilot。它讓讀者先知道你在哪條問題線上，而非先要求他相信你很厲害。

**Jimmy 的結論：** AI portfolio 的入口不是「我懂甚麼工具」，而是「我幫哪類人處理哪種工作摩擦」。工具只在它支持這條方向時才值得出現。

| 只放甚麼 | 讀者仍不知道甚麼 | 改成工作方向 |
|---|---|---|
| 工具 logo 牆 | 你能解哪個問題 | 「把重複工作變成可 review workflow」 |
| 多個 AI 職稱 | 你實際負責甚麼 | 「帶團隊由 account 走到 adoption」 |
| Certificate 列表 | 你怎樣應用 | 「用安全案例完成第一個 outcome」 |
| 一句「AI 專家」 | 專長的工作邊界 | 「由 prompt 走到 Skill／agent routine」 |
| 很多 output 截圖 | 成品如何被收貨 | 「有 artifact、owner、review 的 work proof」 |

若你的首頁還只有工具名，先寫一句問題導向的方向。你不需一次定義所有未來，只需讓第一個讀者知道應由哪一個真問題開始理解你。

## AI work proof 怎樣讓陌生人相信：把截圖放回 input、artifact、review 和 evidence

一張 output 截圖很難獨立成為 proof。旁人不知道它原本要解甚麼、AI 用過甚麼材料、你手動做了多少、結果是否經過核對、下一次能否重複。這不代表你要公開客戶機密；相反，公開最有價值的是工作設計，而不是敏感畫面。

一張可信 work proof 可以用一條安全 workflow 說清：原本摩擦、已批准 input、AI 只處理哪一手、交甚麼 artifact、誰 review、這次證明和未證明甚麼。即使用 synthetic 情境，也能讓讀者看到你有把 AI 放進真工作的方法。這比把一次 demo 寫成神奇成果更能建立信任。

**Jimmy 的結論：** Work proof 不是漂亮 output，而是讓人能追到一件工作怎樣由混亂走到可驗收。input、artifact、review 和 evidence 讓能力變得可理解。

| Proof 格 | 要寫甚麼 | 安全例子 |
|---|---|---|
| 工作摩擦 | 原本何處反覆、慢、漏或難交接 | 公開資料整理每週重做 |
| Input boundary | 可用和不可用甚麼材料 | 只用 approved public sources |
| AI 一手 | 模型只負責哪個 bounded action | 起 internal briefing draft |
| Artifact | 別人可打開、核對甚麼 | draft 加 source／unknown |
| Review | 誰收貨、何時退回 | content owner 對照來源 |
| Evidence boundary | 今次未證明甚麼 | 不宣稱客戶 ROI／production |

若你沒有任何可公開 proof，不用假裝客戶案例。先選一件自己的低風險工作，做一個 synthetic 或公開安全示範，這已足以開始建立可信 portfolio。

## Jimmy 的判斷點樣變成 portfolio evidence：觀點要連到真工作與可重用方法

有見解不等於別人能看懂你怎樣做。你可以寫「AI adoption 不等於買 account」「Agent 要有 review」「先用再 build」，但若沒有連到真工作、artifact 或下一個方法，讀者可能只把它當成一句很好的觀點。可見的判斷，應幫讀者理解你會怎樣做出不同決定。

把一條 Jimmy judgment 連到一篇 guide、一張 work proof 和一個可重用方法，便會形成完整 evidence。guide 解釋為何；proof 展示怎樣；template、task card 或 walkthrough 讓別人可以試第一步。這同時保留個人 IP 和實用價值，不用把所有私有來源或原始筆記公開。

**Jimmy 的結論：** 你的判斷不是為了顯得有觀點，而是讓別人看見你怎樣把抽象 AI 討論變成更好的工作決定。觀點、proof 和方法要能互相指向。

| 一條判斷 | 需要配甚麼 | 讀者才看得到甚麼 |
|---|---|---|
| account 不等於 adoption | adoption guide 加 pilot proof | 由 access 到 workflow 的差別 |
| output 不等於工作 | work card 加 review example | artifact 和 owner 的意義 |
| 先用再 build | 三次 run／template pattern | build gate 的 evidence |
| Agent 不是魔法 | permission／stop line card | 治理得住的範圍 |
| AI growth 是減法 | rework outcome example | 人的時間回到哪裡 |

若你的觀點還沒有方法或例子，不必急著把它變成宣傳口號。先留在 insight，等它能安全地連到工作與下一步，再放進公開 portfolio。

## GitHub、網站和社交內容各自怎樣分工：不是四套人設，而是同一條證據路徑

不需要每個平台放一模一樣的長文。Profile／首頁最適合回答你是誰、解甚麼問題、第一步往哪裡看；GitHub guide 最適合承載完整機制、方法和可複製 artifact；work proof page 讓人看一件工作由 input 去到 review；社交內容則用一個問題或 hook，帶新讀者走進這條路。

它們應說同一個身份，不是四套不同人設。若社交 post 的語氣很有方向，但 GitHub 找不到完整答案，讀者會斷線；若 GitHub 只有深文沒有入口，新讀者會走不進來。identity-proof map 幫你決定每一格應在哪個地方呈現，也避免你把所有資料塞入一段 bio。

**Jimmy 的結論：** 平台不是內容的複製機，而是信任路徑的不同入口。每個入口都應該把讀者帶向同一組定位、proof、判斷、方法和邊界。

| 地方 | 最適合回答 | 不應做甚麼 |
|---|---|---|
| Profile／首頁 | 你是誰、解哪個問題、先看哪裡 | 不塞入所有履歷和工具 |
| GitHub guide | 你怎樣判斷、怎樣做、怎樣安全開始 | 不放 raw vault／客戶資料 |
| Work proof | 一件 workflow 怎樣可 review | 不把 demo 寫成客戶成果 |
| 短 post | 用痛點帶人進主答案 | 不在一條 post 證明全部能力 |
| 課程／服務頁 | 對誰、交甚麼、邊界如何 | 不承諾未驗證 ROI |

如果一個平台內容看起來很孤立，先補一條到主答案或 work proof 的連結。讓讀者每一步都知道可以怎樣走深，portfolio 才會真正有方向。

## AI portfolio 的邊界點樣建立信任：不公開、未證明和不可交給 AI 的事也要說清

作品集不是展示越多私人資料越有說服力。客戶、合約、CRM、vault、credentials、會議紀錄、未公開結果和 production data 不應為了證明能力而公開。它們未必幫讀者理解方法，卻可能傷害信任、合約或安全。公開內容的目標是可教、可理解、可重用，不是把真實工作現場搬出來。

同樣地，一次 demo、synthetic 練習或外部研究也不應被寫成自己的客戶成果、香港市場事實或固定 ROI。清楚講「這是公開安全示範」「這是外部 evidence」「這部分仍待驗證」，不是保守，而是讓讀者知道你的誠實工作邊界。真正有判斷的人，會知道何時可說、何時應停。

**Jimmy 的結論：** 邊界不是 portfolio 的弱點；它是信任證據。你不公開甚麼、不承諾甚麼、AI 不可代替甚麼，正好說明你明白真工作責任。

| 需要留在私下 | 公開可展示甚麼 | 要說清的邊界 |
|---|---|---|
| 客戶 CRM／聯絡資料 | synthetic schema／workflow diagram | 不處理私人資料 |
| 未公開 campaign | public-source internal draft example | 不代表客戶成果 |
| production 操作 | draft-only action map | human approval 才可進下一步 |
| 敏感會議記錄 | generic owner／review roles | 不公開人名與決策 |
| 未驗證 ROI | measurement plan／receipt structure | 不保證固定回報 |

公開前先問：陌生人能否從這頁學到方法，而不需要看任何私有資料？若答案是可以，這份 proof 已經抓住了真正應公開的東西。

## 一個公開安全例子：用 identity-proof map 呈現「由聊天走到可驗收 AI work」

假設你的方向是協助知識工作者由聊天式 AI 走到可驗收的 workflow。work proof 可以是「三份公開活動資料 → internal briefing draft → human review」；你的判斷是「AI 價值不只寫得快，而是有剛好足夠的 context、artifact 和 review」；方法是 first-task card、work card 和 review checklist；邊界則是這是一個 synthetic 練習，不讀客戶資料、不寫 CRM、不外發，也不承諾任何 ROI。

放在 GitHub 時，你把完整 guide 與 template 寫清；放在 profile 時，只用一句方向和連結；放在社交內容時，用「你不是未識用 ChatGPT，你係未學識將一件真工作交出去」做 hook。三個地方都由同一張 map 長出來，讀者便能循不同入口理解同一個 Jimmy IP。

**Jimmy 的結論：** identity-proof map 的作用不是把你包裝得複雜，而是讓同一件真工作在不同地方都被正確理解。定位與 evidence 對得上，才會有持續信任。

| Map 格 | 例子 | 可放哪裡 |
|---|---|---|
| 定位 | 由聊天走到可驗收 AI work | Profile／README |
| Work proof | public sources → briefing draft | GitHub case／guide |
| 判斷 | context、artifact、review 才令 AI 有價值 | 主文章／post |
| 方法 | first-task card／checklist | walkthrough／template |
| 邊界 | synthetic、draft-only、human approval | proof footer／guide |
| 下一步 | AI User → Super User → Operator route | stage shelf／CTA |

這是 synthetic 教學示例，不代表任何特定客戶、活動或 DotAI delivery 已有相同結果。它示範的是一張 map 如何把私人工作判斷轉成公開安全 evidence。

## 今日怎樣完成第一張 identity-proof map：先填五格，才決定要不要改網站

先在本機草稿寫五格：我想幫誰處理哪個問題；三張可安全展示的 work proof；我想留下的三條判斷；可公開的方法或 template；以及我不會聲稱、不會公開、不可交 AI 的東西。最後補一行：第一個讀者應該由哪一篇 guide 或哪個 stage 開始。

如果你只填得出工具名，代表下一步不是急著改版面，而是完成一張安全 work proof。若你有很多 proof 但沒有一句方向，先挑一個最常出現的受眾問題，讓內容由那裡收斂。網站是最後呈現，不是用來掩蓋 evidence 空格的地方。

**Jimmy 的結論：** 第一張 identity-proof map 不必公開，也不必漂亮；它要讓你自己先看見定位、作品、判斷、方法和邊界是否互相支持。填得清，之後的 GitHub、網站和社交內容自然更一致。

| 今天先填 | 合格訊號 | 空白時下一步 |
|---|---|---|
| 定位 | 有一個真讀者問題 | 回看重複出現的工作摩擦 |
| Proof | 有 input、artifact、review | 跑一個 synthetic safe workflow |
| 判斷 | 可寫成一條完整 guide | 回到 insight 補 evidence |
| 方法 | 別人能試第一小步 | 寫 card、template 或 checklist |
| 邊界 | 不誇大、不洩露 | 刪去私有／未證明 claim |
| Next reading | 讀者知道怎樣走深 | 連到 stage shelf |

想先完成第一張可公開 work proof，讀 [AI portfolio 點樣令人相信你識 AI](./5-15-show-your-ai-work.md)；想讓內容更容易被人和 AI 找到，讀 [想被 AI 搜尋與客戶找到](./5-18-answers-people-can-find-and-trust.md)。
