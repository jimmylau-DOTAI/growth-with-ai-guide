# 唔好問「你第幾級」：用一件真工作診斷 AI 下一步

「你識唔識 AI？」「你現在第幾級？」這些問題答了通常沒有用。有人每天用 AI，仍然只是在問問題；有人只用一個工具，卻已經把一條工作交接得很穩。若只看工具數、職位或自評分數，帶領者很容易給錯下一步。

較準的診斷不是評價一個人，而是看一件最近真工作在哪裏斷掉：任務是否清楚？資料是否有可信 context？做法能否交接？AI 有沒有 quality gate 和 stop line？又是否已有人能帶其他人跑 pilot？這些是工作 evidence，不是身份標籤。

Jimmy 的看法是：最準的 AI stage 診斷，不是你講自己識幾多工具，而是最近一件工作卡在哪一個可見的交接位。用十五分鐘、一件低風險真工作和五條 evidence 問題，找最早斷點，再設計一個相鄰、可 review 的練習。

| 最早答不清的工作格 | 最接近入口 | 先留下甚麼 artifact |
|---|---|---|
| 任務、材料、完成線模糊 | AI User | 小 work brief |
| 每次都重講 context／標準 | AI Super User | context pack／review checklist |
| 做法重複但交不到下一手 | AI Operator | current-state note／handoff |
| 有流程但未有 gate、control、evidence | AI Builder | work card／run receipt |
| 想帶人擴大但無 owner、pilot、outcome | AI Value Creator | pilot canvas／outcome card |

## 自評與工具數點解診斷唔到下一步：它們看不到工作真正卡位

自評問卷常問「你覺得自己多熟悉 AI」，工具清單則問「你用過幾多 app」。兩者都可以做開場對話，卻無法告訴你某一條工作下一步需要甚麼。熟悉很多功能的人，可能仍沒有安全 input 或 reviewer；只用一個工具的人，可能已累積很成熟的 context、handoff 和 outcome evidence。

職級也不是答案。manager 不一定知道一條 workflow 的最早 input 缺口，初級同事也不一定缺乏判斷。把 stage 變成能力認證、招聘、薪酬或績效工具，會令對方想答「正確」的答案，而不再誠實展示真工作。這正好失去診斷的目的。

**Jimmy 的結論：** 診斷要看工作，不是看人。只要用最近一件可回看的工作，帶領者就能避開工具焦慮與身份標籤，直接找到最小下一步。

| 常見診斷方法 | 它容易誤導甚麼 | 真工作診斷改問甚麼 |
|---|---|---|
| 「你用過幾多工具？」 | 工具數等於成熟 | AI 在這件工作做了哪一手？ |
| 「你覺得自己幾級？」 | 信心等於能力 | 哪一格 input／review 答不清？ |
| 「你是甚麼職級？」 | 職位等於 owner | 誰實際驗收與處理例外？ |
| 「有冇上過堂？」 | Knowledge 等於 Ability | 返工時可否留下 artifact？ |
| 「有冇做過 demo？」 | 一次成功等於可重複 | 跑過幾次、見過甚麼例外？ |

當診斷從自我形象回到一件真工作，答案會變得可以行動：不是「你還未夠高級」，而是「先補這一格 context 或 handoff」。

## 15 分鐘真工作診斷怎樣開始：選一件最近做過、下星期還會再做的事

診斷不需要準備大量資料。請對方帶一件上星期完成、下星期很可能又會做的低風險工作，例如整理公開資料、起一份 internal draft、準備會議議程或做一張工作表。不要選「我想學 Agent」這類願望，因為願望沒有 input、artifact 或 review 可看。

先用兩分鐘聽對方描述原本工作：誰開始、哪裏最煩、最後交甚麼。這已經能幫你判斷問題是在工作本身，還是在工具。接著才問五條 evidence 問題，不急著教工具、不急著給答案，讓對方用具體例子說出現在 workflow 的樣子。

**Jimmy 的結論：** 診斷的起點不是一個 AI 目標，而是一件真工作。最近、重複、低風險的工作最有用，因為它有機會在下一輪立即留下新 evidence。

| 適合帶來診斷的工作 | 為何適合 | 不適合起步的題目 |
|---|---|---|
| 公開文章整理成 brief | source 與 artifact 可回看 | 「我想學 AI Agent」 |
| FAQ draft | 格式、review、unknown 可見 | 「我想用最潮工具」 |
| 會議議程草稿 | owner 與完成線較清楚 | 「我要自動化全公司」 |
| 重複資料整理 | handoff 與 rework 易看見 | 高風險客戶／付款資料 |
| 內部 content outline | 可在 draft 層試行 | 直接對外發送任務 |

若對方帶來的是一件高風險或敏感工作，也不要為了診斷而要求他分享私人 chat、客戶資料或未批准文件。先用公開或去識別化版本理解 workflow。

## 五條 evidence 問題怎樣找最早斷點：由 input 追到 owner，不先追工具

五條問題依序是：資料從哪裡來？誰決定內容或品質？AI 現在做了哪一步？它交甚麼 artifact 給誰？出錯時誰可以停止？它們看似簡單，卻涵蓋了 context、authority、handoff、review 和 escalation。最早答不清的地方，通常就是現在最值得補的一格。

例如如果對方說不清 input 或完成線，AI User 是合適入口；有任務但每次重講格式、例子和標準，則先補 AI Super User 的 context；能穩定做但交不到同事，才是 AI Operator；已有 workflow 卻怕跑錯或越權，才進 AI Builder；想帶人擴大而未有 pilot、owner、outcome，才需要 AI Value Creator 的工作。

**Jimmy 的結論：** 不用把五條問題當考試。它們是把 AI workflow 拆開來看；第一個空白格，比所有後面的工具建議都重要。

| Evidence 問題 | 它實際檢查甚麼 | 答不清時的入口 |
|---|---|---|
| 資料從哪裡來？ | approved input 與 context | AI User／Super User |
| 誰決定內容或品質？ | reviewer 與 owner | Super User／Value Creator |
| AI 現在做哪一步？ | bounded task | AI User／Builder |
| 交甚麼 artifact 給誰？ | handoff 與可回看結果 | Operator |
| 出錯時誰可停止？ | control 與 escalation | Builder／Value Creator |

不要等五條都完美才開始。找到最早缺口後，只補一格，然後在下一輪真工作看它有沒有改善。

## 最早斷點怎樣對應五個 stage：不是升級路線，而是選練習入口

stage 地圖的用途不是把人分類，而是幫你選合適練習。任務、材料、完成線都未清楚，就先做 AI User 的小 work brief；每次都要重講背景，就做 AI Super User 的 context pack；重複工作未能交接，就做 AI Operator 的 current state；有 workflow 卻缺 gate，就做 AI Builder 的 work card；想帶其他人跑，才做 AI Value Creator 的 pilot canvas。

這些入口可以因工作而不同。有人可以在公開內容工作走到 Builder，但在涉及客戶資料的 workflow 仍只應停在 User 或 Super User；這反而代表他理解風險，而不是不夠成熟。下一步由工作證據決定，不由頭銜決定。

**Jimmy 的結論：** stage 是為一件工作找入口，不是給一個人貼永久標籤。只補最早一格，才能令成長變小、清楚和可驗收。

| 最早斷點 | 不要急著做 | 最小相鄰練習 |
|---|---|---|
| 任務／材料／完成線模糊 | 造 automation | 寫一張 work brief |
| Context 每次重置 | 換模型 | 做 context pack |
| 交接不清 | 開多個 Agent | 寫 current-state／handoff |
| 沒有 quality gate | 加大權限 | 做 checklist／stop rule |
| 無 owner／pilot | 宣布團隊轉型 | 填 pilot canvas |

當一個練習完成，才再次用同一件工作診斷。這讓 stage 不是一條抽象階梯，而是一個不斷回到真 workflow 的學習 loop。

## 一個公開安全例子：每週 internal draft 為何先要補 context，而不是直接 automation

假設有人每星期用 AI 將公開資料整理成 internal draft，但每次都要大改，也不敢交給同事。五問後發現：他知道 output 是甚麼，但沒有固定的已批准材料、格式、禁用 claim 和 reviewer。最早斷點不是 automation，而是 context。

所以先走 AI Super User：做一頁 context pack，加一張 review checklist，清楚列出可用 source、每個 claim 要有 link、推論要標記、資料不足便停。下一輪再看是否格式更穩、reviewer 是否少退回、工作是否真的重複到值得寫 handoff。這時才可能走向 AI Operator，而不是接 CRM 或自動發送。

**Jimmy 的結論：** 這個例子顯示診斷的價值在於阻止過早 build。當最早缺口被補好，下一個 stage 會自然出現；不用靠一個很大的 AI 計劃硬推。

| 五問結果 | 發現的狀態 | 正確下一步 |
|---|---|---|
| 資料從哪來 | 沒有固定 approved source | 建 source bundle |
| 誰決定品質 | reviewer 未定 | 指定 content owner |
| AI 做哪一步 | 只知「幫我整理」 | 限成 internal draft |
| 交甚麼 artifact | 沒有固定格式 | 建 brief template |
| 出錯誰停止 | unknown 未定義 | 加 stop rule |

這個例子只使用公開資料和 internal draft，不允許 AI 接觸 CRM、客戶／私人資料、外部發送、公開設定或 production 系統。

## 診斷時有咩不可做：不把 stage 變成績效工具，也不為了完整而收敏感資料

stage 診斷不應被用作能力認證、招聘、薪酬、績效或職級工具。當人覺得答案會影響評價，他自然會隱瞞困難、誇大工具使用，診斷就失去真實 evidence。它的目的只是為下一個學習或 workflow step 找到合適入口。

同樣地，不要為了了解 workflow 而收集客戶資料、私人 chat、付款資料或未批准文件。診斷只需要看工作形狀，不需要看敏感內容；公開、去識別化或 synthetic 例子已足夠。更不要因一次低風險 draft 成功，就推定這人可以處理高權限或不可逆工作。

**Jimmy 的結論：** 好診斷保護人與資料。它只收集找下一步所需的最小 evidence，不評分、不貼標籤，也不把一件安全練習誤當成高風險授權。

| 不應做的事 | 為何有風險 | 正確替代 |
|---|---|---|
| 用 stage 決定績效／職級 | 人會答「應該」而非真實 | 用它設計練習 |
| 要求分享私人原始資料 | 不必要擴散敏感內容 | 用公開／去識別化例子 |
| 一次成功就加權限 | 證據範圍太小 | 重跑、review、設 stop line |
| 只問工具清單 | 看不到 workflow 缺口 | 問五條 evidence 問題 |
| 將困難當能力不足 | 忽略工作設計問題 | 找最早斷點 |

如果你對資料邊界或授權有不確定，正確診斷結果是 stop 並找 owner 澄清，而不是要求更多資料來「補完整」。

## 今日怎樣做一次十五分鐘診斷：最後只寫最早卡位、下一個 artifact、下次 reviewer

找一位想用 AI 的人，只叫他帶來一件已完成的低風險工作。用五條問題聽十五分鐘，最後不要給一大堆建議，只寫三句：最早卡位、下一個 artifact、下次誰 review。這三句會把對話由泛泛的 AI 焦慮轉成一個能做的相鄰練習。

下次見面時，不問「感覺有冇好啲」，而是看新的 artifact、返工原因、unknown 是否被標記，以及 owner 是否願意接手。這會讓診斷本身變成一個小 learning loop；如果 evidence 顯示最初判斷錯了，就改入口，而不是硬要人走原定 stage。

**Jimmy 的結論：** 最準的 AI stage 診斷，不是你講自己識幾多工具，而是最近一件工作卡在哪一個可見的交接位。十五分鐘、五條問題、三句結果，已經足夠開始。

| 診斷收尾三句 | 你要寫甚麼 | 一個示例 |
|---|---|---|
| 最早卡位 | 第一個答不清的格 | context 沒有固定 |
| 下一個 artifact | 相鄰可 review 練習 | source／review checklist |
| 下次 reviewer | 誰會看新結果 | content owner |
| 停止線 | 資料不足時怎處理 | 標 unknown，不猜 |
| 下次 evidence | 怎樣知道有改善 | 格式／退回原因 |

先用公開、低風險的工作跑一次。未完成這個小練習前，不要用 stage 結果評價人，也不要將 AI 接到外部發送、客戶／私人資料、公開設定或 production。下一步可看 [如何診斷 AI adoption bottleneck](./5-13-diagnose-adoption-bottleneck.md)。
