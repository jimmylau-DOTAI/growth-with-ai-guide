# AI portfolio 點樣令人相信你識 AI：先讓人看見你怎樣完成一件工作

你想讓人知道自己不只是「識用 ChatGPT」，於是放上工具 logo、漂亮 output 截圖、學過的課程和一堆 project 名稱。這些東西可以讓人知道你接觸過 AI，但一個準備合作、聘請你或交一條 workflow 給你的人，通常仍會問：你實際怎樣理解問題？AI 做了哪一手？有錯時誰收貨？

問題不在於你沒有能力，而在於能力若只以工具名和成品出現，旁人看不見中間的判斷。一張漂亮圖未必代表能重複交付；一次成功 output 也未必代表知道甚麼資料不能放進去、何時應停、以及怎樣讓另一個人接手。工具愈多，這個落差反而愈明顯。

Jimmy 的看法是：可信的 AI portfolio 不需要公開客戶資料或吹大成果；它要讓人看見你怎樣把一件混亂的真工作，切成有材料邊界、有 artifact、有人 review、也留下下一輪判斷的 AI work proof。你展示的不是「AI 幫我做過甚麼神奇事」，而是你怎樣用 AI 把工作帶到可驗收。

AI portfolio · AI work proof · AI project 展示 · workflow · artifact · human review · evidence · GitHub

| AI work proof 的一格 | 它要解哪個信任問題 | 最後留下甚麼 |
|---|---|---|
| 真工作摩擦 | 原本哪一步反覆、慢、漏或難交接？ | 一句具體 problem statement |
| 範圍與材料 | AI 只做哪一手、可讀甚麼？ | input boundary 與 out-of-scope |
| 可收貨 artifact | 對方如何看見今次交付？ | brief、draft、card、checklist 或 receipt |
| Review 與例外 | 誰可判斷可用，錯了怎樣停？ | owner、acceptance rule、stop line |
| Evidence 與下一輪 | 今次證明了甚麼，還未證明甚麼？ | outcome note 與 retain／revise／stop decision |

## AI portfolio 只放工具截圖點解不夠：別人看不見你怎樣處理真工作

工具截圖只證明一件事：某個工具在某個瞬間出過一個結果。它不能說明原本工作是甚麼、你為何選這一段交給 AI、用了哪些已批准材料，也不能證明 output 有沒有被人核對。若讀者無法看見這些，便很難判斷你是剛好做出一次結果，還是真的懂得把 AI 放進工作。

很多 portfolio 因此會有一個奇怪情況：頁面愈多工具、看起來愈熱鬧，但一有人問「你可以幫我處理哪條 workflow？」便講不清。真正增加信任的，不是再加第 21 個工具，而是讓一條工作有開頭、有邊界、有交付、有 review，令別人知道你做事的方式可以被理解。

**Jimmy 的結論：** AI portfolio 的主角不應是工具，而應是一條被你處理過的工作。工具截圖可以做輔助證據，但不能代替 work proof。

| 只展示甚麼 | 讀者仍然不知道甚麼 | 加回哪一格才可信 |
|---|---|---|
| ChatGPT／Codex 截圖 | 原本問題與 AI 責任 | workflow pain 與 scope |
| 一張好看的 output | 有沒有驗收、能否重複 | artifact 與 review rule |
| 20 個工具 logo | 你能為哪種工作創造甚麼改變 | 一個具體 work case |
| 一句「提升效率」 | 效果如何量、是否只是一時 | evidence boundary |
| 客戶名單或敏感畫面 | 是否安全、是否可公開 | synthetic／公開安全例子 |

先選一件你已經重複做過、能安全抽象的工作，往往比再整理一次工具清單更值得放在 portfolio。讀者能沿著問題到交付去理解你，也會知道你不是把模型 output 當作最後答案。

## AI work proof 應該展示甚麼：由工作摩擦去到可驗收 artifact

一張 AI work proof 不必一開始做成很長 case study，更不必先起完整網站。它只要讓人完整看見一次工作交接：原本何處卡住、AI 只處理哪一段、需要甚麼 context、最後交出甚麼，以及哪個人會按甚麼標準 review。這五格齊了，讀者才可以判斷這件事是否適合自己的情況。

artifact 是這裡最容易被忽略的部分。artifact 不是「AI 生成了一段文字」，而是別人可以打開、核對、退回或接手的東西，例如一份 internal brief、一張 work card、一個 draft、一份 checklist，或一次 run receipt。它把聊天視窗裡的暫時 output，變成工作流程裡可管理的一手。

**Jimmy 的結論：** 一份好 proof 要展示可被收貨的工作，而不是展示 AI 的表演。問題、邊界、artifact、review 和 evidence 缺任何一格，都容易令人誤會能力或風險。

| Work proof 格 | 要交代的內容 | 公開安全寫法 |
|---|---|---|
| 工作摩擦 | 哪一步最常重做、漏資料或等人回覆 | 「公開來源整理常反覆重做」 |
| AI 範圍 | AI 只代勞哪一手 | 「先起 internal briefing draft」 |
| 材料邊界 | 可用與不可用的 input | 「只用已批准公開資料」 |
| Artifact | 最終可檢查交付 | 「來源對照 brief 加 unknown 標記」 |
| Review | 誰收貨、甚麼情況退回 | 「content owner 對照原文 review」 |
| Evidence | 今次只想確認甚麼 | 「看 rework 原因與 review 時間」 |

當你能把一件工作寫到一個陌生人也看懂，這份 proof 已經比只列出「懂 AI agent、懂 automation」具體得多。它亦為你日後的 GitHub 攻略、課程示範、提案或服務卡留下可重用的核心。

## AI project 怎樣由聊天示範變成 workflow proof：先說清 AI 沒有做甚麼

很多人做 AI project 時，會只示範「輸入這段 prompt，模型就做到這個 output」。這種示範對學工具有用，但仍未足以讓別人把它當成工作方法。因為真工作裡最重要的判斷，往往不是 AI 做了甚麼，而是它暫時不可以做甚麼：不可自行對外發送、不可決定敏感內容、不可把不完整資料當成事實。

把限制講清不會令 project 變弱。相反，當讀者看到你會為 input 劃線、會標 unknown、會留下 human approval，他會更容易相信你知道真實使用環境的摩擦。尤其當你的受眾是公司、團隊或準備從聊天走到 workflow 的人，這份克制正是專業的一部分。

**Jimmy 的結論：** AI project 的可信度，來自清楚展示「可以交甚麼」和「暫時不能交甚麼」。先做 draft-only、可 review 的一手，比假裝 autonomous 更值得被信任。

| 示範時常見說法 | 容易造成的誤會 | 改成可驗收的 workflow proof |
|---|---|---|
| 「AI 幫我自動出內容」 | 以為可以直接發佈 | AI 起 draft，owner review 後才決定 |
| 「Agent 幫我做 research」 | 以為所有資料都可靠 | 只讀 approved sources，unknown 要標記 |
| 「自動寫入系統」 | 以為可直接接 production | 先輸出可 review 的 table／receipt |
| 「節省很多時間」 | 以為已有穩定 ROI | 記錄 review 時間、rework 與例外 |
| 「AI 代替人」 | 忽略 owner 與責任 | 寫清人保留的判斷與 approval |

如果你現在只有一次聊天或一次 demo，不用急著把它包裝成很大的 case。先加一個範圍、一次 review 和一個可留低 artifact；它就開始由展示變成可信的 workflow proof。

## AI portfolio 案例怎樣公開才安全：不公開客戶資料也可以展示判斷

想展示真實能力，不等於要把客戶名、會議記錄、CRM 畫面、未公開方案或 production 成果放到 GitHub。這些資料一旦公開，未必為讀者增加多少理解，卻可能傷害客戶、合約或未來合作。公開 portfolio 最重要不是「越真越多」，而是讀者能否理解你的工作判斷。

更好的做法是抽象工作結構，再用公開或 synthetic 情境示範。你可以保留流程的摩擦、AI 的範圍、artifact、review 和量度方法，但移除真實人名、敏感資料、未驗證數字與專屬商業條件。這樣既保留教學價值，也不把私人工作變成內容素材。

**Jimmy 的結論：** 公開 proof 應展示工作方法與邊界，不應展示別人的資料。安全抽象不是削弱案例，而是令你的判斷能被更多人理解和重用。

| 不適合公開 | 可公開的安全替代 | 讀者仍可學到甚麼 |
|---|---|---|
| 客戶 CRM／聯絡資料 | synthetic 欄位與假資料 | 資料結構與 handoff |
| 未公開 campaign／offer | 公開來源 brief 情境 | content review 的流程 |
| 真實 ROI／內部 KPI | 未驗證成效邊界與量度方式 | 怎樣看 evidence |
| 會議記錄與人名 | 角色化 owner 與情境 | 誰在何時決定 |
| production 操作截圖 | draft-only workflow diagram | AI 與 human 的責任分工 |

公開前問自己：一個陌生人是否能從這篇 proof 理解做法，而不需要看到任何私人資料？若答案是可以，代表你已經保留了最重要的部分；若不可以，先補 workflow 說明，不要補敏感畫面。

## AI work proof 怎樣寫得不誇大：分清已證明、正在測試與仍然未知

AI project 很容易令人很快把一次順利 run，講成「已經有效」「已經自動化」或「可用於所有團隊」。但一次 output 只是一次 output；它未必經歷過不同 input、例外、不同 owner 的 review，也未必證明下次會同樣可靠。越早分清 evidence boundary，越容易累積長期可信度。

你不用因此等到有完美數字才公開。你可以誠實地寫：今次先證明甚麼，例如可以把公開來源整理成一份可 review 的 draft；還未證明甚麼，例如能否直接對外發送、能否處理敏感資料或是否節省固定時間。這種寫法讓讀者知道哪一部分可以借鏡，哪一部分仍要自行驗證。

**Jimmy 的結論：** 不誇大的 proof 不是弱 proof。它把「已看到的變化」和「仍要驗證的假設」分開，令下一輪工作有更清楚的方向。

| 你可以說的 evidence | 暫時不要當成甚麼 | 下一輪怎樣驗證 |
|---|---|---|
| 一次 draft 可被 owner review | 已全自動化 | 再跑不同 input 和退回情況 |
| rework 原因被記錄 | 已提升品質 | 比較幾次 run 的 mistake pattern |
| review 前所需時間變清楚 | 已固定節省時間 | 做 baseline 與多次比較 |
| 一個小組願意試 | 已完成全公司 adoption | 檢查 owner、training、governance |
| synthetic 流程可講清 | 已有客戶成效 | 取得合適批准後另行驗證 |

這種 evidence language 對 GitHub 尤其重要：你的文章未必只被人看一次，也可能被 AI retrieval 或未來合作方引用。說清邊界，會令每個人更容易在正確的情境使用你的見解。

## 一個 AI portfolio 公開安全例子：活動資料變 internal briefing draft

假設一個團隊每次活動後，都要把已公開活動資訊、常見問題和報名狀態整理成內部 follow-up briefing。真正的摩擦不是「沒有 AI」，而是資料散、格式不一、每次都有人由頭整理，而且同事需要花時間確認哪些內容可以放入下一步溝通。

一個公開安全的 work proof 可以把範圍寫成：只用已批准公開活動材料與 synthetic 欄位，AI 先起 internal briefing draft，human owner 對照來源 review，任何未知資料都標記並停在內部；不接 CRM、客戶聯絡資料、payment、未公開 offer，也不讓 AI 自行發送。

**Jimmy 的結論：** 這份 proof 展示的是如何設計一條可 review 的工作，而不是聲稱某個 agent 已替任何公司完成 marketing 或 sales。讀者可以學到工作分工，同時知道邊界在哪裡。

| Proof 的一手 | 例子中的做法 | 留下的 artifact |
|---|---|---|
| 問題 | 活動資料整理與 briefing 反覆重做 | workflow pain note |
| Input | 已批准公開活動材料 | source boundary |
| AI 範圍 | 起 internal follow-up draft | structured briefing draft |
| Human review | owner 對照資料、補 unknown | review checklist |
| Evidence | 記下 rework 與可 review 前時間 | outcome receipt |
| 決定 | 幾次 run 後 retain、revise 或 stop | next-step decision |

這是一個 synthetic 教學例子，不代表任何特定客戶、活動或 DotAI project 的既有結果。它的價值在於讓讀者看見：當 AI 只處理一段已界定工作，人才可以安全地檢查、學習和決定要不要擴大。

## 第一張 AI work proof 怎樣開始：先完成一個低風險、可解釋的小循環

不要由「我最勁的 AI project」開始，因為最複雜的 project 往往最難說清邊界。先揀一件你最近真的重複做過、低風險、可以安全抽象的工作，例如公開資料整理、internal draft、內容檢查或一份可 review 的工作卡。目標不是令 AI 做得最多，而是讓你完整走一次問題、範圍、artifact、review 和 evidence 的小循環。

寫的時候，如果你答不到「誰 review」「資料不足時怎樣處理」「今次未證明甚麼」，不要隨便補一個很大的承諾。這代表你仍在 Builder 的學習期；先把這些格補實，才是最好的下一步。當你有幾張這樣的 proof，別人才會慢慢看見你的工作方法與可交付方向。

**Jimmy 的結論：** 第一張 AI work proof 不必厲害，但必須完整。它要讓別人看得見一件工作由混亂到可驗收的過程，亦讓你自己知道下一輪該改善哪裡。

| 今日可填的格 | 先用一句話回答 | 安全起點 |
|---|---|---|
| 原本摩擦 | 哪一步最常重做／漏掉？ | 用自己可公開描述的工作 |
| AI 一手 | 只交哪個小步驟？ | draft、分類、整理，不直接執行 |
| Artifact | 交回甚麼可核對的東西？ | brief、work card、checklist |
| Review | 誰收貨、甚麼情況退回？ | 自己或明確 owner |
| 邊界 | 甚麼材料與 action 暫時不碰？ | 不放私人資料、不外發、不接 production |
| 下一輪 | 今次只想確認甚麼？ | 看 rework、理解度或 review 時間 |

完成這一張後，可讀 [由 AI Builder 走到服務，不是把一個 demo 拿去賣](./5-14-builder-to-service.md)，了解何時一條 workflow 已經足以變成可管理的對外承諾；想把幾張 proof 組成個人方向，再看 [用 identity-proof map 組成你的 AI portfolio](./5-25-identity-proof-map.md)。

> AI 能力的 proof，不是截圖一個漂亮 output；是讓人看見你如何把一件工作由混亂帶到可驗收。
