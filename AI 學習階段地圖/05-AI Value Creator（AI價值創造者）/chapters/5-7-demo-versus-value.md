# AI 做到一次，不等於真係幫到人：由 Demo 到價值，中間差咗甚麼？

見到一個 AI demo，最自然反應是「嘩，原來做到」。它可以在幾分鐘內把抽象想法變成可見畫面，也能幫團隊開始討論可能性。但對真正的工作流程而言，demo 只回答第一條問題：在這次材料、這個情境下，它能不能產出一個結果？

它還未回答下次可不可以再做、誰會用、輸出哪裏需要 review、例外會在哪裏停、或者是否令工作更清楚、更快、更準或更安全。若把一次漂亮 output 直接叫成轉型或 ROI，團隊會跳過最重要的學習，然後在真實資料、真實使用者和真實後果出現時才發現問題。

Jimmy 的看法是：Demo 證明可能性；價值要由真工作、真 owner 和可回看的 evidence 慢慢證明。由 demo 走到 value，不是減少興奮，而是把興奮轉成一條可 review、可重跑、可決定下一步的 workflow。

| 由 demo 到價值的階段 | 它真正證明甚麼 | 還未證明甚麼 |
|---|---|---|
| Demo | 一次在特定情境能產出結果 | 真工作可安全重複 |
| Reviewed artifact | 有人能指出可用與不可用部分 | 多輪結果是否改善 |
| Bounded pilot | 一小段 workflow 可被觀察 | 值不值得全面擴大 |
| Outcome evidence | 質量、時間、rework 或風險的變化 | 完整 ROI 或全公司成功 |
| Decision | retain、revise、stop 或小幅 expand | AI 可以自行作高後果決定 |

## AI demo 點解值得做，但不應被叫成成功：它只證明一次可能性

Demo 很有用。它能讓一個抽象的提議，例如「AI 可以幫手整理資料」或「AI 可以幫手起草內容」，變成大家看得見的東西。這能降低討論門檻，讓團隊開始問「這個能力可否用在我們的某一條工作」。沒有 demo，有些人甚至很難想像 AI 能做甚麼。

問題在於 demo 常用的是整理好的材料、預設輸入和順利情境。真實工作卻有資料不齊、版本不明、例外情況、不同使用者和臨時要求。demo 跑通並不代表那些因素已被處理，也不代表 AI 已有權讀真資料、直接行動或承諾結果。

**Jimmy 的結論：** 不要反對 demo；只要叫對它的名字。它是一個可能性證明，不是價值證明。demo 後最重要的問題是「這一個 output 想進入哪一條真 workflow？」。

| Demo 可以幫你知道 | Demo 無法自己回答 | 下一個合理動作 |
|---|---|---|
| AI 能否做出某種 output | output 是否可被 owner 使用 | 交 reviewer 看 artifact |
| 某種工具有甚麼能力 | 能否在不同 input 下重跑 | 限定範圍跑一次 pilot |
| 團隊對哪個方向有興趣 | 資料、權限、風險是否可接受 | 寫 input boundary 與 stop line |
| 一次結果看起來如何 | 長期是否減少 rework | 留 outcome observation |

只要團隊誠實保留「這只是一個 demo」的狀態，它就不會浪費；它會變成選第一條 pilot workflow 的好材料。

## Reviewed artifact 怎樣把一次 output 變成可討論工作：讓人指出可用、不可用與未知

一份 output 開始對別人有用，不是在它看起來很完整的時候，而是在真正負責這條工作的的人能按標準 review 它。reviewer 應能指出哪些段落可保留、哪些 claim 要補來源、哪些地方不應由 AI 推論、哪些資料仍未知。這把「好像可以」變成可處理的 feedback。

例如團隊每星期要把已批准公開資料整理成 management briefing。AI 第一次交出排版整齊的摘要，這是 demo；當 briefing owner 對照原資料，標出每段是否有 source、哪些觀察需標為推論、哪些欄位缺失，才變成 reviewed artifact。團隊開始知道 AI 在哪裏幫到手、哪裏仍不能信。

**Jimmy 的結論：** AI output 的第一個價值，是變成一份能被人收貨或退回的 artifact。沒有 review 的漂亮答案，只是待處理材料；有 review 的 artifact 才能成為下一輪 workflow evidence。

| Artifact 狀態 | Reviewer 可以看甚麼 | 下一步 |
|---|---|---|
| 只得一段 AI 答案 | 語氣與表面完整度 | 還未能安全用 |
| 有固定欄位的 draft | input、格式、缺欄 | 補資料或 refine |
| 有 source／unknown 標記 | claim、推論與資料邊界 | pass、revise 或 stop |
| 有 review receipt | 修改原因與 owner 決定 | 可以重跑同一範圍 |
| 有多輪版本 | 重複錯誤與改善痕跡 | 決定是否做 pilot |

reviewer 不是要把 AI 生成全部推倒重來；他的工作是讓團隊看清楚 output 哪一格可以被信任、哪一格仍需人承擔。

## Bounded pilot 點樣讓團隊由「原來做到」走到「值不值得繼續」

當一份 artifact 已經可以被 review，下一步不是全公司推出，而是在小範圍重跑一段真工作。bounded pilot 會指定 AI 只做哪一步、只讀哪些材料、交甚麼 internal output、誰 review、何時 stop，並在幾次 run 後看一兩個 outcome。

這一步讓團隊面對 demo 沒有的問題：輸入有沒有缺口？不同人是否理解同一條 rule？review 成本有沒有增加？AI 是否正確在 unknown 時停下？結果有可能是值得保留，也有可能是這條工作現在不適合 AI。兩個結果都比假裝成功更有價值。

**Jimmy 的結論：** Pilot 的目的不是逼出成功故事，而是讓一條 workflow 產生可學習 evidence。只要範圍、owner、quality bar 和 decision date 清楚，停止也會是一個好結果。

| Pilot 必要元素 | 沒有它會怎樣 | 一個安全設定 |
|---|---|---|
| Bounded workflow | 不知 AI 到底幫了哪裏 | 只起 internal draft |
| Approved input | context 混亂或越權 | 指定公開／已批准資料 |
| Human review | output 被誤當完成品 | owner 用 checklist 收貨 |
| Stop line | 資料不足時 AI 硬猜 | unknown／escalation receipt |
| Decision date | pilot 無限延長 | 跑三次後 retain／revise／stop |

不要因為 demo 成功就跳過 pilot。真正的價值通常是在 pilot 的例外、退回和修正裡才逐步被看見。

## Dashboard、repository 與 deploy 點解不自動等於成果：畫面存在不代表工作已改善

dashboard、截圖、repository、甚至 deploy 了的網址，都可能是工作的一部分。它們可以證明某個畫面存在、某段 code 能跑、某次流程成功過；但它們不會自動說明這個系統處理了哪一條 workflow、讀了甚麼資料、誰驗收、例外怎樣處理，或有沒有令工作變好。

對管理者、客戶或團隊來說，更重要的是回到工作問題：原本摩擦是甚麼？AI 現在讀甚麼、不能讀甚麼？output 由誰判斷可用？在甚麼情況停止？又有沒有一項可回看的質量、速度、重工或風險訊號？答不到這些，畫面再漂亮也仍然是值得研究的 demo。

**Jimmy 的結論：** 介面、code 和 deploy 是系統證據，不是價值證據。價值要在 workflow outcome 裡看：一份工作有沒有更可用、可控和可改善。

| 看得見的東西 | 它能證明甚麼 | 它不能代替甚麼 |
|---|---|---|
| Dashboard | 一個狀態被展示 | workflow 是否有效 |
| Repository | 有實作與版本 | owner 是否能使用 |
| Live URL | 一個服務可訪問 | 是否已安全上線或創造價值 |
| Agent 圖 | 有角色設計 | hand-off 與權限清楚 |
| Demo video | 一次流程跑通 | 多輪 outcome evidence |

如果你要展示工作，最好同時展示 workflow 問題、artifact、review 和下一步決定。這比只展示畫面，更能令別人明白實際價值。

## AI value 點解不是「人人都有 account」：價值要有真 owner、真資料邊界和真決定

公司買了工具、同事上過堂、甚至每個人都偶爾用 AI，都不代表 AI 已經創造價值。價值開始出現，是當一條真 workflow 有清楚 owner、資料和權限邊界、review 位置，以及一個大家同意怎樣看的 outcome。這些條件令團隊不會把一次性的好結果誤解成系統能力。

這也是第一個 pilot 應小的原因。小不是因為目標小，而是因為你要先把未知變成可學到的東西。你不需要一開始承諾一個大 Agent OS；你需要先找到一條可以安全試、可以回看、可以根據 evidence 決定下一步的工作。

**Jimmy 的結論：** AI 的價值不是它一次做了幾多，而是人開始知道哪一件工作因為它而真的變得可用、可控和可改善。沒有 owner 和 decision 的 output，不會自動變成價值。

| 「我們已經有 AI」的證明 | 為何仍未夠 | 價值 evidence 要再補甚麼 |
|---|---|---|
| 每人都有 account | 只代表可試用 | 一條 workflow 的 owner 與 artifact |
| 有很多 demo | 只代表一次可能 | 多輪 pilot 與 outcome |
| 有 Agent／tool list | 不知每個的責任 | input、stop line、handoff |
| 有成功案例描述 | 未必有可回看限制 | source、review、決定理由 |
| 有 ROI 預測 | 未跑過工作 evidence | 真實 quality／time／risk 觀察 |

真正的 adoption 是把工具能力放入人能夠理解、review 和改良的工作設計裡，而不是叫大家相信技術本身會帶來價值。

## 一個公開安全例子：由一份 briefing demo 走到有 evidence 的 pilot

假設團隊示範 AI 把三篇已批准公開文章整理成管理層 briefing。第一次生成的摘要排版整齊、結構清楚，這很值得展示；但它仍只是 demo。下一步是請 briefing owner 檢查：每個主張是否有來源、哪些是 AI 推論、哪些地方不適合放進真 briefing。

若 owner 看過後覺得可嘗試，團隊可跑一個小 pilot：AI 只讀指定公開資料，交一份 internal briefing draft，所有 claim 要有 link、未知要標示；owner review，不能直接對外發送或作任何商業承諾。跑三次後比較第一版可 review 前時間、被退回補來源的原因和 reviewer 清理成本。

**Jimmy 的結論：** 這個過程沒有否定 demo 的價值；它把 demo 變成了 workflow 學習。最後可能 retain、revise 或 stop，但每個選擇都有 evidence，而不是由興奮決定。

| 階段 | 在例子裡發生甚麼 | 可以誠實聲稱甚麼 |
|---|---|---|
| Demo | 一次生成 briefing 摘要 | 這個 output 可能可行 |
| Review | owner 核對 source 與推論 | 哪些格可用、哪些要改 |
| Pilot | 限定 input、artifact、review | workflow 正在被測試 |
| Outcome | 比較時間、rework、風險 | 是否值得下一輪 |
| Decision | retain／revise／stop | 現時 evidence 支持的方向 |

這個例子使用公開資料和 internal draft，並不代表任何實際團隊已有相同成效；它不讓 AI 讀私人／客戶資料、直接外發、公開內容或改 production 系統。

## 今日怎樣把一個 demo 變成下一步：先留低假設、owner、stop 與 evidence

如果你剛做完一個令大家興奮的 demo，先不要急著說已經有價值。寫四件事：這次 demo 依賴了甚麼乾淨假設、哪一條真 workflow 最接近、誰會 review 真實 artifact、甚麼 evidence 會令你 decide retain、revise 或 stop。這四件事會把活動變成 pilot 的起點。

接著只選一個低風險 hand-off，保持 output 在 internal review 層。不需要一開始追大規模使用，也不需要先算 ROI；你要的是讓下一輪 result 可以被比較和討論。這才是由 demo 走向真價值最短、亦最安全的路。

**Jimmy 的結論：** AI 做到一次，是邀請你設計下一個問題；不是邀請你跳過所有檢查。將 demo 的假設、owner、stop 與 evidence 寫下來，它才會變成可用的 adoption 起點。

| Demo-to-pilot card | 你要寫甚麼 | 安全起點 |
|---|---|---|
| Demo 假設 | 哪些資料／情境太理想化 | 指定三篇公開文章 |
| 真 workflow | 它最接近哪一手工作 | internal briefing draft |
| Owner | 誰會 review 與決定 | content／briefing owner |
| Stop line | 何時不繼續 | 缺 source、敏感資料、外發請求 |
| Evidence | 一兩個 outcome | 可 review 時間、rework |
| Decision date | 何時檢討 | 三次 run 後 |

未做完這個低風險 pilot 前，暫時不要把一次漂亮 output 當成 transformation、把 AI 接到外部發送、客戶／私人資料、公開設定或 production。下一步可看 [如何用 workflow outcome，而不是工具使用量，判斷 AI 價值](./5-5-workflow-outcome-not-tool.md)。

> Demo 證明可能性；價值要由真工作、真 owner 和可回看的證據慢慢證明。
