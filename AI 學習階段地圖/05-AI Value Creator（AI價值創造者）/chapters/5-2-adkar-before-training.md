# 教咗 AI 工具點解團隊都唔用？Training 前先診斷人究竟卡喺邊

公司買了 AI 工具、安排了 workshop、同事也學過幾個 prompt，三十日後卻發現日常工作沒有改。很多人第一反應是「要再教一次」或「大家不肯學」；但這兩個說法通常把不同問題混成一個 training 問題。

有人可能根本不相信這條 workflow 需要改，有人擔心 AI 會令自己更忙或更危險，有人懂示範卻在真實工作壓力下做不到，也有人試過一次但沒有 owner、時間或回饋令他持續做。若你只補工具技巧，真正卡住的那一關會原封不動。

Jimmy 的看法是：AI adoption 不應由「教甚麼工具」開始，而應由「這個團隊的變化卡在哪裏」開始。ADKAR 是一個有用的診斷框架：Awareness、Desire、Knowledge、Ability、Reinforcement 五層提醒我們，training 只處理其中 Knowledge；而真正 adoption 要讓人明白、願意、做得到並持續使用新的工作方式。

| Adoption 層 | 你要診斷的問題 | 合適的第一步 |
|---|---|---|
| Awareness | 大家明不明白為何要改這條工作？ | 展示目前摩擦與第一個安全成果 |
| Desire | 他願不願意投入改變？ | 聽擔心、利益與真實阻力 |
| Knowledge | 他知不知怎樣做？ | 有情境的短教學與工作卡 |
| Ability | 他在真工作下做不做到？ | 低風險試行、同伴支援與 review |
| Reinforcement | 他為何下星期仍會繼續？ | owner、回饋、可見 evidence 與調整 |

## AI training 點解經常做完就消失：工具知識只是 adoption 的中間一關

一堂 AI workshop 可以讓人看到可能性，也可以教會一些基本操作。可是，學生在課堂裡完成一個 prompt，不代表他回到工作時知道哪條流程值得用、可用哪些資料、結果應交給誰、出錯怎樣處理。工具知識離真實工作很近，卻仍然不是工作改變本身。

最常見的錯配是團隊其實不覺得改變有需要，或者擔心做了反而增加風險，管理層卻不斷提供更多 prompt template。反過來，有人已經想試、也看見價值，但沒有一條低風險 workflow 讓他練習和得到 feedback；再多策略分享同樣不會令他做得到。

**Jimmy 的結論：** training 很重要，但它只解決「知不知怎樣做」。在安排下一堂課前，先判斷團隊缺的是為何要變、願不願變、做不做到，還是有沒有理由持續做。

| 看到的情況 | 可能不是甚麼問題 | 更可能要檢查哪一層 |
|---|---|---|
| 上過堂但沒人用 | 再多 prompt 不一定有用 | Ability 或 Reinforcement |
| 同事說「與我工作無關」 | 不一定是懶或抗拒科技 | Awareness |
| 同事說「怕出事」 | 不只是工具不熟 | Desire、governance 或技術風險 |
| 有人想試但很快放棄 | 不一定缺熱情 | workflow、support 或 Reinforcement |
| 示範時做到、日常做不到 | 不等於不懂 | Ability 在真實壓力下不足 |

當你能指到一個層，而不是籠統說「大家不投入」，改變才有一個可以設計的起點。

## Awareness 點樣由口號變成真理由：讓人先看見哪一條工作值得改

Awareness 不是叫大家相信 AI 很重要，而是讓團隊看見現在這條工作到底在哪裏浪費時間、容易漏項、需要重做或帶來風險。若沒有一個具體摩擦，AI 只會像管理層又推來的一個新工具；同事自然難以判斷它與自己有何關係。

最有用的內容不是一堆未來趨勢，而是一條大家熟悉的工作：每次活動後誰整理資料？哪個欄位經常漏？哪個交接令下一手要重問？當大家共同看見這個 friction，才能討論 AI 是否適合協助其中一小手，而不是要求所有人抽象地「擁抱轉型」。

**Jimmy 的結論：** Awareness 的目標不是說服人愛上 AI，而是讓人同意一條真 workflow 值得改善。沒有共同問題，就不會有共同的改變理由。

| 只講口號 | 改成看真工作 | 團隊可以看見甚麼 |
|---|---|---|
| 「AI 是大趨勢」 | 「活動後 briefing 為何每次都重做？」 | 明確的 rework 摩擦 |
| 「大家要學 AI」 | 「哪個欄位最常漏，誰因此要補？」 | 可處理的品質缺口 |
| 「要提高效率」 | 「由資料齊到可 review 現在要多久？」 | 可觀察 cycle time |
| 「別落後」 | 「哪一手其實不應由人重複做？」 | 合適的 AI hand-off |

先讓大家同意問題的存在，再談解法。若連問題都沒有共同認知，任何工具教學都會被視為額外負擔。

## Desire 點樣聽清楚阻力：反對不是懶惰，而是重要診斷資料

Desire 關乎人願不願意改變。有人可能擔心自己做錯、怕資料外洩、怕 AI 令工作被監控、怕新流程只會加重負擔，也可能已經試過一個不好用的工具。把這些聲音一概叫作 resistance，然後加強宣傳，往往只會令團隊更不信任。

較好的做法是先聽，不急著說服。問一位實際使用者：「你覺得這條工作真係需要改嗎？」「你最擔心哪個後果？」「如果只試一個很小步，你希望它先替你解哪個麻煩？」答案會幫你分清問題是在利益、風險、工作量，還是工具本身根本不可行。

**Jimmy 的結論：** resistance 不是 enemy；它是 adoption dashboard。先分清是合理風險、缺少誘因、還是工具不適合，才知道該修治理、改 workflow 還是暫停試行。

| 同事的說法 | 可能訊號 | 不應立即做甚麼 |
|---|---|---|
| 「我不覺得需要」 | 還未看到 workflow 摩擦 | 強迫學更多工具 |
| 「我怕資料出事」 | governance 或信任未清 | 說「AI 很安全」但不講邊界 |
| 「我沒有時間學」 | 新流程沒有減少現有負擔 | 再加一個長 workshop |
| 「上次試過沒用」 | 工具、input 或工作設計失配 | 把失敗歸咎於態度 |
| 「誰對錯負責？」 | owner、review、stop line 缺失 | 叫 AI 自己保證準確 |

有些反對確實指出真風險。當工具在語言、資料格式、網絡或權限上不可行，先解技術問題；不要把正確警告包裝成「員工還未過關」。

## Knowledge 與 Ability 點解不同：識得聽課，不代表在真實工作做得到

Knowledge 是知道甚麼工具、甚麼 prompt、甚麼流程可以用；Ability 是在自己的真實工作壓力、資料限制、時間限制和 owner review 下，仍然能把那條工作跑起來。兩者之間往往有很大距離。課堂 demo 的資料乾淨、任務短、沒有後果；真工作則充滿缺欄、例外和需要交接的地方。

因此，教學應由真實但低風險的工作開始。讓人練習把已批准材料整理成 internal draft、標未知、交 review receipt，而不是一開始要他用 AI 完成對外或不可逆任務。當有人做不到，先看 task card、context、checklist 和時間是否設計得夠小，而不只是說他還不熟練。

**Jimmy 的結論：** Knowledge 讓人知道路；Ability 要讓人真係行過一次。AI adoption 的教學要包含工作卡、實際 run、review 和修正，而不只是教幾個好 prompt。

| 課堂知道的事 | 真工作能力要多一格 | 可設計的練習 |
|---|---|---|
| 知道如何起草 | 知道可用甚麼 source | 已批准公開材料 draft |
| 知道可上傳文件 | 知道哪些不可上傳 | source boundary card |
| 知道 AI 可分類 | 知道如何驗收分類 | checklist 加 review |
| 知道如何寫 prompt | 知道缺資料何時停 | unknown／stop receipt |
| 知道工具功能 | 知道怎樣交接下一手 | artifact 與 owner |

若團隊只有 Knowledge 而沒有 Ability，你不需要再講更多未來圖景；你需要一條更小、更安全、更容易得到 feedback 的 workflow。

## Reinforcement 點樣令新習慣留下來：30 日後仍有人用，先算 adoption

很多 adoption project 在 workshop 當日很成功，兩星期後卻回到舊習慣。原因未必是內容不好，而是新做法沒有被放進日常節奏：沒有人問那條 workflow 有沒有跑、沒有人看 artifact、沒有時間讓人練習，也沒有在失敗時協助修正。人自然會回到最熟悉、最快完成眼前工作的方式。

Reinforcement 不代表要用獎勵逼人打卡。它可以很簡單：為 pilot 指定一位 owner，每週看一次 output、review receipt 和一兩個 outcome；當出現問題，就修 input、rule 或 scope，而不是責怪使用者。這會讓團隊知道新做法不是一次性活動，而是一條可以一起改善的工作。

**Jimmy 的結論：** workshop 完不等於 adoption 完。真正的問題是三十日後，這條 workflow 有沒有人跑、能否說出它的 evidence、出錯後有沒有被修正。

| 沒有 reinforcement 時 | 可加入的最小支持 | 留下甚麼證據 |
|---|---|---|
| 大家回到舊做法 | 固定 owner 每週看一次 | run receipt |
| 出錯後不敢再用 | 把 unknown／stop 視為正常 | 改善清單 |
| 沒人知道有冇幫到手 | 選一兩個 outcome 觀察 | cycle time、rework、漏項 |
| 新同事不會接手 | 保留工作卡與 source boundary | 可重跑的契約 |
| manager 只看使用率 | 看 workflow artifact | 可討論的實際結果 |

Reinforcement 也是誠實停止的機制。若跑了幾輪仍然沒有改善、治理成本太高或同事指出合理風險，owner 應能選擇 revise 或 stop，而不是硬把使用率撐上去。

## 一個公開安全例子：由「教 AI」改成帶團隊完成第一個可 review 的工作

假設團隊要改善活動後資料整理，過去每次都由不同人找 brief、寫 internal follow-up draft，review 時才發現資料缺失。若只做工具 training，大家可能學會問 AI 寫 email，卻沒有改到這條真 workflow。

較好的做法是先讓團隊看到摩擦，並一起選一個低風險 hand-off：AI 只讀已批准活動 brief、公開 FAQ 和欄位格式，起一份 internal draft，缺資料便標 unknown；內容 owner review，任何對外發送或客戶資料都不進 pilot。大家在一次真實但安全的 run 裡學會 source、artifact、review 和 stop line，而不只是在課堂看示範。

**Jimmy 的結論：** 這種做法同時照顧 Awareness、Knowledge 和 Ability；之後由 owner 每週看 review outcome，才有 Reinforcement。Desire 則來自團隊親眼看到它是否真的減少一個麻煩，而不是被要求相信。

| ADKAR 層 | 在例子裡怎樣發生 | 可看見的結果 |
|---|---|---|
| Awareness | 看見反覆漏欄與 rework | 共同問題描述 |
| Desire | 團隊選擇先解最麻煩一手 | 可接受的小試行 |
| Knowledge | 學 source、格式與 stop rule | work card |
| Ability | 跑一份 internal draft | artifact 與 review |
| Reinforcement | owner 每週看 outcome | retain、revise 或 stop |

這個例子是公開安全的教學情境，不代表任何特定團隊已得到相同結果；它也不讓 AI 接觸私人／客戶資料、對外發送或改 production。

## 今日怎樣診斷團隊卡在哪一關：先做一次低壓對話，不急著排課

選一個你覺得「教過但沒人用」的 AI 工具或流程，找一位當時受訓、現在少用的同事，先問兩條問題：「你覺得這條工作真係需要改嗎？」「如果要改，最大阻力是甚麼？」聽答案，不急著解釋或說服。

把答案放回五層：不覺得要改多數是 Awareness；看見問題但不想試，可能是 Desire；想試但不知道怎做，是 Knowledge；知道卻在真工作做不到，是 Ability；做過一次但沒持續，是 Reinforcement。若答案是「工具在我們的語言或資料格式下根本不可用」，先回去查技術可行性，不要用 ADKAR 蓋過它。

**Jimmy 的結論：** AI adoption 的第一個 leader 動作不是安排更多 training，而是做一個正確診斷。知道團隊卡在哪一關，才知道下一個安全、有效的支持是甚麼。

| 聽到的答案 | 初步診斷 | 較合適的下一步 |
|---|---|---|
| 「我不覺得這件事要改」 | Awareness | 一起看 workflow 摩擦 |
| 「我怕弄錯或增加工作」 | Desire／governance | 聽風險，設低風險 pilot |
| 「我不知道怎樣開始」 | Knowledge | 情境化工作卡教學 |
| 「課堂識，返工做不到」 | Ability | 小 workflow run 加 review |
| 「試過但後來沒再用」 | Reinforcement | owner、節奏與 outcome review |

不要用這張表標籤人，更不要把所有 resistance 當態度問題。它只是幫你選一條較可能有用的下一步，並在實際 pilot 後再修正判斷。接著可看 [如何帶領團隊完成第一個安全成果](./5-10-first-safe-outcome.md)。

> 公司買咗 AI 工具冇人用，通常唔係員工懶，而係你跳過咗 change management。人未明點解要變、未見到自己有咩得著，你俾多十條 prompt 都冇用。
