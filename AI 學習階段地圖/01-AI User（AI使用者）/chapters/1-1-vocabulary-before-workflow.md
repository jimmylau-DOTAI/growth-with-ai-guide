# AI 術語新手教學：Prompt、Context、Agent、Codex 是甚麼？先用工作語言理解

第一次看 AI 教學，很容易在第一頁已經遇到一串字：Prompt、Context、LLM、Agent、Codex、terminal、repo、MCP、API、commit。你本來只想試 ChatGPT 幫手寫一封 email，結果反而覺得自己好像未學 coding 就不能開始。

這種卡住感很正常，因為產品名、工程工具和工作方法常被放在同一句說。背到 MCP 的全名，也未必知道它和你手上的工作有甚麼關係；知道 commit 是版本紀錄，也未必知道為何讓 AI 改檔前要留一個安全點。

Jimmy 的重點係：術語不是入場考試，而是一張工作位置圖。你只要知道一個字負責哪一段、現在需不需要它、它會帶來甚麼責任，就可以先用 AI 做一件小工作，而不是等到「全部聽懂」才開始。

| 你見到的字 | 先用工作語言理解 | 現在要不要急住學 |
|---|---|---|
| Prompt、Context、Review | 一次工作怎樣交代、根據和收貨 | 要，這是 ChatGPT 起步地基 |
| Agent、Workflow、Skill | 如何把重複工作交接得更完整 | 做過幾次可驗收小工作後再學 |
| Codex、terminal、repo、commit | 如何在檔案或專案裡安全做改動 | 只有處理工作區／程式時才需要 |
| LLM、API、MCP | AI 的能力底座和資料／工具接駁 | 需要接系統或工具時才深入 |

## AI 術語太多跟唔上，點解不是你技術不夠？

有人會說「用 Codex 開 repo、接 MCP，再寫一個 agent workflow」。對做開技術的人，這是一句快捷語；對剛開始的人，它把不同層次的東西混在一起：有些是工具、有些是連接方式、有些則是工作方法。

所以你覺得自己跟不上，不是因為不夠聰明，而是缺少翻譯。真正有用的不是背所有定義，而是每遇到一個新字，都先問：它究竟是幫我思考、提供資料、做動作，還是保護我不出錯？

**Jimmy 的結論：** AI 術語的價值，在於幫你看清工作由哪裏開始、交給誰、在哪裏要停；不是用來證明你懂不懂技術。

| 先問的問題 | 它幫你避開甚麼誤會 | 一個例子 |
|---|---|---|
| 它幫我完成哪段工作？ | 不把產品名當能力本身 | Agent 是工作交接方式，不是神奇模型 |
| 沒有它，我可不可以先做第一輪？ | 不因新名詞延遲練習 | 不懂 API 仍可先做一份 ChatGPT briefing draft |
| 它會帶來甚麼資料、權限或驗收責任？ | 不把「接得到」誤認為「可以亂用」 | MCP 接到資料，也不代表可以讀所有資料 |

下一次有人丟出一個新名詞，你不需要即刻去學它；先把它放回工作位置，就已經知道它是否關你現在的事。

## Prompt、Context、Review 是甚麼，點解新手用 ChatGPT 一定要分清？

很多人以為「ChatGPT prompt 教學」就是學一些特別的句式。其實 prompt 只是一份工作交代；若沒有材料、限制和收貨方法，再漂亮的句子都只會令 AI 更流暢地猜你的意思。

把 AI 當作剛加入的同事會容易理解：你不會只說「幫我做好啲」，然後期待對方自動知道背景、格式、不能碰的內容和 deadline。你會交材料、講成果、說明哪些地方不可以猜，最後看一次它交回來的東西。

**Jimmy 的結論：** Prompt 是入口，Context 是根據，Review 是人手收貨；三樣一起出現，AI 才是在幫你做一段工作。

| 名詞 | 用工作語言講是甚麼 | 新手要做的最小動作 |
|---|---|---|
| **Prompt** | 今次交給 AI 的工作交代 | 說清今次要交甚麼成果 |
| **Context** | 可以依據的材料、背景、格式與限制 | 只給剛好需要、可安全使用的資料 |
| **Review** | 人檢查是否可用、是否修改或停止 | 逐格檢查，不把流暢當作正確 |

例如把三段公開資料變成 briefing：要求「列來源、日期、重點和待確認」是 prompt；貼進去的三段資料和「不可補外部事實」是 context；你核對每一格才決定是否採用，就是 review。分得開這三樣，便知道結果失準時應改材料、改交代還是改收貨標準。

## Context 不是越多越好，ChatGPT 到底需要甚麼資料？

初學者常在兩個極端來回：要麼只打一條很短的 prompt，然後怪 AI 不知道背景；要麼把整個資料夾、十幾條連結和所有歷史訊息塞進去，結果自己也不知道哪些才是今次工作的根據。

好的 context 不是「全部資料」，而是剛夠讓 AI 做今次工作所需的事實、例子、格式和限制。資料太少會讓它猜；資料太亂則讓它難以判斷甚麼最重要，還可能把不應交出的內容混進一次練習。

**Jimmy 的結論：** Context 的質量，不看你貼了多少，而看 AI 能否根據明確材料交出一份你能驗收的 draft。

| Context 類型 | 可以放甚麼 | 初學者要守住的界線 |
|---|---|---|
| 事實材料 | 公開文章、已批准文字、你自己寫的 synthetic 情境 | 不把客戶、合約、CRM 或未公開資料當練習素材 |
| 成果格式 | 欄位、表格、長度、讀者或使用場合 | 不只說「寫得專業」這類感覺詞 |
| 好／不好例子 | 一個可參考的語氣、禁止出現的說法 | 不照抄別人的私有內容或聲稱 |
| 邊界 | 資料不足時標待確認、不外發、不覆蓋正本 | 不讓 AI 用常識補成既定事實 |

你不必一次就整理完個人知識庫。先為一件小工作選三段安全材料、寫清一個輸出格式，已經是有效的 context 練習。

## AI Agent 是甚麼，它和普通 ChatGPT 對話真正差在哪裏？

「AI Agent」很容易被說成自動取代人的魔法員工。用工作語言講，它其實是在清楚範圍內接走一段工作：知道輸入是甚麼、要經過哪些步驟、交回甚麼成果，以及遇到例外時在哪裏停下來。

一般 ChatGPT 對話同樣很有用，特別適合討論、起草和探索。差別不在誰高級，而在重複工作是否已經有足夠清楚的輸入、輸出、完成線和人手 review，能夠被接成一段可管理的流程。

**Jimmy 的結論：** Agent 不是比 ChatGPT 更勁的聊天機械人；它是把一段工作交代、執行和驗收得更完整的安排。

| 一般 ChatGPT 對話 | 比較接近 Agent 的工作方式 |
|---|---|
| 你每次提出問題，拿回一個回覆 | 它在批准範圍內接資料、完成步驟、交回可 review 的成果 |
| 背景和上次修改留在你腦裏 | 有指定 context、規則、狀態或資料來源 |
| 結果靠你臨場判斷 | 有完成線、例外處理和人手 review 位置 |
| 適合即時探索 | 適合重複、可拆細、可驗收的工作段落 |

如果你尚未能寫出「這件工作交甚麼、甚麼時候停、誰收貨」，不需要急住叫它 Agent。先用對話跑通一次，才有證據判斷是否值得變成 template、Skill、automation 或 Agent。

## Codex、terminal、repo、commit 是甚麼，點解 AI 做檔案工作時會聽到？

當 AI 不只幫你寫一段文字，而要讀一組檔案、修改網站、建立小工具或跑測試，工作就需要一個可控制的地方。Codex、terminal、repo 和 commit 常在這個階段出現；它們不是 AI 入門門票，而是把改動變得可看、可驗和可回退的工具。

即使你不是工程師，理解這幾個字仍有用，因為你會知道何時應停下來 review，何時不應直接分享改動。你不必為了看懂它們而立即開 terminal，更不需要把任何檔案推上 GitHub 才算「開始學 AI」。

**Jimmy 的結論：** 當工作由聊天走到改檔案，最重要不是趕快做更多，而是知道改了甚麼、誰批准，以及怎樣保留回退點。

| 名詞 | 在工作裡的位置 | 甚麼時候才需要關心 |
|---|---|---|
| **Codex** | 可在工作區、檔案或程式專案裡協助完成任務的 AI | 需要處理一組文件、建立小工具或修改專案時 |
| **terminal / CLI** | 用文字指令操作檔案、工具或程式的入口 | 某項工作需直接跑指令，而非只按網頁按鈕時 |
| **repo** | 有版本記錄的專案資料夾 | 多個檔案需一起維護或交接時 |
| **commit** | 一個可回看、可比較的改動記錄點 | 重要改動已檢查、想留安全點時 |
| **push** | 把本機已確認版本送到遠端平台 | 只有檢查並明確決定分享／發布後才做 |

如果你此刻只想把公開資料整理成一頁 briefing，ChatGPT 加一張工作卡就足夠。先認得這些字的作用，等工作需要它們時再用，反而較安全和順暢。

## LLM、API、MCP 放喺邊？用一條工作鏈看清它們

LLM、API 和 MCP 通常在講 AI 系統整合時出現，容易讓人誤以為自己要先學寫 code。其實它們是不同位置的名字：LLM 是理解和生成的能力底座，API 是系統之間交換請求與結果的入口，MCP 則是讓 AI 在受控範圍連接工具或資料的一種方式。

這些字本身不保證做得對。換更強模型不會自動補上錯漏資料；接通 API 或 MCP 也不等於可以讓 AI 讀所有資料、代你發訊息或做高風險決定。真正要保留的是範圍、權限、停位和 review。

**Jimmy 的結論：** 技術名詞最好的理解方式，是放回同一條工作鏈：誰負責想、誰提供資料、誰做動作、誰最後驗收。

```text
你要完成的工作
  → Prompt：交代成果與要求
  → Context：給它剛好需要的資料
  → LLM：理解與產生初步結果的能力
  → Agent / Workflow：把重複步驟串起來
  → Tools / API / MCP：在批准範圍內接資料或做動作
  → Review / Guardrail：核對、批准，遇到例外時停止
```

| 名詞 | 在這條鏈的角色 | 不能誤會成甚麼 |
|---|---|---|
| **LLM** | 理解與生成文字、圖像或判斷草稿的能力 | 換模型便等於有好 workflow |
| **API** | 系統對系統交換資料／請求的入口 | 人人都必須親自寫 code |
| **MCP** | AI 接工具或資料來源的受控連接方式 | 接通後就應該拿到所有權限 |

你現在未必要用完整工作鏈。它的作用，是讓你日後見到新工具時，先判斷它正試圖改變哪一段，而不是被名字牽著走。

## AI 新手現在要先學甚麼，哪些可以遲些再學？

AI 學習不需要照一張考牌表走，每個人的工作都不同。不過若你現在只是想用 ChatGPT 令一件日常工作清楚一點，先把 Prompt、Context、Review 和工作完成線講得出來，會比先研究所有 integration 有用得多。

當同一類工作已重複幾次、你看得見它的輸入與輸出，才開始看 workflow、Skill 或 Agent；當確實需要操作檔案或程式專案，才了解 Codex、repo 和 commit；要跨系統接資料時，才更深入 API、MCP 與權限。

**Jimmy 的結論：** 學習次序應該跟你的工作需要走，不是跟網上最潮的術語走。

| 你現在的情況 | 優先理解 | 暫時不用急 |
|---|---|---|
| 用 ChatGPT 起草、整理、比較 | Prompt、Context、Review | API、MCP、terminal、repo |
| 想交一件重複小工作 | 成果、材料、完成線、停位、workflow | 多 Agent、複雜 integration |
| 想讓 AI 處理檔案或小工具 | workbench、repo、commit、test | 直接 push 公開、接高權限工具 |
| 想接公司資料或跨平台動作 | 權限、資料範圍、owner、approval | 「接上了就全自動」的想法 |

這個次序不會限制你，只會令你更快把真正有用的部分練熟。你知道下一步為何要學，而不是被一串名詞推着走。

## AI 術語學完點樣驗證？用一件低風險工作講返出來

讀懂定義不代表你已經能用。最實際的驗證，是選一件低風險小工作，例如把三段公開資料整理成 briefing，然後不用看筆記，講出你要交甚麼、AI 可看甚麼、你怎樣收貨和哪裏要停。

這個練習也能幫你找到真正卡位：若你說不出可用材料，問題不是 Agent；若你說不出怎樣檢查，問題不是 prompt；若你不能界定停止線，則不應急住接更多工具。你能把問題放回正確位置，便已經開始建立 AI 判斷。

**Jimmy 的結論：** 你不是要背熟術語，而是要能用自己的工作證明你知道它們各自應該出現在哪裏。

```text
我今次想交給 AI 做的是：＿＿＿＿＿＿＿＿＿＿

它只可以看的 context 是：＿＿＿＿＿＿＿＿＿＿

我會用甚麼方法 review 它交回來的東西：＿＿＿＿＿＿＿＿＿＿

如果資料不足或超出範圍，它要在這裡停：＿＿＿＿＿＿＿＿＿＿
```

講得出這四句，你就不只知道 Prompt、Context、Review 是甚麼；你已經能將它們放進一件真工作。下一步可讀 [ChatGPT 新手教學：識得問 AI，點樣先可以將一件真工作交畀佢？](./1-6-start-here-first-ai-work.md)，把這張術語地圖變成第一次可 review 的練習。

## 學 AI 術語時，哪些資料和操作暫時不要急住碰？

「不交」不是保守，而是把學習安排在可控制的地方。新手最值得先避免的，不是某一個特定工具，而是那些一錯便難以回頭、你又未知道如何 review 的動作。

這不代表你永遠不能學 Agent、Codex 或 integration；相反，當你已能說清工作範圍、資料和人手批准，才會更快判斷哪一個工具真的值得接上，而不是為了追術語而把風險也接進去。

**Jimmy 的結論：** 第一輪守住資料界線、人手批准和可逆性，比多學三個英文縮寫重要得多。

| 情況 | 現階段的安全做法 | 為甚麼 |
|---|---|---|
| 客戶資料、合約、CRM、會議記錄、登入資料 | 不用作初學者練習 context | 先守住資料與授權界線 |
| 對外發送、公開發佈、付款、簽約 | 只讓 AI 起 draft，人做最後決定 | 動作難撤回，責任仍在人 |
| 不知道 repo／commit／push | 先在本機或練習材料理解改動 | 版本與分享是不同的決定 |
| 想接大量工具 | 先畫出一條小 workflow 和停止線 | 接通不等於適合自動化 |

> **耐用判斷：** AI 術語不是用來證明你懂技術；它們是幫你看清一件工作由哪裡開始、由誰負責，到哪裡要停的地圖。

## 想由聽得懂 AI 術語，走到真的用 AI 做工作？

當你把術語放回工作位置，下一件應做的不是再看一張名詞表，而是選一件可重做、可 review 的小工作試一次。你會因此知道自己是缺材料、缺標準還是缺安全邊界，而不是籠統地覺得「AI 很複雜」。

DotAI 從真工作、合適練習和人手 review 開始，協助個人和團隊把 AI 放進可看見、可驗收的工作裡。重點不是一開始追求全自動，而是先找一條值得試、能安全停下來的 workflow，再決定是否擴大。

**Jimmy 的結論：** 由聽得懂到做得到，中間不是多背術語，而是完成一次有材料、有完成線、有人收貨的 AI 工作交接。
